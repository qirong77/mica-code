# 【08】Code Agent 从零到一：离屏终端与 Shell 工具的下一步

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

这次先不实现新功能，只记录一个重要方向：**离屏终端**。

我在使用 Codex 时观察到一个很有意思的能力：它可以启动一个看不见的终端进程，先返回一部分输出，后续再继续读取，甚至可以继续写 stdin。比如：

```txt
exec_command(...) -> 返回 session id
write_stdin(session_id, ...) -> 继续写入或 poll 输出
```

这和 mica-code 现在的 `run_shell` 不一样。mica-code 当前只有两种模式：

1. 前台执行：等命令结束，把输出返回给模型。
2. 后台执行：把命令 detach 出去，stdout/stderr 写到临时文件，然后立即返回文件路径。

这已经能覆盖 `npm run dev`、watch 模式、长时间服务这类场景的第一阶段需求，但它不是一个真正的“终端 session”。它没有进程句柄，没有后续 stdin，没有 PTY，也没有 resize。

这篇文章记录两个问题：

- Codex 那种离屏终端大概是怎么做的。
- mica-code 当前的 bash/shell 工具还可以怎么优化。

---

## 一、现在的 `run_shell` 已经解决了什么

当前实现集中在：

```txt
packages/mica-tools/ToolRunShell.ts
```

它的接口很简单：

```ts
{
  command: string;
  timeout?: number;
  run_in_background?: boolean;
}
```

前台模式用 Node 的 `child_process.spawn`：

```ts
const child = spawn(input.command, {
  shell: true,
  detached: true,
  stdio: ['ignore', 'pipe', 'pipe'],
});
```

几个关键点：

- `shell: true`：让模型可以传一整段 shell 命令，而不是 argv 数组。
- `detached: true`：方便超时或 abort 时 kill 整个进程组。
- `stdout/stderr` 通过 pipe 回到 Node，再通过 `callbacks.onChunk` 流式展示到 UI。
- 默认 30 秒超时，超时后先 `SIGTERM`，5 秒后兜底 `SIGKILL`。
- 输出最终会经过 `finalizeTextOutput`，避免整段大输出塞回模型。

后台模式则更克制：

```ts
const fd = openSync(outputPath, 'w');
const child = spawn(input.command, {
  shell: true,
  detached: true,
  stdio: ['ignore', fd, fd],
});
closeSync(fd);
child.unref();
```

这里没有让 stdout/stderr 经过 Node stream，而是直接写文件。对 dev server 和 watch 模式来说，这比把所有日志挂在主进程事件循环上更安全。

所以当前方案已经解决了两个基础问题：

- 不让长时间运行的命令卡住 agent turn。
- 不让大部分后台日志持续占用模型上下文。

但它仍然不是“离屏终端”。

## 二、Codex 的能力模型：进程 session，而不是一次性命令

Codex 的实现可以在临时源码里看到几处线索：

```txt
temp/codex/codex-rs/exec-server/README.md
temp/codex/codex-rs/exec-server/src/local_process.rs
temp/codex/codex-rs/app-server-protocol/schema/typescript/v2/CommandExecParams.ts
```

它的核心抽象不是“执行命令并返回字符串”，而是：

```txt
start process -> process id
read output   -> after seq
write stdin   -> process id + bytes
resize pty    -> process id + columns/rows
terminate     -> process id
```

也就是说，命令执行之后，进程还被系统管理着。模型后续可以通过 process id 继续和这个进程交互。

Codex 的 `CommandExecParams` 里有几个非常关键的参数：

```ts
processId?: string | null;
tty?: boolean;
streamStdin?: boolean;
streamStdoutStderr?: boolean;
timeoutMs?: number | null;
cwd?: string | null;
size?: CommandExecTerminalSize | null;
```

其中 `tty: true` 是分水岭。

没有 PTY 时，子进程看到的是普通 pipe：

```txt
stdin.isatty() -> false
```

有 PTY 时，子进程会认为自己运行在真实终端里：

```txt
stdin.isatty() -> true
```

很多程序会根据这个差异改变行为：

- `npm`、`bun`、`pytest` 是否输出颜色。
- `python` 是否进入交互 REPL。
- `less`、`top`、`vim` 是否正常工作。
- 某些 CLI 是否显示 progress spinner。

Codex 的 `local_process.rs` 里会根据参数选择不同启动方式：

```rust
if params.tty {
    spawn_pty_process(...)
} else if params.pipe_stdin {
    spawn_pipe_process(...)
} else {
    spawn_pipe_process_no_stdin(...)
}
```

然后它把运行中的进程保存在 map 里：

```rust
process_id -> RunningProcess
```

`RunningProcess` 里保存：

- process session
- 是否是 tty
- 是否保留 stdin
- output ring buffer
- next seq
- exit code
- output notify
- close 状态

这就是“离屏终端”的关键。不是 UI 上有没有一个终端窗口，而是程序内部有没有一个可寻址、可继续交互的进程 session。

## 三、mica-code 当前还差什么

当前 `run_shell` 和 Codex 的差距可以用一张表概括：

| 能力                   | mica-code 当前            | Codex                 |
| ---------------------- | ------------------------- | --------------------- |
| 执行一次命令           | 有                        | 有                    |
| 流式输出               | 有一部分                  | 有                    |
| 超时终止               | 有                        | 有                    |
| 后台运行               | 有                        | 有                    |
| 后续读取后台输出       | 通过 read_file 读临时文件 | 通过 process id + seq |
| 继续写 stdin           | 无                        | 有                    |
| PTY                    | 无                        | 有                    |
| resize                 | 无                        | 有                    |
| terminate 指定 session | 无                        | 有                    |
| 进程状态查询           | 无                        | 有                    |
| 输出 ring buffer       | 无                        | 有                    |

这说明 mica-code 现在的问题不是“不能执行 shell”，而是 shell 工具仍然是一次性工具。

一个一次性工具的返回值只有字符串：

```txt
command -> output
```

一个终端 session 的返回值应该包含状态：

```txt
command -> { session_id, output, next_seq, exit_code? }
```

这两个抽象的复杂度差很多。为了不把项目一下子搞复杂，短期不应该直接照搬 Codex 的 exec-server。

## 四、如果以后要做，分两阶段

### 阶段一：非 PTY 的后台 session

第一阶段不碰 PTY，只把当前后台命令从“输出文件”升级为“进程 session”。

最小工具可以是：

```txt
run_shell({ command, run_in_background: true })
shell_read({ session_id, after_seq? })
shell_kill({ session_id })
```

内部维护一个 manager：

```ts
type ShellSession = {
  id: string;
  command: string;
  cwd: string;
  pid?: number;
  startedAt: number;
  exitedAt?: number;
  exitCode?: number | null;
  nextSeq: number;
  chunks: Array<{
    seq: number;
    stream: 'stdout' | 'stderr';
    text: string;
  }>;
};
```

这样可以先解决实际问题：

- dev server 启动后，agent 能继续读取新增日志。
- watch 命令失败后，agent 能看到退出码。
- 用户可以让 agent 停掉某个后台命令。
- 不需要模型去读 `/tmp/mica-tasks/*.out`。

这一版不用 PTY，所以复杂度可控。它仍然不能跑真正的交互式终端程序，但已经比“只给输出文件路径”好很多。

### 阶段二：PTY session

第二阶段再考虑 PTY：

```txt
run_shell({ command, tty: true })
shell_write({ session_id, chars })
shell_resize({ session_id, columns, rows })
```

Node/Bun 侧可选方案一般是 `node-pty`。但这会带来 native dependency、平台兼容、Bun 兼容、安装失败处理等问题。

更重的方案是像 Codex 一样做一个独立的 Rust helper 或 exec server。这个架构更稳，但明显超出 mica-code 当前阶段。

所以短期结论是：

> 先做 session 化后台进程，不急着做 PTY。

## 五、即使不做离屏终端，当前 shell 工具也有优化空间

参考 Codex 的设计，mica-code 当前 `run_shell` 有几个低风险优化方向。

### 1. 给输出增加结构化元数据

现在工具最终返回的是普通文本：

```txt
(退出码: 1)
...
```

这对人可读，但模型很难稳定解析。可以考虑在输出头部固定一段元信息：

```txt
[command]
cwd: /path/to/project
exit_code: 1
duration_ms: 1234
timed_out: false
stdout_truncated: false
stderr_truncated: false

[output]
...
```

这不需要改工具协议，也不需要新增工具，只是让返回文本更稳定。

Codex 的方向是把 `exit_code`、`process_id`、chunk metadata 都作为结构化数据管理。mica-code 可以先用文本格式模拟一部分。

### 2. 区分 stdout 和 stderr

当前前台模式把 stdout 和 stderr 都追加到同一个 `output` 字符串里。这样实现简单，但丢失了 stream 信息。

可以保留两个 buffer：

```ts
stdout += chunk;
stderr += chunk;
```

最终返回：

```txt
[stdout]
...

[stderr]
...
```

或者至少在 stderr chunk 前加标记。很多构建工具会把 warning/error 写到 stderr，区分 stream 对排错有价值。

Codex 的 output chunk 里有 stream 字段，这一点值得参考。

### 3. 明确输出截断状态

当前有两个限制：

```ts
const MAX_SHELL_OUTPUT_CHARS = 60_000;
const MAX_STREAM_CHARS = 120_000;
```

问题是：

- `MAX_STREAM_CHARS` 到顶后，后续 chunk 不再进入 `output`，也不再 `onChunk`。
- 最终 `finalizeTextOutput` 又按 60,000 字符截断。
- 模型能看到结果被截断，但不一定知道流式展示阶段也被截断过。

可以增加一个 `streamCapReached` 标志，首次达到时输出一条明确提示：

```txt
[命令输出过长，后续实时输出已停止收集；请缩小命令范围或重定向到文件]
```

这比静默停止更清楚。

### 4. 给后台输出加 size watchdog

当前后台模式把 stdout/stderr 直接写到临时文件，这很好，但没有文件大小守卫。

如果命令疯狂输出日志，可能写爆磁盘。

可以借鉴 Codex/Claude Code 的后台任务思路：

```txt
每 N 秒检查输出文件大小
超过上限后 kill 进程
在文件尾部写入终止原因
```

例如：

```txt
MAX_BACKGROUND_OUTPUT_BYTES = 64 * 1024 * 1024
```

这属于防御性优化，和是否做离屏终端无关。

### 5. 后台命令返回 pid 和更明确的后续操作

当前后台返回：

```txt
命令已在后台启动 (id: xxx)
输出文件: /tmp/mica-tasks/xxx.out
如需查看结果，用 read_file 读取输出文件。
```

可以补充：

```txt
pid: 12345
cwd: /path/to/project
stop: kill 12345
```

即使没有 `shell_kill` 工具，至少模型知道可以怎么终止。

不过这也有风险：直接建议 `kill pid` 不如未来提供 `shell_kill(session_id)` 安全，因为 pid 可能复用。所以短期可以展示 pid，长期应使用 session id。

### 6. 增加 `cwd` 参数

Codex 的命令执行支持 `cwd`。mica-code 当前 `run_shell` 总是在当前进程 cwd 下执行，模型如果要进子目录，只能写：

```sh
cd packages/foo && bun test
```

这可以工作，但有几个问题：

- display text 更长。
- shell 组合命令更难分析。
- 将来做权限或审计时不容易知道真实 cwd。

可以给工具加：

```ts
cwd?: string;
```

并做路径校验：

- 必须是当前 workspace 内路径。
- 相对路径解析到当前 cwd。
- 不允许跳出 workspace，除非用户明确允许。

这也是低风险优化。

### 7. 明确 shell 类型

`spawn(command, { shell: true })` 在 Unix 上通常使用 `/bin/sh`，不一定是用户的 `$SHELL`。

这会带来一些细节差异：

- zsh/bash 特性可能不可用。
- `source ~/.zshrc` 这类行为不一致。
- 本地用户以为自己在 zsh，工具实际在 sh。

可以考虑：

```ts
shell?: string;
login?: boolean;
```

但这要谨慎。login shell 会读取用户配置，启动更慢，也可能引入不可预测 alias/function。短期更好的做法是：在工具说明或输出元数据里明确当前 shell。

### 8. 危险命令提示或审批

Codex 有 sandbox/permission policy。mica-code 目前没有完整权限系统。

短期可以先做轻量提示，而不是硬拦截：

```txt
检测到危险命令：rm -rf / git reset --hard / git clean -fdx
```

如果未来做 approval，可以把这类命令接入审批面板。

注意：不要用很脆弱的正则把普通命令误杀。第一版只覆盖极少数明显危险模式即可。

### 9. Windows 和跨平台行为

当前 kill 进程组的逻辑是：

```ts
process.kill(-child.pid, signal);
```

这是 Unix 风格。Windows 上负 pid 不是同样语义，fallback 到 `child.kill(signal)` 也可能只杀 shell，不杀子进程树。

如果项目未来要支持 Windows，需要单独处理：

- Windows process tree kill。
- shell 选择。
- PTY 用 ConPTY。

这不是当前优先级，但需要记录。

## 六、优先级建议

如果只做稳健性，不做离屏终端，我建议优先级是：

1. **后台输出 size watchdog**：防止日志写爆磁盘。
2. **结构化返回元数据**：让模型稳定知道 exit code、duration、cwd、截断状态。
3. **stdout/stderr 分流**：减少排错信息丢失。
4. **stream cap 明确提示**：避免静默截断。
5. **cwd 参数**：减少 `cd xxx && ...` 命令串。
6. **后台 pid/status 信息**：为未来 session manager 铺路。
7. **危险命令提示**：先提示，后审批。
8. **PTY session**：最后再做，避免过早引入 native dependency 和复杂状态。

这条路线和 Codex 的方向一致，但不会一开始就复制它的完整 exec-server。

Codex 是成熟产品，需要支持本地、远程、沙箱、审批、PTY、stdin、resize、输出 delta、进程生命周期通知。mica-code 目前更适合从一个小的 `ToolRunShell` 演进：

```txt
一次性命令
  -> 防御性 shell 工具
  -> 后台任务
  -> session 化后台进程
  -> 可选 PTY
```

## 七、暂不实现的原因

离屏终端很诱人，但它不是一个小功能。

一旦引入 process session，就会带来一组长期问题：

- session 存在哪里，什么时候清理？
- agent 重启后，旧进程怎么办？
- 输出保留多少，按字符还是按字节？
- 多个 agent 同时操作同一个 session 怎么办？
- 用户按 abort 时杀不杀后台 session？
- command approval 和 shell session 怎么结合？
- PTY 输出里的 ANSI 控制序列如何展示和截断？
- 交互程序卡住时如何恢复？

所以当前选择是：先记录设计，不急着实现。

真正该先做的是几个低风险 shell 工具优化。它们不会改变工具抽象，却能让当前 `run_shell` 更可靠，也能为未来离屏终端打基础。

# 【10】Code Agent 从零到一：上下文压缩不是总结一下

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

Code Agent 聊久了，最先撞上的不是模型不聪明，而是上下文越来越脏。

一开始只有几轮对话：用户说需求，agent 读文件，跑测试，改代码。上下文还很清爽。再往后，终端输出、工具结果、错误堆栈、文件内容、反复修改的方案都会堆进历史。模型每一轮都要带着这些旧东西继续工作，直到某一刻开始变慢、变贵、变笨，甚至直接超过 context window。

这时候大家都会想到一个命令：`/compact`。

但真正做起来会发现，`/compact` 不是“让模型总结一下聊天记录”这么简单。总结太短，agent 会失忆；总结太长，压缩没有意义；只保留总结，最近的工具结果和用户措辞会丢；只保留最近消息，历史决策又会断；重复 compact，如果处理不好，还会把第一次 compact 的历史摘要吞掉。

这篇记录 mica-code 这次重做 `/compact` 的方案：参考 Claude Code 的 compaction 思路，但做成适合当前架构的轻量实现。

---

## 一、旧方案的问题：一条 checkpoint 解决不了长会话

mica-code 之前的 compact 逻辑很直接。

核心代码在：

```txt
packages/mica-context/CompactionService.ts
```

旧方案大概是：

```txt
messages -> build transcript -> model summary -> [Mica compact checkpoint]
```

压缩后，整个会话只剩一条 user message：

```ts
[
  {
    role: 'user',
    content: '[Mica compact checkpoint]\n\n...' 
  }
]
```

这个方案有一个明显优点：省 token。

但它也有几个硬伤。

### 1.1 最近上下文被一起压没了

Code Agent 很依赖“刚刚发生了什么”。

比如最近一轮可能刚跑完：

```txt
bunx tsc --noEmit
bunx vitest run packages/mica-context/CompactionService.test.ts
```

测试失败信息、用户刚刚强调的偏好、刚读过的文件片段，这些内容如果全靠 summary 复述，风险很高。摘要模型漏掉一行错误、一个文件路径、一个用户约束，后续 agent 就可能沿着错误方向继续跑。

所以 compact 后不能只剩 summary。至少要保留最近几轮原文，让 agent 能无缝接着干活。

### 1.2 重复 compact 可能丢历史

旧实现为了避免重复总结 checkpoint，会过滤已有 checkpoint：

```ts
const messages = input.messages.filter((message) => !isCompactCheckpoint(message));
```

这个思路看起来合理：旧 checkpoint 已经是压缩产物，不要再总结它。

但问题是，后续 compact 的结果只保留新的 checkpoint。如果旧 checkpoint 没有参与新摘要，也没有被保留下来，那么更早的历史就消失了。

长会话里这很危险：

```txt
第一次 compact: A+B+C -> summary_1
继续聊: D+E+F
第二次 compact: D+E+F -> summary_2
最终只剩 summary_2，summary_1 没了
```

正确策略应该是：**旧 summary 要作为新摘要的输入，被 merge 进下一次 summary。**

### 1.3 压缩请求本身也可能超长

还有一个很尴尬的问题：当会话已经很长时，用来生成摘要的请求本身也可能超过模型上下文。

也就是说：

```txt
你需要 compact，因为上下文太长
但 compact 需要读取上下文
读取上下文又太长
```

如果没有兜底策略，用户就会卡在一个死循环里：当前会话太长，正常 query 不行，compact 也不行。

## 二、参考 Claude Code：compact 是一个边界机制

Claude Code 的实现不是单纯“总结全部消息”。它更像一套上下文边界机制。

我参考了几处核心设计：

```txt
temp/claude-code/src/commands/compact/compact.ts
temp/claude-code/src/services/compact/compact.ts
temp/claude-code/src/services/compact/prompt.ts
temp/claude-code/docs/context/compaction.mdx
```

它里面有很多复杂能力，比如 Session Memory Compact、MicroCompact、Reactive Compact、hooks、prompt cache sharing、post compact attachments。mica-code 目前不需要全搬。

但有几个思想非常值得借鉴。

### 2.1 compact boundary

Claude Code 会插入 compact boundary，后续处理只看最后一个 boundary 之后的消息。

这解决了“重复 compact 怎么办”的问题：

```txt
boundary
summary
recent messages
```

下次 compact 时，不是盲目扫全量历史，而是从边界之后开始构造新的 compact 视图。旧 summary 不会被当成垃圾丢掉，而是作为历史摘要继续参与合并。

mica-code 新方案也采用这个结构。

### 2.2 summary + recent messages

Claude Code 的压缩结果不是只有 summary，还会保留一段近期消息。

这比“一条摘要走天下”稳很多：

```txt
summary 覆盖旧历史
recent messages 保留工作现场
```

旧历史负责回答：为什么走到这里？

最近消息负责回答：现在具体在做什么？

Code Agent 需要的不是文学摘要，而是能继续工作的状态快照。

### 2.3 no-tools summary prompt

Claude Code 的 compact prompt 非常强调：不要调用工具，只返回文本。

这是一个很小但很关键的细节。

compact 是在整理已有上下文，不是在继续探索。如果摘要子 agent 又开始读文件、跑命令，就会引入新事实、新成本和新失败点。更糟糕的是，它可能把“摘要任务”变成另一个 agent turn。

所以 mica-code 的 summary prompt 也加了强约束：

```txt
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
```

并且要求输出：

```txt
<analysis>...</analysis>
<summary>...</summary>
```

`analysis` 只帮助模型组织信息，最终会被剥掉；真正进入上下文的是 `summary`。

## 三、新方案：summary 覆盖历史，recent 保留现场

mica-code 现在的 compact 结果变成：

```txt
[
  compact boundary,
  compact summary,
  ...kept recent messages
]
```

也就是：

```ts
const compactMessages = [boundaryMessage, summaryMessage, ...compactedKeptMessages];
```

这三个部分各自有职责。

### 3.1 boundary：告诉系统从哪里重新开始

boundary 是一条特殊 user message，内容以固定前缀开头：

```txt
[Mica compact boundary]
```

它会记录一些元信息：

```ts
{
  beforeCount,
  beforeTokenEstimate,
  summarizedCount,
  keptCount,
  keptTokenEstimate,
  keptCompacted,
  promptTooLongRetries,
  trigger: 'manual',
  createdAt
}
```

这些信息不会让模型变聪明，但对调试很重要。比如用户反馈“compact 后还是很大”，我们可以看到是不是 `kept recent messages` 太重，或者 summary 本身太长。

### 3.2 summary：旧上下文的可继续工作摘要

summary message 以：

```txt
[Mica compact checkpoint]
```

开头，并告诉后续 agent：

```txt
This session is being continued from a previous conversation.
The summary below covers the earlier portion of the conversation.
```

这不是为了给用户看得漂亮，而是为了让模型知道：这条消息不是新需求，而是历史压缩结果。

### 3.3 kept recent messages：保留最近工作现场

新实现不会把最近几轮也压成摘要，而是保留原消息。

默认策略是自动计算保留窗口：

```txt
普通模式：
- 至少保留约 8k tokens
- 至少保留 4 条有文本的消息
- 最多保留约 32k tokens

aggressive 模式：
- 至少保留约 2k tokens
- 至少保留 2 条有文本的消息
- 最多保留约 12k tokens
```

同时也支持手动控制：

```txt
/compact --keep-recent 4
/compact --aggressive
/compact --preview
/compact 聚焦测试输出和刚才修改过的 compact 逻辑
```

`--preview` 只计算压缩效果，不写入 agent snapshot。

## 四、保留最近消息，也不能原样保留所有大输出

第一次跑真实历史测试后，我发现了一个很实际的问题。

只要最近消息里有巨大的工具输出，compact 效果就会明显变差。

一开始 10 个真实 resume session 的压缩结果里，有几条很不理想：

```txt
messages  before   after   saved ratio
344       148836   101902  31.5%
217       111393   93240   16.3%
```

这说明 summary 已经把旧历史压掉了，但 recent messages 里还拖着大块 payload。比如：

- 超长 shell 输出；
- 大段文件内容；
- 图片/base64；
- UI 渲染用的 `toolUseResult`；
- 大 JSON 或重复日志。

所以新方案又加了一层：**recent messages 保留结构，但清理大 payload。**

也就是说，不是把最近消息一起总结掉，而是做轻量 pruning：

```txt
保留：role、消息顺序、工具调用关系、短文本、错误信号、head/tail
清理：超长字符串、base64、image_url、document/image block、toolUseResult
```

核心策略是：

```ts
const compactedKeptMessages = compactKeptMessages(keptMessages, options);
```

对超长字符串，使用已经在项目里验证过的 head/signals/tail 思路：

```txt
--- head ---
前面一段

--- signals ---
error / failed / stack / exit code / file.ts:123 等高信号行

--- tail ---
末尾一段
```

这比简单 `slice(0, n)` 更适合工具输出。因为错误通常不一定在开头，测试总结也经常在结尾。

## 五、prompt too long 的兜底：丢最旧 round 重试

compact 请求本身也会超上下文，所以必须有逃生路径。

新实现里，如果摘要调用报：

```txt
prompt too long
context length
maximum context
input too large
tokens exceed
```

就会触发 retry。

每次 retry 丢掉最旧的一部分 round，并在前面插入标记：

```txt
[earlier conversation truncated for compaction retry]
```

这样做是有损的，但比卡死好。它的定位是最后兜底：当完整历史已经无法送进摘要模型时，至少尽量保住较新的历史，并明确告诉 summary 模型：更早部分已经因 compact retry 被截断。

默认最多重试 3 次，aggressive 模式最多 4 次。

## 六、真实历史测试：不要只测玩具数据

这次测试除了构造的小样本，还专门读取本地 resume 历史做 cloned preview。

要求是：如果本地没有历史，就跳过；如果有历史，至少取 10 个真实 session 测。

测试不会写回真实历史，只会：

```txt
读取 ~/.mica/sessions
选 messages 数量最多的 10 个 session
深拷贝 snapshot.messages
执行 compact preview
检查原始 messages 没有被污染
```

代码对应：

```txt
packages/mica-context/CompactionService.test.ts
```

优化后的 10 个真实 session 压缩效果如下：

## 七、命令层交互：少打扰，但给救急开关

`/compact` 现在默认不弹确认框。

原因很简单：它本来就是用户主动输入的命令，再加确认会变啰嗦。真正需要的是明确反馈和可预览。

现在支持：

```txt
/compact
/compact --preview
/compact --aggressive
/compact --keep-recent 5
/compact 聚焦最近的测试结果和 compact 相关文件
```

成功提示从原来的工程日志：

```txt
Compact: 42 -> 1 messages, tokens 50000 -> 3000
```

改成：

```txt
compact: 42 -> 9 messages, saved ~47k tokens (82%), kept 7
```

如果是 preview：

```txt
compact preview: 42 -> 9 messages, saved ~47k tokens (82%), kept 7
```

如果会话太短，不再显示 `failed`，而是普通提示：

```txt
compact: 当前会话内容较少，暂不需要 compact
```

这类小交互很重要。`not needed` 不是失败，用户不应该看到红色错误语气。

## 八、实现边界：没有照搬 Claude Code 的全部复杂度

Claude Code 的 compaction 系统很强，但也很重。

它有：

- MicroCompact；
- Session Memory Compact；
- Reactive Compact；
- pre/post compact hooks；
- prompt cache sharing；
- compact boundary metadata；
- post compact attachments；
- partial compact；
- context collapse。

mica-code 这次只吸收最核心的部分：

```txt
boundary
summary + recent messages
no-tools prompt
analysis/summary 分离
prompt-too-long retry
recent payload pruning
真实历史测试
```

这是一个有意克制的选择。

如果一开始就把所有高级能力都搬进来，代码会立刻膨胀，而且很多能力没有当前产品场景支撑。比较稳的做法是先把最容易出错的主路径做好：手动 `/compact` 能稳定压、不会丢历史、不会破坏最近上下文、能在真实 resume 历史上跑通。

## 九、这次学到的原则

这次改 compact，最后沉淀下来几个原则。

### 9.1 compact 不是删除历史，而是重建可继续工作的上下文

目标不是 token 越少越好。

如果压到 1k tokens，但 agent 完全不知道下一步该干什么，这不是成功。真正的指标应该是：

```txt
足够省 token
足够保留当前工作现场
足够恢复用户意图和约束
足够支持下一轮直接继续
```

### 9.2 summary 和 recent messages 各有职责

summary 适合保存：

- 用户目标；
- 关键决策；
- 文件路径；
- 已完成工作；
- 失败和修复；
- 下一步。

recent messages 适合保存：

- 最近用户原话；
- 最近工具结果；
- 最新错误输出；
- 刚刚修改的上下文；
- 当前任务的即时状态。

不要强迫其中一方承担全部职责。

### 9.3 重复 compact 必须 merge 历史 summary

只要支持长会话，就一定会发生多次 compact。

第一次 compact 的 summary 不是临时垃圾，而是压缩后的历史本体。第二次 compact 必须把它纳入新摘要，否则历史会一层层蒸发。

### 9.4 真实历史比 mock 更诚实

构造测试能覆盖边界，但真实 session 才能暴露体积问题。

这次如果只测 mock 数据，就不会发现 kept recent messages 里大 payload 拖垮压缩率的问题。真实历史一跑，问题马上出现。

## 十、下一步

现在的 compact 已经能解决手动压缩的主路径，但后续还有几个方向。

第一，做更细的 tool-aware pruning。现在主要是按 JSON 结构和字符串长度清理，未来可以识别具体工具，比如 `run_shell`、`read_file`、`grep_search`，分别定制保留策略。

第二，引入自动 compact。当前 `/compact` 是手动命令，未来可以结合 context usage，在接近阈值时提示或自动执行。

第三，做 partial compact。比如用户在历史里选一个位置，只压缩这个位置之前或之后的消息。Claude Code 已经有类似设计，mica-code 可以后面再接。

第四，把 compact 结果做成更可观察的 UI。现在主要是 message bar 提示，后面可以在 `/context` 面板里展示最近一次 compact 的压缩率、保留消息数量和 retry 次数。

最后，这次最大的感受是：上下文工程不是“把东西塞给模型”，而是持续决定什么该留下、什么该折叠、什么该变成摘要、什么必须保留原文。

对 Code Agent 来说，`/compact` 不是清理聊天记录。它更像一次换背包：把旧工具、旧地图和旧票据整理成一张可靠的路线图，同时把手上正在用的东西留下。

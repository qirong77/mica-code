# 【01】Code Agent 从零到一：ink 渲染管线全景

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

> 作为一个前端开发，你可能觉得"在终端里渲染 React 组件"就是把 JSX 转成字符串然后 `console.log`。直到你发现**终端不是浏览器**——它没有 CSS、没有 DOM、没有 `requestAnimationFrame`、甚至没有"像素"的概念。

mica-code 的终端 UI 基于开源 [ink](https://github.com/vadimdemedes/ink) 库，但我们 fork 了一个自己的版本（`@anthropic/ink`）。本系列文章从前端工程师的视角，逐层解释为什么需要 fork、fork 做了什么。

这是第一篇，聚焦**基础概念和渲染管线**——先搞清楚数据是怎么从 React 状态变成终端屏幕上的字符的。后续两篇分别深入性能优化和交互能力。

本文假设你熟悉 React 的基本概念（组件、JSX、虚拟 DOM、state 更新），但对终端工作原理不熟悉。先讲终端基础，再讲完整渲染流程。

---

## 第零章：终端怎么"显示"东西？

| | 浏览器 | 终端 |
|---|---|---|
| 最小渲染单元 | 像素 | **字符格（cell）** |
| 布局引擎 | CSS Flexbox/Grid | 无（需自己实现） |
| 样式 | CSS 属性 | **ANSI 转义序列** |
| 更新方式 | DOM diff → 浏览器合成 | **逐 cell 写入字节流** |
| 通信 | HTTP/WebSocket | **stdin/stdout 字节流** |

终端的屏幕是一个二维的**字符网格**。比如你的窗口是 80 列 * 24 行，就是一个 80*24 的表格，每个格子叫一个 **cell**。一个 cell 有字符内容和样式（颜色、加粗等）。

**ANSI 转义序列是终端的"CSS"**。浏览器里写 `style={{ color: 'red' }}`，终端里发出 `\x1b[31m`（前景色变红）+ 字符 + `\x1b[0m`（重置）。它是状态切换指令流，不是成对的标签。

## 第零章（续）：如果不用 ink，你会怎么写？

在钻进 ink 的源码之前，先退一步想：如果没有这个库，你打算怎么在终端里做一个动态 UI？

假设你要做一个最简单的 CLI 聊天工具，界面上有三个区域：顶部状态栏（显示当前模型和 token 数）、中间聊天记录（不断追加新消息）、底部输入提示。每次用户输入一条消息，状态栏的 token 数要 +1，聊天区要追加一行，输入提示要移动到新位置。

### 最原始的做法：清屏重写

最简单的思路——每次状态变了，清屏，把所有内容重写一遍：

```typescript
function render(state: AppState) {
  process.stdout.write('\x1b[2J')     // 清屏
  process.stdout.write('\x1b[H')      // 光标回到 (0,0)

  // 状态栏
  process.stdout.write(`\x1b[7m Model: ${state.model} | Tokens: ${state.tokens} \x1b[0m\n`)

  // 聊天记录
  for (const msg of state.messages) {
    process.stdout.write(msg + '\n')
  }

  // 输入提示
  process.stdout.write(`\n> ${state.inputBuffer}_`)
}
```

用户敲一个字符，`state.inputBuffer` 变了，调用 `render`。整屏清空，从头写到尾。

**问题 1：闪。** 清屏 (`\x1b[2J`) 到重写完成之间，屏幕是空的。如果你的终端刷新率恰好卡在这个间隙，用户会看到一瞬白屏。看似微不足道，但用户每敲一个字符就闪一次——一秒钟闪五六次，体验近似于盯着一个坏掉的荧光灯管打字。

**问题 2：浪费。** 用户只改了一个字符，你却把整屏 80×24=1920 个 cell 全部重写了一遍。输入 100 个字符 = 192,000 次写入。其中 191,900 次都在写和上一帧完全相同的内容。

### 稍微好一点：手动做增量更新

只改变了的区域，不清屏：

```typescript
function updateInput(char: string) {
  process.stdout.write(`\x1b[23;3H`)   // 跳到输入行
  process.stdout.write(char)           // 只写这一个字符
}

function updateTokens(count: number) {
  process.stdout.write(`\x1b[1;30H`)   // 跳到状态栏 token 位置
  process.stdout.write(String(count))  // 只改这个数字
}

function appendMessage(msg: string) {
  process.stdout.write(`\x1b[${chatBottom};0H`)  // 跳到聊天区底部
  process.stdout.write(msg.padEnd(cols))          // 写整行覆盖
}
```

不闪了，也不浪费了。但这才刚刚开始。

### 当复杂度开始增长

上面的代码只能处理"单行追加"和"固定位置覆盖"。但真实场景很快就超出这个范围：

**场景 A：消息太长折行了。** 一条消息占了两行，聊天区下面所有内容都要往下挪一行。推着输入提示往下走，如果输入提示已经贴着屏幕底部——还需要把聊天区整体向上滚动一行。

```typescript
function appendLongMessage(msg: string) {
  const lines = wrap(msg, cols)  // 自己写一个折行算法
  // 需要滚动了？
  if (chatBottom + lines.length > terminalRows) {
    // 手动实现滚动：把聊天区内容整体上移，最上面一行丢弃
    // 这需要你维护一份"当前屏幕状态"来知道每行写了什么
  }
  // 逐行写入，手动算坐标
}
```

开始维护"当前屏幕状态"的那一刻，你就已经在徒手实现半个 Screen Buffer 了。

**场景 B：用户切换模型选择框。** 按 Tab 展开下拉菜单。你需要在状态栏下方临时画一个浮层，盖住聊天区的前几行。用户选完按 Enter，浮层消失，被盖住的内容要恢复。

```typescript
function openDropdown(items: string[]) {
  // 先"记住"被盖住的那几行
  savedLines = readFromScreen(2, 0, 2 + items.length, cols)
  // 画浮层
  for (let i = 0; i < items.length; i++) {
    process.stdout.write(`\x1b[${2 + i};0H`)
    process.stdout.write(items[i].padEnd(cols))
  }
}

function closeDropdown() {
  // 恢复被盖住的内容
  for (let i = 0; i < savedLines.length; i++) {
    process.stdout.write(`\x1b[${2 + i};0H`)
    process.stdout.write(savedLines[i])
  }
}
```

但这意味着你需要一个"屏幕读取"能力——而终端没有这个 API。你读不到屏幕上当前显示了什么，只能靠自己记。于是你开始在内存里维护整个屏幕的状态数组。

**场景 C：窗口 resize 了。** 终端从 80×24 变成 120×30。状态栏要拉宽，聊天区要重新折行，所有固定坐标全部失效。你需要拦截 resize 事件，重新计算所有元素的布局，然后整屏重写。这一次，你手动维护的坐标表全部作废。

### 四个根本性的缺失

走到这里，你会发现你根本不是在做"终端 UI"，你是在从零实现一个终端渲染引擎。问题是——

| 你缺什么 | 为什么缺了就会崩溃 |
|---|---|
| **布局引擎**：无法声明"状态栏在上面、聊天区占 flex: 1" | 手动算坐标 → resize 时全部重算 → 容易出错 |
| **状态追踪**：不知道屏幕上的 cell 和上一次比变了什么 | 要么全量重写（闪），要么手动维护屏幕快照（心智负担） |
| **双缓冲**：没有一个"画完再换"的机制 | 边写边显示 → 用户看到中间态（撕裂） |
| **组件化**：UI 结构不清晰，状态和渲染逻辑耦合 | 一个字段改动需要改散落在各处的坐标计算代码 |

### ink 把这些手工活变成了声明式组件

用一种对比的方式来感受 ink 的价值。同样的 CLI 聊天工具界面，不用 ink 和用 ink：

**不用 ink：**

```typescript
// 三个区域，每次更新都要手动管理坐标、状态、屏幕快照
let screenState: Cell[][]          // 当前屏幕内容快照
let savedRegion: string[] | null   // 被浮层盖住的内容

function render(state: AppState) {
  // 100+ 行坐标计算、区域保存/恢复、滚动逻辑、折行算法...
}
```

**用 ink：**

```tsx
<Box flexDirection="column" height="100%">
  <StatusBar model={model} tokens={tokens} />
  <ChatMessages messages={messages} flexGrow={1} />
  <InputPrompt buffer={input} />
</Box>
```

你只管"想要什么布局"，ink 负责"放在哪个坐标"。这之间的翻译过程，就是 ink 的渲染管线——第一章要讲的内容。

ink 面对这四个根本缺失，建立了四条对应的机制：

| 原生缺失 | ink 的方案 | 对应第一章的哪个环节 |
|---|---|---|
| 没有布局引擎 | **Yoga Flexbox** 算每个元素的 x、y、w、h | 1.2 布局计算 |
| 没有状态追踪 | **Screen Buffer** 维护当前屏幕状态 + diff 找差异 | 1.3 绘制 + 1.5 diff |
| 没有双缓冲 | **双帧 buffer**（frontFrame / backFrame）+ swap | 1.4 双缓冲 |
| 没有组件化 | **React reconciler** 把 JSX 翻译成虚拟树操作 | 1.1 React 通知 ink |

这也解释了为什么 ink 选择了 React——它不只是要一个"把 JSX 变成字符串"的工具，它需要一个完整的 reconciliation 管线来驱动布局→绘制→diff→输出的流水线。React 的虚拟 DOM 和 host config 扩展点恰好提供了这个能力。

## 第一章：从 setState 到屏幕上的字符

在你深入后面的优化章节之前，先把整个流程串起来：当你调用 `setState({ text: 'hello' })` 之后，终端怎么知道要在哪个位置显示什么文字？

### 1.1 React 算完谁变了，通知 ink

`setState` 触发后，React 的核心引擎（reconciler）开始计算哪些组件需要更新。这个 reconciler 和浏览器里的 React DOM 用的是同一个 `react-reconciler` 包，但它不操作真实的 DOM，而是调用 ink 提供的一套"翻译函数"：

```typescript
// 浏览器里：document.createElement('div')
// ink 里：createInstance('ink-box', props, root, hostContext)

// 浏览器里：parent.appendChild(child)
// ink 里：appendChild(parentNode, childNode)

// 浏览器里：element.setAttribute('title', 'hello')
// ink 里：commitUpdate(node, oldProps, newProps)
```

这套函数叫做 host config。它把 React 的"增删改查"操作翻译成对一棵虚拟终端树的操作。这棵树由 `DOMElement` 节点组成——你可以把它理解成浏览器 DOM 的终端版本，每个节点附带布局信息。

### 1.2 算出每个组件放在哪、占多大

React 更新完虚拟树后，`resetAfterCommit` 钩子触发布局计算。ink 用 Yoga（Facebook 的 Flexbox 引擎）来算位置和尺寸：

```typescript
rootNode.yogaNode.setWidth(terminalColumns)     // 告诉 Yoga 终端有多宽
rootNode.yogaNode.calculateLayout(terminalColumns) // 开算
```

Yoga 会遍历整棵节点树，根据 Flexbox 规则（`flexDirection`、`flexGrow`、`alignItems` 等）算出每个节点的 `left`、`top`、`width`、`height`。

**Fork 的 Yoga 和开源有什么不同？**

开源 ink 用 Facebook 的 Yoga，但它是以 WASM 二进制文件的形式加载的。Fork 删掉了这个依赖，用了一个纯 TypeScript 实现（`yoga-layout/index.ts`，约 2500 行）。

为什么要自己写？

- **启动更快**：省去 WASM 加载时间，实测约 8-15ms
- **只保留需要的功能**：Fork 的 Yoga 只实现了 ink 真正用到的 Flexbox 子集，删掉了 `aspect-ratio`、`box-sizing: content-box`、RTL（从右到左的文字排版）等用不上的特性
- **加了多层缓存**：引入了单槽缓存 `_hasL`、多槽缓存 `_cIn/_cOut`、flex-basis 缓存 `_fbBasis`。遇到脏节点时，大量干净的子树可以跳过。实测效果：500 条消息的 ScrollBox 里只有一个叶子节点变了，重新布局的调用次数从 76000 次降到了 4000 次

### 1.3 把组件"画"到 Screen Buffer 上

布局算完了，该"画"了。`onRender` 被触发，遍历整棵虚拟终端树，把每个节点的文字、样式、位置转化成对 Screen Buffer 的写入操作：

```
renderNodeToOutput(rootNode, output, { prevScreen })
  → 遇到 Text 组件：算它能铺满几个 cell，把字符和样式写进对应 cell
  → 遇到 Box 组件：如果没变，直接 blit（从缓存拷贝一块连续内存）
                   如果变了或删了，擦除旧区域，写入新内容
  → 所有操作收集到 Output 队列里
  → output.get() 把队列里的所有操作合起来，一次性应用到 Screen Buffer
```

**Screen Buffer 就是渲染的"画布"**。它是一个二维数组，每个元素代表一个 cell 的最终状态——包含显示什么字符、什么颜色、是否粗体等。后面的 diff（对比新旧两帧）、文本选择、搜索高亮，都是在这块 buffer 上操作的。

但这里有个问题：你不能直接在用户正在看的那个画布上改。一边擦一边画，用户会看到中间状态——闪。

### 1.4 双缓冲：一块画、一块看

> 从本节到 1.6，讲的是**开源 ink 已有的渲染机制**——双缓冲、逐 cell diff、ANSI 序列化。fork 完全沿用了这套管线，没有改动。把这些搞清楚之后，后续文章才会深入到 fork 独有的性能优化。

你往屏幕上画东西的过程不是瞬间完成的。如果在用户正看着的那块画布上直接擦掉旧内容、写上新内容，用户会看到中间状态——比如先看到一半新 UI 和一半旧 UI 混在一起，然后下一帧才变全。这就是"闪烁"的来源。

ink 的解决方案和所有图形系统一样：**准备两块画布**。

```typescript
// 在 Output 类里维护两块完整的 screen buffer
this.backFrame  // 后台 buffer：渲染时往这块画，用户看不见
this.frontFrame // 前台 buffer：当前显示在屏幕上的那一帧
```

可以把这两块 buffer 想象成**两张白板**。讲台上永远只挂着一张（`frontFrame`），学生在任何时候看到的都是这一张完整的内容。老师在下面（`backFrame`）悄悄地写好新内容，写完了把两张白板一换。学生只看到了"旧内容→新内容"的一次性切换，看不到擦和写的过程。

具体到每轮渲染，流程是这样的：

```
┌─ 第 N 帧结束状态 ──────────────────────────────────────┐
│  frontFrame: 屏幕上显示着 [hello world]                  │
│  backFrame:  （上一轮的 frontFrame，内容已无用）          │
└─────────────────────────────────────────────────────────┘

1. resetScreen() 清空 backFrame.screen
   → backFrame 从残留数据变成一张全空白的 cell 矩阵

2. renderNodeToOutput(rootNode, backFrame.output, { prevScreen })
   → React 虚拟树遍历，把每个组件的文字、样式、位置作为"写入指令"
   → 累积在 backFrame.output 队列里
   → output.get() 一次性提交到 backFrame.screen[y][x] 的 cell 数组（1.3 节）
   → 同时记录哪些 (x, y) 区域被碰过（damage rectangle，见 1.5）
   → backFrame: [hello world v2] ✓

3. diff(backFrame.screen, frontFrame.screen)
   → 逐个检查 damage rectangle 覆盖的 cell
   → 找出哪些 cell 的字符/样式跟上一帧不一样（1.5 节）

4. 把差异转换成 ANSI 转义序列，write 到终端 stdout（1.6 节）
   → 终端收到后更新对应 cell

5. swap: frontFrame = backFrame（引用交换，零拷贝）
   → 现在 frontFrame 是 [hello world v2]，backFrame 变成旧的那块

┌─ 第 N+1 帧结束状态 ─────────────────────────────────────┐
│  frontFrame: 屏幕上显示着 [hello world v2]               │
│  backFrame:  [hello world]（下轮将被 resetScreen 清空）   │
└─────────────────────────────────────────────────────────┘
```

**关键点**：步骤 2 耗时最长（遍历 React 树 + Yoga 布局 + 写入 cell），但用户在步骤 2 全程看到的还是 `frontFrame` 上的旧内容。直到步骤 4 终端收到 ANSI 指令后才更新屏幕。所以渲染延迟不会造成闪烁，只会让"下一帧"来得晚一点。

游戏引擎的 swap chain、浏览器的 compositor 层用的都是同一个原理。只不过它们的"画布"是像素缓冲区，ink 的"画布"是字符 cell 矩阵。

### 1.5 diff：只更新真正变了的 cell

现在 `backFrame` 上有一帧全新的画面，`frontFrame` 上是上一帧的画面。要把差异告诉终端，让它更新屏幕。

最笨的办法是把 `backFrame` 全量打印一遍——但终端只有几千个 cell 变了，打印全部 80×24=1920 个 cell 浪费带宽，而且全量清屏重写会产生闪烁。

更高效的做法：**逐 cell 对比，只把变了的那些 cell 变成终端指令**。

```typescript
// 遍历当前帧中"被写入过"的区域（damage rectangle）
for (const [x, y] of backFrame.damagedCells()) {
  const old = frontFrame.screen[y][x]  // 旧 cell
  const cur = backFrame.screen[y][x]   // 新 cell
  if (old !== cur) {
    patches.push({
      type: 'cell',
      x, y,
      char: cur.char,
      style: cur.style,
    })
  }
}
```

**damage rectangle（脏矩形）是什么？**

步骤 1.3 的 `renderNodeToOutput` 在往 `backFrame` 写入时，不是盲目地遍历所有 cell。它在写的过程中同步记录"哪些坐标被碰过了"——这就是 damage rectangle。

```typescript
// output.ts 中的逻辑
output.cursorTo(x, y)    // 移动写入光标的同时
  → this.backFrame.damage(x, y)  // 标记该坐标为脏

output.write('hello')    // 连续写 5 个字符
  → 标记 5 个连续坐标为脏
```

可以把它想象成一张"便签纸"：你在画布上画画时，顺手在另一张小纸上圈出你改过的地方。diff 阶段不用拿着放大镜看整张画布，只要看便签纸上圈起来的那几个区域。

**为什么这是性能关键？**

假设终端窗口是 80 列 × 30 行 = 2400 个 cell。用户输入了一个 `/model haiku` 命令，只让聊天框里多了一行新文本——大约 20 个 cell 变了。

- 如果全量对比：遍历 2400 个 cell → 2400 次比较
- 如果只检 dirty area：damage rectangle 标记了 20 个 cell → 20 次比较

差值就是 120 倍。帧率 60fps 时，这个差距被放大到每秒 142,800 次 vs 1,200 次的比较操作。

**Patch 是什么？**

diff 的结果是一个 `Patch[]` 数组。每个 Patch 不是"更新这个 cell 为 X"的简单指令——它是终端指令的抽象表示：

```typescript
// 可能产生的几种 Patch 类型
{ type: 'cursor-move', x: 5, y: 10 }          // 把光标移到 (5, 10)
{ type: 'cell', char: 'h', style: { bold } }    // 在当前光标位置写一个 'h'
{ type: 'style', sgr: '\x1b[31m' }             // 切换前景色为红色
{ type: 'erase', width: 10 }                    // 从光标位置清 10 个 cell
```

这些 Patch 随后送入 1.6 的序列化阶段，被翻译成真正的 ANSI 逃逸序列。

### 1.6 把 Patch 序列化成 ANSI 字节流

`Patch[]` 数组还不能直接送进终端。因为终端接收的是**字节流**——一串连续的字符和 ANSI 转义序列。所以需要把 Patch 翻译成这一串字节。

#### 第一步：合并优化 Patch

连续的 Patch 可能产生冗余。比如写入 "hello" 时，5 个字符在同一行连续排列，如果每个字符都带一个"移动光标到 (x, y)"指令，就产生了 4 次多余的光标移动。序列化前先做一轮合并：

```
合并前:  cursor(5,10) → cell('h') → cursor(6,10) → cell('e') → cursor(7,10) → ...
合并后:  cursor(5,10) → cell('h') → cell('e') → cell('l') → cell('l') → cell('o')
```

光标只在起点移动一次，后续字符自然顺序写出。这减少了终端的指令处理量和传输字节数。

#### 第二步：翻译成 ANSI 转义序列

每个优化后的 Patch 被翻译成一段字节：

```typescript
// 具体转换示例
{ type: 'cursor-move', x: 5, y: 10 }
  → `\x1b[10;5H`      // CSI {row};{col}H  —— 光标定位（注意：ANSI 的行号从 1 开始）

{ type: 'style', sgr: '\x1b[31m' }
  → `\x1b[31m`        // CSI 31m —— SGR 设置前景色为红色

{ type: 'cell', char: 'h' }
  → `h`               // 直接拼 ASCII 字符本身，没有转义序列

{ type: 'erase', width: 10 }
  → `          `       // 10 个空格（用空格覆盖旧字符）
```

光标指令是状态式的——终端有一个内部"光标位置"，你发出 `\x1b[10;5H` 后，光标跳到 (5,10)，后续所有写入操作都从那个位置继续。所以 Patch 合并能消除连续写入时的多余光标移动。

#### 第三步：BSU/ESU 包裹——消除撕裂感

最后，整个更新序列被包裹在一对特殊的 ANSI 序列中：

```typescript
let buffer = BSU  // \x1b[?2026h  —— Begin Synchronized Update

for (const patch of optimizedPatches) {
  buffer += serializePatch(patch)
}

buffer += ESU      // \x1b[?2026l  —— End Synchronized Update
terminal.stdout.write(buffer)
```

**Synchronized Output（同步输出）**是 DEC 定义的终端协议扩展（`DECSET 2026`）。正常模式下，终端收到字节就立即绘制，导致多行更新出现撕裂感——终端在画第 2 行时，用户已经看到了第 1 行的新内容，而第 3 行还是旧的。BSU/ESU 告诉终端："下面这一批操作是一个逻辑帧，先缓存起来别急着显示，等我发 ESU 后再一次性把整帧画出来。"

这是一个可选特性——原生 Windows Console 不支持，iTerm2 和 Windows Terminal 支持。ink 在初始化时通过探测 `\x1b[?2026$p` 的响应来检测终端是否支持，不支持就跳过 BSU/ESU 包裹。

#### 完整示例

假设用户输入后，聊天框只新增了一行 "[user] hello"。整帧的最终输出指令可能长这样：

```
\x1b[?2026h            ← BSU，开始同步更新
\x1b[15;5H             ← 光标跳到第 15 行第 5 列
[user]                 ← 新文本
\x1b[16;3H             ← 光标跳到第 16 行第 3 列
hello                  ← 新文本
\x1b[?2026l            ← ESU，结束同步更新，终端一次性刷新
```

用户看到的效果：旧内容保持不变，两行新文本瞬间同时出现，没有闪烁，没有撕裂。

# 【08】Code Agent 从零到一：记忆系统的设计与实现

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

对话式 AI 做代码助手最大的尴尬是什么？不是你写错了，是你忘了。

昨天你花了三小时跟 agent 确定了一个重构方案，详细到每个文件的改动顺序。今天打开新对话，agent 礼貌地问你："需要我帮你做什么？"——它不记得你是谁，不记得你们昨天讨论的决策，甚至不记得你反复强调"这个项目的测试不要 mock 数据库"。

这就是没有记忆系统的 agent。每一轮对话都是全新的，像一个间歇性失忆的同事。

本文记录 mica-code 记忆系统的完整设计——从分析 claude-code-main 的架构到落地自己的实现，包括存储模型、召回策略、提取机制、以及一个关键的 forked agent 设计。

## 第一章：claude-code-main 的记忆系统架构

在动手设计之前，先搞清楚参考实现是怎么做的。claude-code-main 的记忆系统是一个**多层级、文件驱动、AI 辅助维护**的架构——没有数据库，没有向量存储，纯 Markdown 文件。

### 1.1 存储布局

所有记忆落在 `~/.claude/projects/<sanitized-git-root>/memory/` 下。同一个 Git 仓库的不同 worktree 共享一个记忆目录——通过 `findCanonicalGitRoot()` 找到真正的 `.git` 根。

核心入口是 `MEMORY.md` 索引文件。每次对话都完整加载，但有双重上限：200 行 AND 25KB。任意一条超标就截断并追加警告。

### 1.2 四类型分类法

记忆被约束为一个封闭的四类型系统。关键是**只存储无法从当前项目状态推导的信息**——代码架构、文件路径、git 历史都可以实时获取，不需要记忆。

| 类型 | 存储内容 | scope |
|------|---------|-------|
| user | 用户角色、偏好、技术背景 | 始终 private |
| feedback | 用户对 AI 行为的纠正和确认——从失败 AND 成功中记录 | 默认 private |
| project | 非代码可推导的项目上下文（截止日期、事故、决策） | 偏向 team |
| reference | 外部系统指针（Linear 项目、Slack 频道） | 通常 team |

feedback 类型的设计特别精妙——"Record from failure AND success"。如果只记教训不记肯定，AI 的行为会逐渐变得保守，越来越不敢做用户之前认可过的事情。

每条记忆使用 frontmatter 格式，`description` 字段不是给人读的摘要，而是给召回系统做相关性判断的搜索关键词。

### 1.3 智能召回：Sonnet 侧查询

当项目有几十上百个记忆文件时，全量注入上下文是浪费 token。做法：扫描所有 frontmatter → 格式化为清单 → 独立 API 调用给 Sonnet（max_tokens: 256，JSON Schema 输出）→ 选 ≤5 条 → 只注入这 5 条的全文。

"侧查询"指它在主 agent 对话流之外独立运行，用小模型 + 极短 token 做选择题。还有两个去噪机制：近期工具去噪（当前使用的工具的参考文档不召回）、已展示去重。

### 1.4 记忆提取：Forked Agent 后台运行

记忆提取不是主 agent 的职责，而是一个独立的后台 forked agent。每一轮对话结束后触发，但有精妙的控制：光标追踪（避免重复提取）、互斥排除（主 agent 写了就跳过）、节流、尾随运行、硬上限（maxTurns: 5）。

关键设计：forked agent 传入与主 agent 完全相同的 system prompt 和 tools 定义。Anthropic 的 prompt caching 按前缀匹配，相同的 system prompt → 第一个 token 就能命中 cache。

权限沙箱：只允许 Read/Grep/Glob + 只读 Bash + 记忆目录下的 Edit/Write。

### 1.5 Session Memory 与 Compact 联动

第二层记忆——Session Memory。与 auto memory（跨对话持久化）不同，它存储在 `~/.claude/session-memory/<session-id>.md`，由 forked agent 每 N 次 tool call 自动更新。

核心价值在 compact：当对话太长需要压缩时，传统做法是调摘要 API。但 session memory 已经是实时维护的摘要，直接用它替代 API 调用——更快、更便宜。

### 1.6 记忆漂移防御

两组专门的 prompt 指令：TRUSTING_RECALL_SECTION（"Before recommending from memory"——行动导向的标题措辞经过 A/B 测试 3/3 vs 0/3）、忽略语义（"就当 MEMORY.md 是空的"）、新鲜度标注（超过 1 天的记忆注入 `<system-reminder>` 警告）。

## 第二章：mica-code 需要什么样的记忆系统

claude-code-main 的记忆系统功能完整但体量庞大——包含了 GrowthBook 远程 feature gate、team memory、KAIROS 日志模式、agent memory 等多个子系统。mica-code 是轻量级的，不能也不需要全部照搬。

### 2.1 取舍决策

| 保留 | 舍弃（暂不） | 理由 |
|------|-------------|------|
| 文件存储 + 四类型分类 | — | 已充分验证，直接复用 |
| MEMORY.md 索引 + 双上限截断 | — | 索引形态是最小可行的召回入口 |
| 记忆漂移防御 prompt | — | prompt 文本直接复用，成本为零 |
| Forked agent 提取 | SubAgent（已有） | SubAgent 不支持 prompt cache 共享，需要用 streaming API + 同 system prompt 实现真正的 forked agent |
| Session memory + compact 联动 | — | 核心价值在减少 compact 的 API 调用 |
| Sonnet 侧查询召回 | 记忆数 <20 时全量注入即可 | 侧查询需要额外 API 调用，记忆少时不划算 |
| — | GrowthBook feature gate | mica-code 不需要远程开关 |
| — | Team memory | 单用户场景不需要 |
| — | KAIROS 日志模式 | 无长期运行 assistant |

### 2.2 核心架构

```
~/.mica/
├── memory/
│   └── <project-hash>/
│       ├── MEMORY.md           ← agent 维护的入口索引
│       ├── user_*.md
│       ├── feedback_*.md
│       ├── project_*.md
│       └── reference_*.md
└── session-memory/
    └── <session-id>.md         ← forked agent 维护的会话摘要
```

项目隔离使用 sha256 哈希前 16 位：`createHash('sha256').update(gitRoot).digest('hex').slice(0, 16)`。

### 2.3 System Prompt 注入

记忆系统通过 `MemoryPlugin` 注入到 system prompt 中。利用已有的 `SystemPromptBuilder` 机制，追加 `<memory>` section：

```
<system>
你是 Mica Code...
</system>

<context>
环境信息...
</context>

<memory>
# Memory system
你有一个持久的、基于文件的记忆系统...
... 类型规范 + 保存方法 + 访问规则 + 漂移防御 ...
</memory>

<project-instructions>
AGENTS.md 内容...
</project-instructions>
```

MEMORY.md 索引作为 system prompt 的一部分，模型在每次对话开始时都能看到所有已知记忆的索引。200 行 / 25KB 的双上限确保不会占据过多上下文。

## 第三章：Forked Agent——为什么要自己造轮子

mica-code 已经有了 `createSubAgent()` 用于 compact 摘要，为什么还要实现 `createForkedAgent()`？

### 3.1 SubAgent 的局限

SubAgent 实现比较直接：

```typescript
export function createSubAgent(options: SubAgentOptions) {
  return async function run(
    userMessages: Anthropic.MessageParam[],
  ): Promise<SubAgentResult> {
    const client = getClient();
    const messages: Anthropic.MessageParam[] = [...userMessages];

    while (true) {
      const response = await client.messages.create({  // non-streaming
        model: modelName,
        system: systemPrompt,    // 自定义 prompt，与主 agent 不同
        messages,
        tools: tools.length > 0 ? tools : undefined,
      });
      // ... handle tool calls
    }
  };
}
```

三个问题：

1. **不共享 prompt cache**。SubAgent 使用自定义 `systemPrompt`（如"你是一个擅长总结技术对话的助手"），与主 agent 的完整 system prompt 不同。Anthropic 的 prompt caching 是按 prefix 匹配的，prefix 不同 = 0% cache hit。

2. **使用 `client.messages.create()`**（非流式），而非 `client.messages.stream()`。非流式调用不返回 cache 统计信息，无法衡量 cache 效果。

3. **工具集可定制但无白名单过滤**。传入的 `tools` 是定义列表，SubAgent 自身没有在执行层做二次校验——如果传入完整工具列表，SubAgent 可以做任何事。

### 3.2 ForkedAgent 的设计

```
createForkedAgent({
  promptMessages,     // 给子 agent 的指令
  systemPrompt,       // 与主 agent 完全相同 → cache hit
  allowedTools,       // 白名单：null = 全部, 数组 = 仅这些
  maxTurns: 5,        // 硬上限
  thinkingDisabled,   // 关闭 thinking 减少 token
})
```

核心差异：

**1. 共享 system prompt**

```typescript
// MemoryPlugin 中：
const systemPrompt = getSystemPrompt();  // 主 agent 的完整 system prompt
await createForkedAgent({
  systemPrompt,        // ← 完全相同，第一个 token 即可命中 cache
  promptMessages: [{ role: 'user', content: extractPrompt }],
  allowedTools: ['read_file', 'write_file', 'edit_file', 'list_files', 'grep_search'],
});
```

**2. 工具白名单过滤**

```typescript
const allTools = getToolDefinitions();
const tools = allowedTools
  ? allTools.filter(t => allowedTools.includes(t.name))
  : allTools;
```

在工具定义层面就做了过滤——模型看到的工具列表只包含白名单内的。这意味着模型不会请求被禁止的工具（如 run_shell），从根本上避免了权限泄露。

**3. 返回详细统计**

```typescript
interface ForkedAgentResult {
  messages: Anthropic.MessageParam[];
  text: string;
  totalUsage: {
    input_tokens: number;
    output_tokens: number;
    cache_read_input_tokens: number;     // ← cache 命中统计
    cache_creation_input_tokens: number;
  };
  turnCount: number;
}
```

### 3.3 与 SubAgent 的关系

两者分工明确：

| 场景 | 使用 | 原因 |
|------|------|------|
| 记忆提取 | ForkedAgent | 需共享 cache，5 轮上限 |
| 会话记忆更新 | ForkedAgent | 同上 |
| Compact 摘要 | SubAgent（现有） | 自定义短 prompt，独立调用 |
| /init 初始化 | SubAgent（现有） | 独立任务，不共享 cache |

## 第四章：MemoryPlugin——三个 post-turn hook 的协作

MemoryPlugin 是记忆系统的主控插件。它注册了三个在每轮对话后触发的逻辑：

```
AgentTurn.coreRun()
  while (true) {
    result = await executeSingleIteration()
    onIteration?.(result)
    this._notifyIterationComplete()     ← 新增钩子
      → MemoryPlugin.onTurnComplete()
        → tryExtractMemories()           ← hook 1
        → tryExtractSessionMemory()      ← hook 2
  }
  // 中途还有：
  AutoCompactPlugin (middleware)
    → trySessionMemoryCompact()          ← hook 3，compact 时触发
```

### 4.1 Hook 1：记忆提取 (Auto Memory)

触发条件：新消息 ≥ 10 条 **或** token 增长 ≥ 5000。

```typescript
private async tryExtractMemories(messages: ConversationMessage[]): Promise<void> {
  const currentTokens = getContextUsage(messages);
  const tokensSince = currentTokens - this.tokensAtLastExtraction;

  if (newCount < 10 && tokensSince < 5000) return;

  // 更新游标，然后跑 forked agent
  this.lastExtractionMessageIdx = messages.length;
  this.tokensAtLastExtraction = currentTokens;

  const memoryDir = getMemoryDir();
  const memoryCount = scanMemoryFiles(memoryDir).length;

  // 记忆数 > 20：附带清单让 forked agent 筛选更新 ≤5 条
  let recallContext = '';
  if (memoryCount > 20) {
    const manifest = formatMemoryManifest(scanMemoryFiles(memoryDir));
    recallContext = `当前记忆文件清单（${memoryCount} 个），选择最相关的 ≤5 条更新或创建新的`;
  }

  await createForkedAgent({
    promptMessages: [{
      role: 'user',
      content: `查看对话历史，提取应持久化的记忆。${recallContext}
将记忆写入 ${memoryDir}，遵循 system prompt 中 "Memory system" 部分的规范。
MEMORY.md 索引保持在 200 行以内。如果没有值得保留的记忆，不做任何操作。`,
    }],
    systemPrompt: getSystemPrompt(),
    allowedTools: ['read_file', 'write_file', 'edit_file', 'list_files', 'grep_search'],
    maxTurns: 5,
    thinkingDisabled: true,
  });
}
```

关键点：
- fork agent 拥有 `write_file` 和 `edit_file` 权限，可以写入记忆目录
- 通过 `maxTurns: 5` 限制消耗，防止验证循环
- 记忆数少时全量列出，记忆数多时让 fork agent 自己做筛选（相当于轻量版的"侧查询"）

### 4.2 Hook 2：会话记忆更新 (Session Memory)

触发条件：工具调用 ≥ 10 次 **且** token 增长 ≥ 10000。

```typescript
private async tryExtractSessionMemory(messages: ConversationMessage[]): Promise<void> {
  this.sessionMemoryToolCallCount++;

  if (this.sessionMemoryToolCallCount < 10 && tokensSince < 10000) return;

  this.sessionMemoryToolCallCount = 0;

  const memoryPath = getSessionMemoryPath(sessionId);
  const currentContent = readSessionMemory(sessionId) ?? '';

  await createForkedAgent({
    promptMessages: [{
      role: 'user',
      content: `更新会话记忆文件 ${memoryPath}。
当前内容：${currentContent || '(空)'}
汇总：用户请求、决策、文件修改、错误修复、待完成任务。`,
    }],
    systemPrompt: getSystemPrompt(),
    allowedTools: ['read_file', 'write_file', 'edit_file', 'list_files', 'grep_search'],
    maxTurns: 3,
    thinkingDisabled: true,
  });
}
```

Session memory 格式灵活，不需要四类型分类——它就是当前对话的滚动摘要。

### 4.3 Hook 3：Compact 集成

这是对现有 `AutoCompactPlugin` 的改造。原本 compact 触发时调用 SubAgent 做模型摘要，现在优先使用 session memory：

```typescript
// utils/compact.ts 新增函数
export async function trySessionMemoryCompact(
  sessionId: string,
  messages: ConversationMessage[],
): Promise<ConversationMessage[] | null> {
  const sessionMemory = readSessionMemory(sessionId);
  if (!sessionMemory || !sessionMemory.trim()) return null;  // fallback to model summary

  const toKeep = messages.slice(-KEEP_RECENT_COUNT);
  const summaryMessage = `以下是之前对话的会话记忆摘要：${sessionMemory}`;
  return [{ role: 'user', content: summaryMessage }, ...toKeep];
}
```

如果 session memory 文件存在且有内容，直接用它的内容作为摘要——零 API 调用。如果不存在或为空，fallback 到原有的模型摘要。

## 第六章：关键设计权衡

### 6.1 为什么不用向量数据库

向量数据库在做语义搜索上确实更灵活，但对于 code agent 的记忆系统来说，引入它的代价远大于收益：

- **依赖**：需要额外的服务或嵌入式库（如 sqlite-vec、chroma）
- **一致性**：文件可以被 git 追踪、diff、备份——向量存储做不到
- **简单性**：200 行 MEMORY.md 索引 + agent 自己 grep 搜索已经覆盖了大多数查询场景

claude-code-main 的做法就是纯文件——这个设计决策经过了生产验证，直接复用。

### 6.2 为什么 post-turn 而非 pre-turn

记忆提取在每轮对话**后**而非**前**触发。为什么？

- pre-turn 提取会阻塞用户等待响应
- post-turn 用 fire-and-forget 模式，提取失败不影响主流程
- forked agent 是异步的，与下一轮对话可以并行运行

但这也意味着提取有**最多一轮的延迟**。如果用户连续快速发消息，上一轮的提取可能还没完成。MemoryPlugin 用 `extracting` 标记防止重叠运行，未来可以扩展为 stash-queue 模式（claude-code-main 的做法）。

### 6.3 为什么记忆数 ≤20 时不做侧查询

claude-code-main 的 Sonnet 侧查询是针对大量记忆文件的优化。当记忆数少时，MEMORY.md 索引本身只有几十行，全量注入的 token 成本远低于一次额外的 API 调用。

20 是一个经验阈值——200 行上限 ÷ 10 行每记忆 ≈ 20 条记忆。超过这个数时索引开始接近上限，此时交给 forked agent 做筛选更合理。

### 6.4 为什么 Session Memory 不需要四类型

Auto memory 的四类型分类是为跨对话检索服务的——类型标签帮助未来对话的召回系统判断相关性。

Session memory 只在当前对话内使用，而且用途单一（compact 时的摘要）。分类会增加 forked agent 的认知负担和 token 消耗，换来的检索便利在本对话内用不上。

### 6.5 Forked agent vs 直接在对话中写

为什么不让主 agent 在对话过程中直接写记忆文件？它已经有 write_file / edit_file 权限。

原因是**注意力分离**。当 agent 在执行一个复杂的实现任务时，让它同时判断"这段对话里有什么值得记住的"会分散注意力，降低任务质量。Forked agent 独立运行，专注于提取记忆，不受当前任务上下文干扰。

而且 forked agent 的 system prompt 包含完整的记忆系统指令——它清楚四类型分类、MEMORY.md 索引格式、什么不该存。主 agent 的注意力应该放在用户的任务上。

## 第七章：还没做的事

### 7.1 真正的侧查询召回

当前实现是：记忆数 >20 时附带清单，让 forked agent 在提取 prompt 里自己选。但理想的召回应该是一个独立的、极轻量的 API 调用——类似于 claude-code-main 的 Sonnet 侧查询：

```
用户查询 → scanMemoryFiles() → formatMemoryManifest()
→ sideQuery(Sonnet, max_tokens=256, output=JSON) 
→ 返回 ≤5 条最相关路径
→ 读全文 → 注入为 attachment
```

这需要 `sideQuery()` 基础设施——与主 agent 共享客户端但独立调用。可以在下一轮迭代中实现。

### 7.2 推荐记忆提升

当前 MEMORY.md 索引总是在 system prompt 中。对于那些 agent 多次访问但不在索引中的记忆，可以增加一个"高频记忆"推荐列表——类似于 claude-code-main 的 `findRelevantMemories` 在 query 层的 prefetch。

### 7.3 跨项目记忆共享

如果用户在多个项目中有共享的偏好（如"不要用 ORM"、"首选 Bun 而非 Node"），这些 user 类型的记忆应该在所有项目中可用。当前实现是每个项目独立的记忆目录，全局共享层还没有。

### 7.4 `/dream` 记忆固化

claude-code-main 的 KAIROS 模式有一个夜间 `/dream` 任务，将每日日志蒸馏为主题文件 + 索引。对于长期大量使用 mica-code 的场景，类似的记忆整理机制可以减少 MEMORY.md 膨胀。

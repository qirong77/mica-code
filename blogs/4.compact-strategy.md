# 【04】Code Agent 从零到一：对话压缩策略的演进

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

让 LLM Agent 处理长对话是个棘手的问题。当几百轮对话塞满上下文窗口时，你需要"压缩"历史消息来腾出空间。mica-code 的初版压缩实现很直接——把旧消息打包送给 LLM，请它吐一句摘要。这听起来合理，直到你看到实际效果：

```
[对话历史摘要]
用户询问了autocompact插件的压缩逻辑，助手分析了claude-code-main的实现方式并提出了重构方案。
```

几十条消息、数千行代码细节、多轮纠错——全变成了一句话。下一轮 LLM 就懵了："你说的那个重构方案具体是什么来着？"

这就是 mica-code 初版 `auto-compt-plugin.ts` 的现状。本文记录了从"一段简洁摘要"到结构化压缩的完整演进过程，以及从 claude-code 参考实现中借鉴的核心设计原则。

---

## 初版：把所有鸡蛋压成一个饼

```typescript
// auto-compact-plugin.ts 初版
const response = await client.messages.create({
  model: modelName,
  max_tokens: 2048,
  system: '你是一个对话压缩助手。请将以下对话历史压缩为一段简洁的摘要，用中文回答。'
    + '保留：用户的问题、关键回答、重要决策、未完成的任务。',
  messages: [
    ...messages,
    { role: 'user', content: '请将以上对话历史压缩为一段简洁的摘要。' },
  ],
});
```

问题一目了然：

1. **输出空间只有 2048 tokens**。你知道一个稍微复杂点的代码片段本身就多大吗？连完整函数签名都可能放不下。
2. **prompt 太弱**。"压缩为一段简洁的摘要"——LLM 会忠实地执行"简洁"二字，结果就是所有技术细节被蒸馏成一句废话。
3. **没有结构引导**。没有要求 LLM 区分"已解决的问题"和"待处理的任务"，没有要求它保留文件路径和代码片段。

结果就是：压缩后的上下文对 LLM 后续工作几乎没有帮助，下一轮它又得重新读文件、重新理解意图。

## 分析 claude-code 的压缩体系

claude-code 的压缩实现远远不只是一个 prompt。它是一个**三层防御体系**，每层解决不同粒度的问题。

### 第一层：Microcompact（每轮触发，无感）

microcompact 不生成摘要，而是在每次 API 调用前悄悄清理过期的工具返回值。

```
Read file A → result (800 tokens)    ← 第一轮
Read file B → result (1200 tokens)   ← 第二轮
Read file C → result (3000 tokens)   ← 第三轮（此时前两个结果可能没用了）
```

当工具返回值数量超过阈值（默认 10 个），microcompact 会标记最老的为"可删除"，下次 API 请求时告诉服务端跳过它们。

**但这有个关键问题：改了消息内容 = 破坏 prompt cache。**

Anthropic API 的 prompt cache 工作原理是：如果两次请求的消息前缀完全相同，服务端可以复用上一次的计算结果（cache hit），省时省钱。如果你把 tool_result 从 800 tokens 改成一句话，前缀变了，cache 就失效了。

claude-code 的解法是 `cache_edits`——一种特殊的 API 内容块：

```json
{
  "type": "cache_edits",
  "edits": [
    { "type": "delete_tool_result", "tool_use_id": "toolu_xxx" },
    { "type": "delete_tool_result", "tool_use_id": "toolu_yyy" }
  ]
}
```

这个块不改变消息内容本身——消息的字节序列完全不变——但告诉服务端"从缓存读取时忽略这几个块"。这是真正的零成本删除：既释放了上下文，又保住了 cache hit。

> 这个机制只支持 Claude 4.x 模型。对于其他 API（比如 Mica 默认用的 DeepSeek），这条路走不通——所以 mica 的下一层压缩尤其重要。

### 第二层：Auto Compact（超过阈值触发，生成摘要）

这才是 mica 已有的那层。但 claude-code 用的 prompt 完全不是"给出简洁摘要"，而是一个长达 150 行的**9 节结构化模板**。

核心设计：

**`<analysis>` + `<summary>` 两阶段输出**

```
<analysis>
[这里让模型自由梳理：按时间顺序过每条消息，
识别用户意图、技术决策、文件名、错误、修复……]
</analysis>

<summary>
1. 主要请求与意图
2. 关键技术概念
3. 文件与代码（含完整片段）
4. 错误与修复
5. 问题解决
6. 所有用户消息
7. 待完成任务
8. 当前工作
9. 可选的下一步
</summary>
```

**为什么要分两阶段？** 让模型先"自言自语"整理思路能显著提升摘要质量。`<analysis>` 是一个草稿空间，模型可以在里面犯错、遗漏、再修正，最终只把整理好的 `<summary>` 输出给最终上下文。`formatCompactSummary()` 会丢弃 `<analysis>`（它只对压缩过程有价值），保留 `<summary>`。

**为什么是这 9 节？** claude-code 团队显然踩过很多坑。例如：
- **所有用户消息**：LLM 特别容易在压缩后"忘记"用户说过什么。单独一节强制它回顾每一条用户输入。
- **文件与代码（含完整片段）**：如果没有这一节，LLM 会说"修改了某文件"，但下一轮记不住具体改了什么——然后重读文件，白费 tokens。
- **可选的下一步 + 对话原文引用**：防止模型在恢复上下文后跑偏。引号里是用户原文，不是模型自己的总结。

### 第三层：Reactive Compact（API 返回 prompt-too-long 时触发）

当 token 计数估算不准，API 真的返回 "prompt too long" 错误时，立即执行紧急压缩。这是最后的防线——按 API-round 粒度从头部逐步截断并重试。

## mica-code 的改造

mica 是轻量级项目，不可能照搬三层体系。但我们从 claude-code 的 Auto Compact 层中提炼了**立即可落地的改进**：

### 改动 1：SUMMARY_MAX_TOKENS: 2048 → 8192

```typescript
const SUMMARY_MAX_TOKENS = 8192;
```

9 节结构化摘要需要空间。8192 足以容纳多个文件的代码片段和详细描述。实际输出通常不会打满——prompt 里的模板本身约 800 tokens，留给实际内容的空间仍然充裕。

### 改动 2：新的压缩 prompt

完整 prompt 约 55 行，核心思想：

```typescript
const compactPrompt = `CRITICAL: 只输出纯文本，不要调用任何工具。

你的任务是创建一份详细的对话历史摘要。请先用 <analysis> 标签组织思路，
确保覆盖了所有必要的信息点，然后用 <summary> 标签输出最终摘要。

分析时请按时间顺序检查每条消息，识别：用户的明确请求和意图、你的处理方式、
关键决策、技术概念、具体文件名和代码、遇到的错误及修复方式、用户的具体反馈。

摘要应包含以下结构：

1. 主要请求与意图：...
2. 关键技术概念：...
3. 文件与代码：逐个列出查看、修改或创建的文件，包含完整代码片段
4. 错误与修复：列出所有遇到的错误以及如何修复
5. 问题解决：记录已解决的问题和仍在排查中的问题
6. 所有用户消息：列出全部非工具返回的用户消息
7. 待完成任务：...
8. 当前工作：精确描述摘要请求前正在进行的工作
9. 可选的下一步：包含对话原文引用

输出格式示例：
<analysis>...</analysis>
<summary>...</summary>`;
```

几个设计细节：

1. **开头就是 CRITICAL 禁令**。参考实现甚至把 NO_TOOLS_PREAMBLE 放在第一位，因为 Sonnet 4.6+ 在拿到完整工具列表后有时会调用工具而不是输出摘要——如果只给一轮机会，调用工具 = 失败。
2. **prompt 放在 user message 而非 system**。system 只放简单角色提示。实践中，user message 里的指令被 LLM 遵守的概率更高。
3. **中文适配**。mica 的用户是中文环境，整个 prompt 用中文，保留的是结构设计而非英文原文。

### 改动 3：formatCompactSummary()

```typescript
private formatCompactSummary(raw: string): string {
  let result = raw.replace(/<analysis>[\s\S]*?<\/analysis>/g, '');
  const summaryMatch = result.match(/<summary>([\s\S]*?)<\/summary>/);
  if (summaryMatch?.[1]) {
    result = summaryMatch[1].trim();
  }
  return result.replace(/\n{3,}/g, '\n\n').trim();
}
```

三层处理：
1. 删除 `<analysis>` 块——这个草稿对后续对话没有价值，只浪费上下文
2. 提取 `<summary>` 内容——如果模型没用 XML 标签（兼容性处理），不过滤
3. 清理多余空行

### 改动 4：压缩后的消息包装

```typescript
const summaryMessage =
  `以下是之前对话的详细摘要，对话因上下文超限被压缩。` +
  `请基于此摘要和后续保留的消息继续工作，不要询问摘要中已涵盖的问题。\n\n${summary}`;
```

不只是一个标签。这告诉 LLM 三件事：
- 这是压缩恢复，不是新对话
- 你已经有了足够的上下文
- 别问重复问题，直接继续工作

## 还没有做的事：cache_edits 和 post-compact 恢复

当前改造聚焦于"摘要质量"这一个维度。claude-code 还有两个重要能力尚未引入：

### Post-compact 上下文恢复

压缩后，LLM 丢失了所有文件内容、skill 指令、plan 文件。claude-code 在 `compactConversation()` 中做了一件很重的事——重新读取最近访问的文件，注入已调用的 skills，重新播报工具列表、agent 列表、MCP 指令。

这对 mica 来说可能需要一个文件追踪机制：在 FileReadTool 执行时记录时间戳，压缩时选择最近 N 个文件重新读取并附加到恢复的上下文里。

### Microcompact / cache_edits

这是依赖 API 层的能力。如果你切换到了支持 `cache_edits` 的 API（比如直接使用 Anthropic SDK），可以实现在不破坏 prompt cache 的情况下逐步删除旧的 tool_results。

---

## 核心原则

回顾整个过程，从 claude-code 的压缩体系中可以提炼出三个通用原则：

1. **摘要不是省事，是恢复**。压缩后的摘要必须能让模型无缝继续工作，文件路径、代码片段、错误历史一个都不能少。如果压缩后的上下文还需要模型重做工作，那压缩是失败的。

2. **结构引导比字数限制更重要**。不要告诉 LLM "请简洁"，而是要告诉它"请用这个结构输出"。LLM 天生擅长填充模板，模板里的每个槽位都是一种硬约束，比"简洁"这种模糊指示有效得多。

3. **分析草稿和最终输出分开**。`<analysis>` 给模型思考空间，`<summary>` 给最终上下文。两阶段输出的质量远高于单阶段，代价只是多一些输出 token——相比压缩节省的上下文 tokens 来说微不足道。

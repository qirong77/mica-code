# 【05】Code Agent 从零到一：工具设计的防御性编程

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

让 LLM 调用本地工具看起来很简单：接收参数、执行、返回结果。

但工具一旦接入真实项目，就会马上遇到几个问题：

- `read_file` 读了一个 5MB 的打包产物，直接把上下文撑爆；
- `web_fetch` 把整页 HTML、脚本、导航、广告都塞回模型；
- `run_shell` 执行了 `find .` 或 `cat package-lock.json`，返回几万行输出；
- `grep_search` 在 `node_modules`、`dist`、`.git` 里扫了半天；
- `list_files` 一次列出几千个文件，模型其实只需要其中十几个。

这篇文章记录 mica-code 对工具层做的一次防御性改造。目标不是把工具做复杂，而是给每个工具加上几道必要的防线：**限制输入、限制执行、限制输出**。

---

## 一、为什么工具结果需要预算

对 Code Agent 来说，工具输出不是普通日志，而是下一轮模型输入的一部分。

也就是说：

```txt
工具输出字节数 ≈ 下一轮 prompt token 成本
```

一个工具返回 100KB 文本，模型就要重新阅读这 100KB；多个工具连续返回大结果时，上下文窗口和成本都会迅速失控。

所以工具设计里有一个基本原则：

> 工具不能假设自己的输出可以完整返回给模型。

这次改造里，我先加了一个通用输出限制模块：

```typescript
// packages/tools/utils/outputLimits.ts
export const DEFAULT_MAX_TOOL_OUTPUT_CHARS = 60_000;
export const DEFAULT_PREVIEW_CHARS = 4_000;

export function formatSize(bytes: number): string {
  if (bytes < 1024) return `${bytes}B`;
  if (bytes < 1024 * 1024) return `${(bytes / 1024).toFixed(1)}KB`;
  return `${(bytes / (1024 * 1024)).toFixed(1)}MB`;
}

export function truncateMiddle(text: string, maxChars: number, markerPrefix = '内容已截断'): string {
  if (text.length <= maxChars) return text;

  const marker = `\n\n[${markerPrefix}，省略 ${text.length - maxChars} 字符]\n\n`;
  const budget = Math.max(0, maxChars - marker.length);
  const head = Math.ceil(budget * 0.65);
  const tail = Math.floor(budget * 0.35);

  return text.slice(0, head) + marker + text.slice(text.length - tail);
}
```

这里没有只保留开头，而是使用 **middle truncation**：保留前 65% 和后 35%。

原因是很多输出的尾部也很关键：

- 测试失败日志的最后几行通常有错误原因；
- `npm install` / `pnpm install` 的尾部有最终失败信息；
- 网页文档开头可能是导航，真正 API 说明在后面；
- `git diff` 的尾部可能还有重要文件。

简单 `slice(0, max)` 经常会丢掉最关键的结论。

## 二、read_file：不要默认读完整文件

最危险的工具之一是 `read_file`。

一个天真的版本可能是：

```typescript
async execute(input: { file_path: string }): Promise<string> {
  const content = await readFile(input.file_path, 'utf-8');
  return content
    .split('\n')
    .map((line, i) => `${String(i + 1).padStart(4)} | ${line}`)
    .join('\n');
}
```

它的问题有三个：

1. 默认读取完整文件；
2. 默认认为文件是文本；
3. 默认认为每一行长度都合理。

真实项目里这三个假设都不成立。

### 1. 默认分页读取

改造后的 `read_file` 默认只读 200 行：

```typescript
const DEFAULT_LIMIT_LINES = 200;
const HARD_LIMIT_LINES = 2_000;
```

输入 schema 也明确告诉模型：

```typescript
limit: {
  type: 'number',
  description: `读取行数。默认 ${DEFAULT_LIMIT_LINES}，最大 ${HARD_LIMIT_LINES}。`,
}
```

如果模型没有传 `limit`，工具不会再返回完整文件，而是返回第一页，并提示后续如何继续读取：

```txt
[第 1-200 行，共 1834 行]
文件: src/index.ts
大小: 84.2KB
后续可用 offset=201, limit=200 继续读取。
```

这会把模型的行为从“拿完整文件”引导成“按需分页”。

### 2. 先 stat，再决定是否读取

在真正读取文件内容之前，先看文件大小：

```typescript
const MAX_DIRECT_READ_BYTES = 256 * 1024;
const HARD_READ_BYTES = 2 * 1024 * 1024;
```

策略是：

- 文件超过 `256KB` 且没有显式 `limit`：拒绝直接读取；
- 文件超过 `2MB` 且没有显式分页：拒绝直接读取；
- 用户显式传了 `offset/limit`：允许按行流式读取目标范围。

这比简单禁止大文件更好，因为大文件里某个局部内容仍然可能有价值。我们拒绝的是“无脑整读”，不是拒绝所有访问。

### 3. 二进制检测

仅靠扩展名不够。有些二进制文件没有扩展名，有些文本文件扩展名不标准。

所以读取前会 sniff 前 8KB：

```typescript
const BINARY_SNIFF_BYTES = 8 * 1024;

function looksBinary(buffer: Buffer): boolean {
  if (buffer.length === 0) return false;
  if (buffer.includes(0)) return true;

  let suspicious = 0;
  for (const byte of buffer) {
    if (byte < 7 || (byte > 14 && byte < 32)) suspicious++;
  }
  return suspicious / buffer.length > 0.3;
}
```

如果检测到二进制，直接返回 metadata：

```txt
检测到二进制文件，未返回内容。
文件: assets/logo.png
大小: 42.1KB
```

### 4. 流式按行读取

即使用户读取大文件的某个范围，也不应该把整个文件读进内存。

改造后使用 `readline` 流式扫描：

```typescript
async function readLineRange(
  filePath: string,
  offset: number,
  limit: number,
): Promise<{ lines: string[]; totalLines: number }> {
  const lines: string[] = [];
  let lineNo = 0;
  const end = offset + limit - 1;
  const rl = createInterface({ input: createReadStream(filePath), crlfDelay: Infinity });

  for await (const line of rl) {
    lineNo++;
    if (lineNo >= offset && lineNo <= end) lines.push(line);
  }

  return { lines, totalLines: lineNo };
}
```

这样即使文件很大，内存里也只保留目标范围内的行。

### 5. 单行截断

很多文件行数不多，但单行极长：

- minified JS；
- sourcemap；
- lock file；
- JSON dump；
- base64；
- SVG。

所以每行还要单独限制：

```typescript
const MAX_LINE_CHARS = 2_000;
```

超长行会变成：

```txt
12 | {"deps": ... [单行截断，省略 58321 字符] ... }
```

这比整体截断更精确，因为它保留了文件结构和行号。

## 三、web_fetch：网页不是正文

`web_fetch` 的 token 浪费通常比 `read_file` 更严重。

一个网页里真正有价值的是正文，但原始 HTML 里还包含：

- script；
- style；
- svg；
- base64 image；
- cookie banner；
- 导航菜单；
- footer；
- 相关推荐；
- 埋点和广告。

如果直接把 HTML 转成文本，会让模型读大量噪音。

### 1. 降低下载上限

原来最大内容长度是 10MB，这次降到 5MB：

```typescript
const MAX_CONTENT_LENGTH = 5 * 1024 * 1024;
```

并且在下载前先看 `content-length`：

```typescript
const contentLength = response.headers.get('content-length');
if (contentLength && parseInt(contentLength, 10) > MAX_CONTENT_LENGTH) {
  throw new Error(`内容大小超过 ${formatSize(MAX_CONTENT_LENGTH)} 限制`);
}
```

下载后还要再检查一次，因为有些响应没有 `content-length`。

### 2. HTML 先清理，再转 Markdown

这次加了一层 HTML 清理：

```typescript
function stripHtmlNoise(html: string): string {
  return html
    .replace(/<script\b[^>]*>[\s\S]*?<\/script>/gi, '')
    .replace(/<style\b[^>]*>[\s\S]*?<\/style>/gi, '')
    .replace(/<noscript\b[^>]*>[\s\S]*?<\/noscript>/gi, '')
    .replace(/<svg\b[^>]*>[\s\S]*?<\/svg>/gi, '')
    .replace(/data:image\/[^;\s"']+;base64,[A-Za-z0-9+/=]+/g, '[base64 image omitted]');
}
```

然后再交给 Turndown 转 Markdown：

```typescript
const html = stripHtmlNoise(rawBuffer.toString('utf-8'));
return cleanText(getTurndown().turndown(html));
```

这一步能明显减少无效 token。

### 3. 支持 query，只返回相关片段

这是 `web_fetch` 最重要的优化。

新增参数：

```typescript
query: {
  type: 'string',
  description: '只返回与该查询相关的页面片段，用于减少 token 消耗（可选）',
}
```

如果模型想知道某个页面里的“authentication headers”，它不需要读完整页面：

```json
{
  "url": "https://docs.example.com/api",
  "query": "authentication headers"
}
```

工具会把页面按段落切开，对 query terms 做简单打分，只返回最相关的几个段落：

```typescript
function pickRelevantSections(content: string, query: string): string {
  const terms = query.toLowerCase().split(/\s+/).filter((term) => term.length >= 2);

  const paragraphs = content.split(/\n{2,}/).filter(Boolean);
  const scored = paragraphs
    .map((paragraph, index) => {
      const lower = paragraph.toLowerCase();
      const score = terms.reduce((sum, term) => sum + (lower.includes(term) ? 1 : 0), 0);
      return { paragraph, index, score };
    })
    .filter((item) => item.score > 0)
    .sort((a, b) => b.score - a.score || a.index - b.index)
    .slice(0, 8)
    .sort((a, b) => a.index - b.index);

  return scored.map((item) => item.paragraph).join('\n\n---\n\n');
}
```

这不是复杂 RAG，只是一个轻量关键词过滤，但对减少 token 已经很有效。

### 4. 支持 max_chars

新增参数：

```typescript
max_chars: {
  type: 'number',
  description: `最多返回字符数，默认 ${DEFAULT_MAX_CHARS}，最大 ${HARD_MAX_CHARS}`,
}
```

默认：

```typescript
const DEFAULT_MAX_CHARS = 30_000;
const HARD_MAX_CHARS = 100_000;
```

如果内容超出，就走 middle truncation，而不是原样返回。

### 5. 非文本响应不强行解析

对于非文本内容：

```typescript
if (!contentType.includes('text/') && contentType) {
  return `非文本响应 (${contentType})，未尝试解析为正文。`;
}
```

这样不会把图片、压缩包、PDF 等内容误当文本塞回模型。

## 四、run_shell：命令输出是另一个 token 黑洞

Shell 工具的问题是：你永远不知道命令会输出多少。

这些命令都可能制造巨量输出：

```bash
cat package-lock.json
find .
ls -R
rg something .
npm test
```

### 1. 限制捕获和返回

这次给 shell 加了两层限制：

```typescript
const MAX_SHELL_OUTPUT_CHARS = 60_000;
const MAX_STREAM_CHARS = 120_000;
```

- `MAX_STREAM_CHARS`：最多捕获多少输出，避免进程内存无限增长；
- `MAX_SHELL_OUTPUT_CHARS`：最多返回多少给模型，避免上下文爆炸。

输出完成后统一走：

```typescript
const truncated = finalizeTextOutput(output, {
  maxChars: MAX_SHELL_OUTPUT_CHARS,
  label: '命令输出',
});
```

### 2. 对高风险命令给提示

工具不会阻止所有大输出命令，但会识别一些常见模式：

```typescript
function largeOutputHint(command: string): string | null {
  const trimmed = command.trim();

  if (/\bcat\s+/.test(trimmed)) {
    return '检测到 cat 命令。读取大文件时建议改用 read_file 的 offset/limit。';
  }

  if (/\bls\s+(-[^\n]*R|[^\n]*-[^\n]*R)/.test(trimmed)) {
    return '检测到递归 ls。建议用 list_files 并缩小 pattern/path。';
  }

  if (/\bfind\s+\.?(\s|$)/.test(trimmed) && !/\|\s*(head|grep|rg|sed)\b/.test(trimmed)) {
    return '检测到可能产生大量输出的 find。建议加更具体条件或 pipe 到 head/grep。';
  }

  return null;
}
```

这类提示的目的不是教育用户，而是影响模型下一步的工具选择：

- 不要用 `cat` 读大文件；
- 用 `read_file` 的 `offset/limit`；
- 用 `grep_search` 定位；
- 用 `head/tail` 缩小输出。

## 五、grep_search：搜索结果也需要上限

`grep_search` 原本已经用了 `rg`，这是对的。ripgrep 比系统 grep 更适合 code agent：

- 快；
- 默认尊重 `.gitignore`；
- 支持 glob；
- 输出格式稳定。

但还需要继续加防线。

### 1. 默认忽略生成目录

这次显式加了这些 glob：

```typescript
const args = [
  '--line-number',
  '--color=never',
  '--no-config',
  '--glob',
  '!node_modules/**',
  '--glob',
  '!.git/**',
  '--glob',
  '!dist/**',
  '--glob',
  '!build/**',
  '--glob',
  '!coverage/**',
  '--glob',
  '!.next/**',
];
```

虽然 ripgrep 会尊重 `.gitignore`，但显式排除这些目录可以降低误扫大目录的概率，尤其是在没有 `.gitignore` 或搜索路径不是仓库根目录时。

### 2. 捕获限制和返回限制

```typescript
const MAX_GREP_OUTPUT_CHARS = 40_000;
const MAX_CAPTURE_CHARS = 120_000;
```

即使用户传：

```json
{ "head_limit": 0 }
```

也不会无限返回，而是经过统一输出限制：

```typescript
resolve(
  finalizeTextOutput(lines.slice(skipOffset).join('\n'), {
    maxChars: MAX_GREP_OUTPUT_CHARS,
    label: '搜索结果',
  }),
);
```

`head_limit=0` 可以表示“不按行数限制”，但不能表示“突破上下文预算”。

## 六、list_files：列文件也会爆上下文

`list_files` 很容易被低估。

一个 monorepo 里执行：

```json
{ "pattern": "**/*" }
```

可能返回几万行路径。路径虽然短，但数量一多也会占用大量 token。

这次加了默认上限：

```typescript
const DEFAULT_LIMIT = 500;
const HARD_LIMIT = 5_000;
```

并且默认忽略常见大目录：

```typescript
const DEFAULT_IGNORE = [
  'node_modules/**',
  '.git/**',
  'dist/**',
  'build/**',
  'coverage/**',
  '.next/**',
  '.cache/**',
  'target/**',
];
```

返回结果会明确告诉模型是否被截断：

```txt
src/index.ts
src/tools/read.ts
...

[显示 500 个文件，共 18421 个。请缩小 path/pattern 或调整 limit。]
```

这比悄悄截断更好，因为模型知道自己看到的不是完整列表。

## 七、这次改造后的工具边界

| 工具          | 主要风险                 | 改造策略                                             |
| ------------- | ------------------------ | ---------------------------------------------------- |
| `read_file`   | 大文件、二进制、超长行   | stat、二进制 sniff、默认分页、流式按行、单行截断     |
| `web_fetch`   | HTML 噪音、网页过大      | 下载限制、清理 HTML、Markdown、query 过滤、max_chars |
| `run_shell`   | stdout/stderr 无限输出   | 捕获限制、返回限制、高风险命令提示                   |
| `grep_search` | 搜索范围过大、结果过多   | 默认忽略目录、超时、捕获限制、返回限制、分页         |
| `list_files`  | 文件路径列表过长         | 默认 limit、hard limit、忽略生成目录、截断提示       |

这里有一个共同点：**所有工具都要承认自己可能被模型用错。**

模型不一定知道某个文件是构建产物，也不一定知道某个命令会输出十万行。工具层必须兜底。

## 八、几个设计原则

### 1. 默认返回小结果

不要默认“完整返回”。

更好的默认值是：

- `read_file` 默认 200 行；
- `web_fetch` 默认 30000 字符；
- `grep_search` 默认 200 行；
- `list_files` 默认 500 个；
- `run_shell` 默认 60000 字符。

如果模型真的需要更多，它可以继续分页读取。

### 2. 拒绝无脑整读，但允许精确读取

大文件不是完全不能读，而是不能不带范围地读。

```txt
坏：read_file("large.log")
好：grep_search("ERROR", "large.log")
好：read_file("large.log", offset=1200, limit=100)
```

### 3. 截断必须显式告诉模型

不要静默截断。工具输出应该告诉模型：

- 原始大小；
- 返回上限；
- 当前范围；
- 是否还有后续；
- 下一次应该用什么 offset/limit。

否则模型会误以为自己看到了完整信息。

### 4. 限制执行过程，不只限制最终输出

只在最后截断还不够。

例如 shell 如果持续输出 500MB，最后截断成 60KB 也太晚了，进程内存已经被打爆。所以要同时限制：

- 下载大小；
- 捕获大小；
- 读取方式；
- 返回大小。

### 5. 工具输出也是 prompt 工程

工具的错误提示、截断提示、分页提示会直接影响模型下一步行动。

比如这句：

```txt
请使用 offset 和 limit 参数分段读取，或用 grep_search 搜索特定内容。
```

它不只是给用户看的，也是给模型看的。好的工具输出会把模型引导到更省 token、更安全的路径上。

## 九、后续还可以做什么

这次改造是低侵入版本，还有几件事可以继续优化：

### 1. 大结果落盘

Claude Code 有一个值得借鉴的设计：工具结果过大时，把完整结果保存到 session 目录，只把 preview 和文件路径返回给模型。

这样模型既不会被大输出撑爆，也能在需要时用 `read_file` 继续查看某个片段。

### 2. read_file 去重缓存

如果同一个文件、同一个 offset/limit、mtime 没变化，可以返回：

```txt
该文件范围之前已读取，内容未变化。
```

避免重复把相同内容塞进上下文。

### 3. fetch 正文提取更智能

现在只是清理 HTML 后转 Markdown。后续可以加入 Readability 算法，更准确地提取正文区域，过滤导航和 footer。

### 4. JSON 结构化读取

对于大 JSON，可以支持：

```json
{ "mode": "summary" }
```

返回 key 分布、数组长度、sample，而不是完整 JSON。

也可以支持：

```json
{ "json_path": "dependencies.react" }
```

只读取目标节点。

---

## 结语

给 Code Agent 写工具，不能只考虑 happy path。

真实项目里有巨大的 lock file、构建产物、日志、二进制文件、网页噪音、递归命令和 monorepo。LLM 会在不知道代价的情况下调用这些工具。

所以工具层必须有自己的边界：

```txt
先判断，再执行；
先分页，再完整；
先搜索，再读取；
先截断，再返回；
能提示，就提示下一步怎么做。
```

防御性编程不是让工具变保守，而是让工具在最坏情况下仍然可控。

对 Code Agent 来说，这就是工具设计的底线。

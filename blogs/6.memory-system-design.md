# 【06】Code Agent 从零到一：claude-code 文件级记忆系统设计

> 本文是 [mica-code](https://github.com/qirong77/mica-code) 系列文章之一。mica-code 是一个从零搭建的 CLI code agent，基于 Bun + TypeScript + React（Ink）+ Anthropic SDK，目标是搞清楚 Claude Code 这类工具底层到底怎么工作。

一个 Code Agent 如果每次对话都从零开始认识你和你的项目，就像一个每次见面都要重新自我介绍才能工作的搭档。你不会觉得他不可靠，但你也绝对不会依赖他。

给 LLM 加上"记忆"不是新鲜事——你可以把整个对话历史塞进去，也可以用向量数据库做 RAG。但 claude-code 选择了一条非常不同的路：**文件系统就是记忆系统**。MEMORY.md 是索引，一个目录下的 .md 文件是记忆条目，前端的 frontmatter 是元数据。没有向量化、没有嵌入模型、没有外部数据库。一切直接可读、可 grep、可 git diff。

本文拆解这套看似简单但经过大量 eval 验证的设计。

---

## 第零章：如果你不给它记忆

没有持久记忆的 agent 的典型表现：

- 你告诉他"不要 mock 数据库做测试"，下次他又写了 `jest.mock`
- 你解释过项目使用 pnpm workspaces，他每次都要 `grep package.json` 确认
- 你花了三小时和他讨论的架构决策，下周他就忘了
- 他永远不会主动了解你的角色和偏好，每次都是"我是一个 AI 助手，请问你需要什么帮助"

这些问题不解决，agent 永远只能做一次性任务，无法成为真正的"搭档"。

## 第一章：整体架构——文件系统即数据库

claude-code 的内存系统存储在文件系统中，默认路径：

```
~/.claude/projects/<sanitized-git-root>/memory/
├── MEMORY.md                    # 索引文件（总是加载到上下文）
├── user_role.md                 # 主题文件（按需加载）
├── feedback_testing.md
├── project_migration_deadline.md
└── team/                        # 团队共享记忆（TEAMMEM feature）
    └── MEMORY.md
```

关键设计决策：**索引 + 主题文件分离**。

`MEMORY.md` 不是存放记忆内容的地方，它是一个纯索引——每行一个链接：

```
- [用户角色](user_role.md) — 资深后端工程师，偏好中文，专注 TypeScript 项目
- [测试反馈](feedback_testing.md) — 不要 mock 数据库，用真实测试库
```

每条索引不超过 ~150 字符，整个 MEMORY.md 上限 200 行 / 25KB。超出会被截断并附带警告。

为什么要这样设计？因为 MEMORY.md 每次对话启动都会**完整加载到系统提示的上下文中**。把它做大等于每轮都吃掉宝贵的上下文预算。主题文件只在 LLM 认为相关时才会通过专门的选择器去读取（后面会讲）。

代码实现上，索引和主题文件的职责非常明确：

```typescript
// memdir/memdir.ts — MEMORY.md 的截断逻辑
export const MAX_ENTRYPOINT_LINES = 200
export const MAX_ENTRYPOINT_BYTES = 25_000

// 截断优先按行（自然边界），再按字节（防止超长行）
// 两者同时限制，缺一不可
```

## 第二章：记忆的四分类法——"什么要记"比"怎么记"更重要

claude-code 把记忆严格限制为四种类型，且每种类型都有明确的边界：

| 类型 | 用途 | 不该记的 |
|------|------|----------|
| `user` | 用户角色、偏好、知识、职责 | 代码偏好可以写在 CLAUDE.md |
| `feedback` | 工作方式指导（避免什么、坚持什么） | 一次性夸赞/抱怨 |
| `project` | 项目上下文（截止日期、事故、决策） | 代码架构、文件路径 |
| `reference` | 外部系统指针（Linear 项目、Slack 频道、Grafana 面板） | 临时使用的链接 |

但比"四种类型"更重要的是 **"什么不该记"**这一负向清单。这是经过大量 eval 迭代才发现的关键：

```typescript
// memoryTypes.ts — WHAT_NOT_TO_SAVE_SECTION
// 这些内容永远不应当被记为记忆：
- 代码模式、架构、文件路径 → 可以通过阅读当前项目状态推导
- Git 历史、谁改了什么 → git log / git blame 是权威来源
- 调试方案、修复配方 → 修正在代码里，提交信息有上下文
- 任何已经在 CLAUDE.md 中记录的东西
- 短暂的任务细节：进行中的工作、临时状态、当前对话上下文
```

这个负向清单有一个有趣的 Eval 验证细节。Prompt 工程团队发现，即使明确写出"不要存这些"，LLM 仍然会在用户说"请记住本周的 PR 列表"时照做。他们加了一条更狠的规则：

> 即使用户明确要求你保存，这些排除规则仍然适用。如果他们要求保存 PR 列表或活动摘要，请询问其中**令人惊讶或非显而易见**的部分——那才是值得保留的。

每条记忆文件用 YAML frontmatter 标注类型：

```markdown
---
name: {{记忆名}}
description: {{一行描述——用于未来判断相关性，所以必须具体}}
type: user
---
{{记忆内容}}
```

这个 `description` 字段不是给人类看的——它是给**记忆选择器**（一个 side-query Sonnet 调用）用来判断哪些记忆与当前查询相关的。

## 第三章：记忆注入——系统提示 + 查询时召回

记忆系统有两条注入路径：**被动加载**和**主动召回**。

### 路径一：MEMORY.md 被动加载

每次会话启动时，`MEMORY.md`（索引文件）通过 `loadMemoryPrompt()` 被拼接进系统提示中。这是一个关键的架构决策——它不做 RAG，不向量化，不排序。直接把索引完整放在提示词里。

这背后有一个重要的工程考量：prompt cache 友好性。

```typescript
// memdir/memdir.ts — loadMemoryPrompt() 的路径分发
export async function loadMemoryPrompt(): Promise<string | null> {
  // 根据启用的功能组合返回不同的提示词变体：
  // - KAIROS（长驻助手）：daily log 模式
  // - TEAMMEM（团队记忆）：combined 模式（私有 + 团队双目录）
  // - 默认 auto-memory：individual 模式（单目录）
  // - 禁用：返回 null
}
```

系统提示中注入的不只是索引内容，还有一套完整的行为指令——这也是为什么 `memoryTypes.ts` 里有 190 行的提示词模板：

- **How to save memories**：两步流程（写主题文件 → 在 MEMORY.md 加索引），强调"先检查是否有已存在的文件可以更新"
- **When to access memories**：什么时候该去看记忆，什么时候该无视
- **Before recommending from memory**：这是最重要的一条——"记忆说 X 存在"不等于"X 现在仍然存在"

### 路径二：查询时主动召回

当 LLM 的查询可能与某些记忆相关时（例如用户说"继续上次的迁移工作"），会触发 `findRelevantMemories()`：

```typescript
// findRelevantMemories.ts
// 1. scanMemoryFiles() — 扫描记忆目录，读取每个 .md 的前 30 行 frontmatter
// 2. sideQuery(Sonnet) — 把查询 + 文件 manifest 送给 Sonnet 选择至多 5 个
// 3. 读取选中的完整文件，以 relevant_memories attachment 注入对话
```

这个选择器有几个巧妙的设计：

**防止重复召回**。通过 `alreadySurfaced` 集合跟踪已经展示过的文件路径。如果上一轮已经召回了 `user_role.md`，这轮不会再选它——节省选择器预算去发现新的相关记忆。

**工具噪声抑制**。如果 agent 正在活跃使用某个工具（如 `mcp__X__spawn`），选择器会自动跳过该工具的使用说明文档——因为对话中已经有实际用法。但仍然保留关于该工具的警告和坑点记忆——"正在使用时，这些东西才最重要。"

**时间感知**。每条记忆都标注了创建时间：

```typescript
// memoryAge.ts
function memoryAge(mtimeMs: number): string {
  const d = Math.max(0, Math.floor((Date.now() - mtimeMs) / 86_400_000))
  if (d === 0) return 'today'
  if (d === 1) return 'yesterday'
  return `${d} days ago`
}

function memoryFreshnessText(mtimeMs: number): string {
  const d = memoryAgeDays(mtimeMs)
  if (d <= 1) return ''
  return `This memory is ${d} days old. ` +
    `Memories are point-in-time observations, not live state — ` +
    `claims about code behavior or file:line citations may be outdated. ` +
    `Verify against current code before asserting as fact.`
}
```

"47 days ago" 比一个 ISO 时间戳更有效——LLM 对时间戳做算术很差，但"47 天前"能直接触发"可能需要验证"的直觉。

## 第四章：后台记忆提取——不会打断你的工作

记忆不应该只靠 LLM 在对话中主动保存。用户和被对话打断后可能忘了说"记住这个"，LLM 自己也可能忽略。

claude-code 的方案是 **extractMemories**——一个在每轮对话结束后自动运行的后台 agent：

```
用户输入 → 主 agent 处理 → 返回响应 → stop hook 触发 → extractMemories
```

核心设计：

**Forked Agent，不破坏主对话的 prompt cache**。extractMemories 使用 `runForkedAgent`——完美 fork 主对话的系统提示和消息前缀，共享 prompt cache。这意味着这次后台提取不会计入用户的 token 消耗感知。

**主 agent 优先**。如果主 agent 已经在当轮中自己写过了记忆文件，extractMemories 会自动跳过——它只做补充。

**约束工具权限**。提取 agent 只能使用只读文件和 grep，写文件只能写到记忆目录内。rm 被禁止。它被明确告知"不要花轮次去验证——直接从对话内容中提取即可"。

**先读后写**。提示词明确要求两轮策略：第一轮并行读取所有可能需要更新的文件，第二轮并行写入。避免"读一个写一个"的串行浪费。

## 第五章：Auto Dream——记忆的自我清理

记忆写多了就会退化——重复、过时、矛盾。claude-code 通过 **Auto Dream** 机制定期整理：

```
触发条件（三重门控）：
1. autoMemoryEnabled && autoDreamEnabled（全局开关）
2. 距上次整理 ≥ 24 小时
3. 至少有 5 个新会话产生
```

触发后以 **forked agent** 方式运行，四阶段流程：

1. **Orient** — 浏览记忆目录，读 MEMORY.md
2. **Gather** — 从日志、会话记录、代码库中采集信号
3. **Consolidate** — 合并新信号到主题文件，删除过时事实，将相对日期转绝对日期
4. **Prune** — 保持 MEMORY.md 在 200 行以内

并发控制用的是 PID 锁文件：

```
.consolidate-lock
├── 内容：持有者 PID
├── mtime：即 lastConsolidatedAt 时间戳
└── 过期：1 小时（防止 PID 复用）
```

如果 forked agent 失败或被用户终止，锁文件的 mtime 回退到获取前的值，下次仍可以触发。用户也可以通过 `/dream` 命令手动触发，不受门控限制。

## 第六章：记忆漂移——"记得"不等于"正确"

这是 claude-code 记忆系统中最不显眼但最重要的一笔。

一个 LLM 从记忆中读到"用户是前端工程师，使用 React"，然后据此推荐了某个 React 特供方案。但实际上用户三周前已经转到 Vue 了，只是记忆没更新。

这就是"记忆漂移"——记忆没有错，但世界变了。

claude-code 在三个层面处理这个问题：

**1. 时间感知**。每条记忆召回时都伴随"X days ago"的年龄标注，超过 1 天就附带新鲜度警告。

**2. 验证优先于断言**。系统提示中有一个专门的章节：

> A memory that names a specific function, file, or flag is a claim that it existed *when the memory was written*. It may have been renamed, removed, or never merged. Before recommending it:
> - If the memory names a file path: check the file exists.
> - If the memory names a function or flag: grep for it.
> - "The memory says X exists" is not the same as "X exists now."

这段文字的措辞经过多次 eval 迭代。早期版本用抽象的"Trusting what you recall"做标题，效果很差（0/3）。改成"Before recommending from memory"这个动作导向的表述后，eval 通过率直接跳到 3/3——同样的正文，只改了标题。

**3. 排除已经读过的文件**。如果 agent 在当轮已经主动读了某个文件，该文件不会被召回为"相关记忆"——当前状态覆盖了记忆快照。

## 第七章：工程细节中的魔鬼

### Prompt Cache 友好性

记忆系统的每一个环节都在关注 prompt cache 的稳定性：

- **MEMORY.md 的 header（age + path）是创建时预计算并存储的**，避免渲染时调用 `Date.now()` 导致每次产生不同字节从而摧毁 cache。
- **KAIROS 模式**中，daily log 路径用 `join(memoryDir, 'logs', 'YYYY', 'MM', 'YYYY-MM-DD.md')` 这个模板描述而不是拼当前日期。因为提示词被 `systemPromptSection('memory', ...)` 缓存，不会随日期变化而失效。

### 路径安全

对于团队记忆（TEAMMEM），服务器推送的文件名可能包含路径穿越攻击（`../../../etc/passwd`）。`validateTeamMemKey()` 做了多层防御：

1. 字符串级别：拒绝 `\0`、`\\`、`/` 开头、URL 编码的 `..`
2. Unicode 规范化：拒绝全角字符（`．．／`）在 NFKC 下变成 `../` 的攻击
3. `resolve()` 消除 `..` 段
4. `realpath()` 解析符号链接——如果有人把 team 目录下的文件 symlink 到 `~/.ssh/authorized_keys`，resolve() 看不到但 realpath() 能看到

### 按需功能组合

记忆系统的三个模式通过 feature flag + 条件构建模块化组合：

```typescript
// memdir.ts — loadMemoryPrompt 的路径分发
if (feature('KAIROS') && autoEnabled && getKairosActive()) {
  return buildAssistantDailyLogPrompt(skipIndex)  // 长驻助手：追加式日志
}
if (feature('TEAMMEM') && isTeamMemoryEnabled()) {
  return buildCombinedMemoryPrompt(...)  // 团队协作：私有 + 共享双目录
}
if (autoEnabled) {
  return buildMemoryLines(...)  // 默认：单目录个人记忆
}
return null  // 完全禁用
```

每个分支有独立的提示词模板——不是运行时拼条件，而是编译时有不同的函数。这是为了减少 prompt 模板中的条件分支，保持每种模式下的提示词纯粹且短。

## 总结

claude-code 的记忆系统的核心理念就是几个关键词：

**文件系统即数据结构**。不引入外部数据库、向量存储、嵌入式模型。记忆就是 `.md` 文件，索引就是 MEMORY.md。简单到可以直接用任何编辑器打开修改，用 git 做版本控制，用 grep 搜索。

**写量少，不写噪声**。四分类法 + 负向清单严格限制了什么值得记。代码模式、架构、git 历史等可推导信息一律不记。"你甚至会用"不如不记"来拒绝用户明确要求保存的内容——保存一条好记忆比保存十条垃圾更难。

**读时有验证**。记忆不是真理，是过去某个时间点的快照。每条记忆携带时间戳和新鲜度警告，涉及代码建议时必须 grep 验证。

**自动维护**。extractMemories 做被动采集，Auto Dream 做主动整理。用户几乎不需要手动管理记忆生命周期。

**安全防御深入**。团队记忆的路径验证做了四层防御（字符串 → Unicode → resolve → realpath），从符号链接攻击到全角字符注入都有考虑。

这套设计最值得借鉴的不是某个具体的代码模式，而是"把文件系统当作唯一数据源"的工程直觉——它避开了 RAG 和向量数据库的复杂性，用最笨的方法达到了最可靠的效果。

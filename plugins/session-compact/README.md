# 会话压缩

主会话区右键菜单里的三条入口（清单里标了 `surface: "chat"`：压缩的是你正看着的这段
历史，侧栏会话行不放这几项）。模型配置变化后，下一次发送会在写入用户输入前自动快速压缩；
上下文到达阈值时还会自动走一遍「交接 → 压缩 → 继续」。

| 菜单项     | 做什么                                                                             | 代价            |
| ---------- | ---------------------------------------------------------------------------------- | --------------- |
| 快速压缩   | 把历史里的工具过程聚合成一条占位调用（说明里写明每种工具调了几次），思考与图片丢掉   | 本地操作，毫秒级 |
| 模型压缩   | 把用户与助手的对话交给模型写一段 checkpoint 摘要，旧历史折成摘要加最近几轮           | 一次模型请求    |
| 交接并压缩 | 让模型先写一份交接文档，再按自动压缩的同一条流水线压一次（手动入口，不看阈值）       | 一次模型请求起  |

三条都通过 `ctx.agent.compactIdleHistory` 压缩并保存当前会话记录，紧接着发出的请求按压小的
历史发送，`conversationMessages` 同步当前压缩结果。对话区完整展示当前持久化记录：模型压缩
后旧历史会变成摘要加最近几轮，重开会话也读取这份记录，不另存一份不随压缩变化的原始展示历史。
模型配置变化后的轮前 `compactHistory({ mode: 'quick' })` 同样落盘当前压缩结果并同步展示。

## 自动压缩：先写可见的交接文档，再压

一轮**成功结束**后看最近一次请求的输入（`ctx.agent.lastUsage().inputTokens`，就是输入框左下角
那个 ctx 数）。达到阈值时，插件以自己身份往会话里发一条消息——它会作为一条用户消息出现在
对话里，模型必须回答：

1. **交接**：消息要求模型暂停手里的活、这一轮不调用任何工具，按固定结构写一份交接文档
   （任务目标 / 已完成 / 进行中 / 待办 / 关键约束与坑 / 下一步），写在这条回复里。
2. **快速压缩**：交接那一轮结束、会话空闲后，先走一次 `mode: 'quick'`（只折工具过程）。
3. **模型压缩**：快速压缩后估算的上下文仍高于「模型压缩阈值」（默认 100K），再走一次
   `mode: 'model'` 写 checkpoint 摘要。
4. **继续**：压缩完成后发一条「继续」，让模型按交接文档里的待办接着做；交接文档里没有
   待办时它只回一句「没有待办，已收尾」。

交接文档还会另存一份到 `$MICA_HOME/handovers/<会话>-<时间>.md`（可在设置里关掉）：模型压缩
会把对话正文折成摘要，这份文件是之后回看「当时到底交接了什么」的唯一入口。对话里也会留
一条 compact notice，写明压缩前后的数字与实际做了哪几步。

### 触发与闸门

| 条件         | 默认值                | 说明                                                                 |
| ------------ | --------------------- | -------------------------------------------------------------------- |
| 触发阈值     | 400K tokens           | 最近一次请求的输入。同时不超过模型窗口的 90%：窗口小于约 444K 时提前触发 |
| 模型压缩阈值 | 100K tokens           | 快速压缩后估算仍高于它就补一次模型压缩                               |
| 最小间隔     | 10 分钟               | 两次自动流程之间至少隔这么久（从触发算起）；压不下去时靠它避免反复烧钱 |
| 连续失败     | 3 次                  | 报错或压完仍在阈值以上都算；到 3 次停下并提示，上下文回到阈值以下后自动恢复 |

另外几条不做的事：

- 会话正忙（这一轮在跑、别的进程持锁）时压缩返回 `busy`，下一拍再来，不排队也不插进正在跑的请求。
- 宿主的排队槽里已经有一条用户消息时先让它跑，不抢位置。
- 用户在自动流程里自己发了消息：压缩照做，但压完不再自动「继续」。
- 传输层那种「压缩后 lastUsage 不变」的坑：状态里记下压缩那一刻的用量，同一个数再来一次
  不算新的一轮（否则压完会立刻再次触发）。

### 为什么不在 `turn:after` 里直接压

压缩要独占写会话文件，`turn:after` 触发时这一轮还没有完全退出（`running` 仍是 true），
此时调 `compactIdleHistory` 只会拿到 `busy`。所以 `turn:after` 只做两件事：判定是否该发
交接、以及认出「交接那一轮回来了」并进入 `compact` 阶段；真正的压缩交给后台常驻任务，
空闲时每 1 秒试一拍（`ctx.background`，随插件生命周期停止）。

压缩期间宿主会开一个维护窗口（`reason: 'compaction'`，客户端显示成「压缩结束后发送」）：
用户这几秒按下的发送留在输入框上方的排队行里（可见、可撤回），窗口结束由客户端补发。
插件在窗口关闭后再等一下、确认用户没接手，才发「继续」。

### 会话重开与进程重启

不需要重启会话：一轮结束不等于会话结束，app-server 进程常驻，压缩改的是会话文件，宿主随后
广播 `historyReplaced`，页面直接换成压缩后的记录，下一轮原地继续。

进程真的退出了（关会话 / 退出应用）也没关系：流程阶段记在 `ctx.sessionState`（随会话快照
落盘、resume 带得回来）。落在 `compact` 阶段的会在下次打开会话时接着压；落在 `handoff` /
`resume` / `resuming` 的说明那一轮消息已经随旧进程丢了，setup 时退回 `idle`，下一轮重新判断。

## 快速压缩只动工具过程

压缩区里的工具调用与结果合成**一条占位调用 + 一条结果**：调用名是其中出现最多的那个，
说明形如 `[Mica compact] Placeholder for 42 collapsed tool calls (not a real result): read_file × 18, bash × 12…`，
思考（Responses 的 reasoning 条目、Chat 的 `reasoning_content`）丢掉，图片与文档块换成占位
文本。用户与助手的正文原样保留、顺序不变，也不合并轮次。

代价是这一区的工具时序只剩计数，不能再逐条重放：要细节就重新读文件、重跑命令。连续点几次
是幂等的——新计数会并进同一条说明；没有可清理的内容时返回「没有可清理的工具结果」。

## 模型压缩只把对话交给模型

摘要请求里只有用户说的是什么、助手答了什么（以及上一次压缩留下的 checkpoint 摘要）。
工具调用、工具结果、思考过程都不进摘要输入：它们占九成篇幅，却几乎不进摘要结论。
内核的 `CompactionService` 用 `summaryInput: 'dialogue'` 生成这份正文，分段、预算与截断
仍归它管。

摘要请求走清单里的 `llm`：默认复用当前会话模型，也可以在插件设置里换成更便宜的接口
（失败会自动降级回会话模型）。自动压缩里的模型压缩同样用它；真没配置时退回宿主的摘要
子代理，不把流水线卡在「先去配一个模型」上。

## 什么时候用哪个

- 任务跑了一大段、上下文里堆着几十万 token 的工具输出，但对话本身还有用：**快速压缩**。
- 上下文已经被旧任务塞满、想把它收成一段能接得上的摘要：**模型压缩**。
- 想立刻验证一遍自动流水线，或者主动给任务做一次「换人交接」：**交接并压缩**。
- 模型压缩不按消息条数判断：只有一轮但请求/回复很长时也会尝试摘要，并原样保留最新用户请求；短历史或预计压缩后不会节省上下文时才跳过。

## 实现要点

- 菜单项来自清单（`desktop.sessionMenu`），处理器来自 `ctx.desktop.sessionMenu()`：
  右键要立刻画出菜单，不能为了知道有没有菜单项去冷启动一个 app-server。三项各自
  声明了图标（`eraser` / `sparkles` / `notebook-pen`）：共用插件图标时，菜单上分不出哪一行
  是哪件事；也都写了 `surface: "chat"`，只出现在主会话区的右键菜单里。
- 自动压缩的策略（阈值、窗口上限、闸门、两条消息的正文）在 `autoCompact.ts`，是不碰宿主
  的纯函数；接线（hooks / 后台 tick / 落盘）在 `index.ts`。
- 交接/继续两条消息都以固定标记开头（`［Mica 自动压缩］` / `［Mica 自动压缩·继续］`），
  `turn:before` / `turn:after` 靠「来源是插件 + 带标记」认出自己发出的一轮，不必把整段
  正文存进会话状态。
- 会话正忙（这一轮在跑、另一个进程持有 turn lease）时宿主返回 `busy`，插件提示
  「等这一轮结束再压」，不会排队、更不会插进正在跑的请求。
- 菜单动作只有一句 `message` 能回给用户，所以失败也折成一句话（「模型压缩失败：…」），
  不抛异常——抛出去页面只会显示一句更含糊的错误。
- 轮前的自动快速压缩没有菜单可以回话：压掉了多少与跳过的原因（没有可清理的工具过程）
  写进插件日志 `compact.turn-prepare`；真的失败（例如压缩结果没能写进会话文件）时先
  退回压缩前的历史，再在对话里留一条 warning notice 说明原因，这一轮照常发送——
  不能让一次压缩失败悄悄变成「切了模型却什么都没发生」。
- 压缩结果写不进会话文件就是失败，不报「完成」：内存与磁盘一旦分叉，下一轮对齐磁盘时
  会把压缩结果丢掉，用户看到的是「压了又回去」。

## 操作观察

菜单保留原中文 message，并附固定 outcome/code：busy、空内容 skipped、未配置 declined、取消 cancelled、真正失败 error 与 applied success 分开。宿主能力使用 dependency:host 健康，不清摘要模型或业务故障。

自动流水线每一步都有固定事件，排查时按顺序看：

| 事件                          | 含义                                                       |
| ----------------------------- | ---------------------------------------------------------- |
| `compact.auto-handoff`        | 交接请求发出去了（带用量、阈值、是否进了排队槽）            |
| `compact.auto-skip`           | 这一轮没触发（排队槽被占、冷却、还没有新用量、连续失败…）    |
| `compact.auto-handoff-failed` | 交接请求没发出去（busy / 宿主没有提交入口）                 |
| `compact.auto-applied`        | 压缩完成（前后估算、做了快速/模型哪几步）                   |
| `compact.auto-failed`         | 某一步失败；到第 3 次会停下来                               |
| `compact.auto-resume`         | 「继续」发出去了；`compact.auto-resume-failed` 是没发出去   |
| `compact.auto-user-intervened`| 用户中途插话：压缩照做，但不再自动继续                      |
| `compact.auto-handover-file-failed` | 交接文档另存失败（不影响压缩）                        |

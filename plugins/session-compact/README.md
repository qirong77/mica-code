# 会话压缩

会话右键菜单里的两条手动入口。**不点就不发生任何事**：没有阈值、次数，也没有自动触发。

| 菜单项   | 做什么                                                                         | 代价            |
| -------- | ------------------------------------------------------------------------------ | --------------- |
| 快速压缩 | 只把历史里的工具结果换成占位符（`[Old tool result content cleared during compact]`） | 本地操作，毫秒级 |
| 模型压缩 | 把用户与助手的对话交给模型写一段 checkpoint 摘要，旧历史折成摘要加最近几轮         | 一次模型请求    |

两条改的都是会话**已经落盘的那份历史**（`ctx.agent.compactIdleHistory`），所以压完重开
这条会话，看到的也是压缩后的样子；紧接着发出的请求直接按压小的历史发送。

## 快速压缩只动工具结果

用户与助手的正文、工具调用的参数、图片与 reasoning 条目一概不动，也不合并轮次——历史条数
不变，压完还能原样重放这次对话。连续点几次，第二次就没有可换的了，返回「没有可清理的工具结果」。
它只清掉历史里最占地方、又最没有复用价值的那部分：工具输出。

## 模型压缩只把对话交给模型

摘要请求里只有用户说的是什么、助手答了什么（以及上一次压缩留下的 checkpoint 摘要）。
工具调用、工具结果、思考过程都不进摘要输入：它们占九成篇幅，却几乎不进摘要结论。
内核的 `CompactionService` 用 `summaryInput: 'dialogue'` 生成这份正文，分段、预算与截断
仍归它管。

摘要请求走清单里的 `llm`：默认复用当前会话模型，也可以在插件设置里换成更便宜的接口
（失败会自动降级回会话模型）。

## 什么时候用哪个

- 任务跑了一大段、上下文里堆着几十万 token 的工具输出，但对话本身还有用：**快速压缩**。
- 上下文已经被旧任务塞满、想把它收成一段能接得上的摘要：**模型压缩**。

## 实现要点

- 菜单项来自清单（`desktop.sessionMenu`），处理器来自 `ctx.desktop.sessionMenu()`：
  右键要立刻画出菜单，不能为了知道有没有菜单项去冷启动一个 app-server。
- 会话正忙（这一轮在跑、另一个进程持有 turn lease）时宿主返回 `busy`，插件提示
  「等这一轮结束再压」，不会排队、更不会插进正在跑的请求。
- 菜单动作只有一句 `message` 能回给用户，所以失败也折成一句话（「模型压缩失败：…」），
  不抛异常——抛出去页面只会显示一句更含糊的错误。
- 没有阈值、计数与空闲提醒：清单里没有 `settings`，除了 `llm` 面板（选摘要模型）之外
  不存任何配置。想在合适的时机压缩，点一下就是了。

# sidecar

一个 sidecar 就是一个**独立的 mica 会话**：自己的上下文、自己的进程、自己的会话文件。
你和它之间是"派活 + 读结果"，不是共享上下文——它看不到你的对话，你也只看到它回传的正文。

**为什么是工具而不是开个终端手敲**：`mica app-server` 给的是结构化事件（正文 delta、
工具调用与结果、轮次终态、用量），一个 `sidecar_status` 就拿到全部进度；而驱动界面要读屏、
点控件，一次观测要几十个回合，界面一改就碎。

## 什么时候派

派出去比留在手里好的情况：

- **会淹没上下文**：跑一遍全量测试、读十几个文件找调用点、遍历一批文件改同样一处；
- **可以并行**：两个方案各自验证一遍、前后端各改一半；
- **需要干净环境**：试一个改动、跑一次会失败的命令，不想污染当前对话的推理链路都行；
- **用户明确要求**："开个子会话去做"、"让另一个会话盯着"。

**不要派**的情况：

- 一两步就能做完的事（派出去的开销比做完还大）；
- 必须和你共用同一份可变状态（同一个文件的连续编辑、同一条调试线索）；
- 结论依赖你刚读到的上下文，而那份上下文写不进一句话（那就先写清楚再派）。

## 一次典型的派活

```text
sidecar_spawn({
  prompt: "在 /repo/api 下跑 bun run test，只跑失败的用例归属哪个模块，把结论按文件列出来。不要改任何代码。",
  title: "跑测试并归类失败",
  cwd: "/repo/api",
  max_turns: 20
})
→ 会话 <id>

sidecar_wait({ session_id: "<id>" })      // 默认等这一轮跑完
→ 状态 + 这一轮的正文 + 工具调用

sidecar_close({ session_id: "<id>" })     // 拿到结论就收掉
```

## 工具

| 工具                 | 做什么                                                            |
| -------------------- | ----------------------------------------------------------------- |
| `sidecar_spawn`      | 开一个子会话并投第一句话，返回会话 id（可只记唯一前缀）           |
| `sidecar_send`       | 追加一句话：它在跑时排到下一迭代边界，空闲时开新一轮              |
| `sidecar_status`     | 看进度：在不在跑、说到哪、调了哪些工具；不带 id 列出全部（只读）  |
| `sidecar_turns`      | 轮次索引：每轮一行（时间/终态/耗时/问答摘要），用来定位「第几轮」 |
| `sidecar_grep`       | 在对话里搜关键词，只回命中那几行（带轮次与说话人）                |
| `sidecar_transcript` | 读对话正文（用户 + 助手，**不含工具与思考**），按字符预算截断     |
| `sidecar_wait`       | 等条件：`idle`（默认）/ `text`（正文匹配）/ `turn`（新一轮结束）  |
| `sidecar_abort`      | 打断当前这一轮，进程与会话都还在                                  |
| `sidecar_close`      | 收掉进程；会话历史仍在会话列表里                                  |

同时最多 **4 个**子会话。跑完就 `sidecar_close`——收掉的不只是进程，还有并发名额。

**它有多贵**：每个子会话是一个完整的 mica 进程（空闲时 RSS ≈ 200 MB，启动 2–3s），
每一轮请求都带着它自己的完整 system prompt 与工具定义（实测约 4 万 input token，
`sidecar_send` 追加的那一句同样如此）。所以「一两步能做完的事」派出去是纯亏：
4 个挂着不关的子会话就是接近 1 GB 常驻内存。

## 怎么读结果

`sidecar_wait` / `sidecar_status` 回的是**投影**：这一轮的正文、工具行（标题 + 状态）、
上一轮结论、用量。原文在子会话自己的对话记录里，需要全文时传 `full: true`。

投影是按「够你决定下一步」裁过的：只留最近一轮、正文截断到几千字符、工具只列最近 8 条
（只有失败的才带输出片段）。所以查进度很便宜——而且自上次查看后没有新输出时，
`sidecar_status` 只回一行。**不要为了保险多查几次**：真没进展时它也只会告诉你没进展。

### 要读对话时，按成本从低到高走

三个读的工具差一个数量级，**不要跳级**：

```text
sidecar_turns({ session_id })                       // 几行：它一共几轮、每轮问了什么答了什么
sidecar_grep({ session_id, pattern: "Cannot find" }) // 几行：这句话在哪一轮说过
sidecar_transcript({ session_id, last_turns: 2 })    // 正文：默认只读最近 1 轮
```

`sidecar_transcript` 的预算按字符算（默认 8000 ≈ 4k token），超了就丢最早的轮次并写明丢了几轮。
要读更多就必须显式传 `last_turns` 与 `max_chars`——默认值不会自己变大。

判断"它到底做成了没有"，看三样，不要只看正文语气：

1. 这一轮的 `status`（`completed` / `failed` / `interrupted`）；
2. 工具行的状态与输出——失败的命令会带 `[error]` 和输出片段；
3. 它自己写的验证结果（跑了什么、输出是什么）。没验证就让它补一次：

```text
sidecar_send({ session_id, text: "把刚才那条命令的实际输出贴出来，并说明改动的文件列表。" })
sidecar_wait({ session_id })
```

## 边界

- **子会话看不到你的对话**。目标、约束、相关路径、验收方式必须写在 `prompt` 里；它不会自己猜你的意图。
- **子会话会污染工作区**。多个 sidecar 同时改同一个仓库等于没人在管：`Implementer` 式的改动一次只派一个，并且 `cwd` 写到具体目录。
- **角色默认跟你一样**：不传 `role` 就继承你当前的会话角色（同一个 agent 换个上下文干活）；要它按另一套规则做事才显式给 `role`。角色名写错不会让子会话起不来，会退化成默认角色并给一条 warning。模型与档位默认沿用当前配置，用 `model` / `effort` 覆盖。
- **它会出现在会话列表**。父会话在侧栏里可折叠展开子会话；会话文件要等第一轮结束才落盘，所以刚 spawn 完还看不到。
- **不要用 `sidecar_send` 轮询进度**。看进度是 `sidecar_status`，等结果是 `sidecar_wait`。
- **最多套两层**（深度由 `MICA_SIDECAR_DEPTH` 记）。子会话里还能再派一个，第三层会被直接拒绝：每层都是完整的 mica 进程（各自加载 MCP 与插件），再深就是指数级的进程树，足以拖死机器。
- **子进程跟着父会话走**：父会话关掉、app 退出、父进程被强杀，它们都会一起收掉。不要指望跨会话复用，也不要试图让它们活过父进程。
- **进程自己退出后条目还在**：`sidecar_status` 会显示 `已退出` 与退出原因，最后一轮仍能读；不再需要时用 `sidecar_close` 清掉，别让它一直挂在列表里。
- **`full: true` 会让投影大好几倍**（正文、工具输出、思考、更早几轮一起给）。只在确实要读
  原文时用一次，别把它当默认值。
- **`cwd` 可以是相对路径或 `~`**：相对路径按当前会话的目录解析，最终一律落成绝对路径。
  目录不存在会直接报错（而不是起一个跑不起来的孩子会话）。
- **投出去的话可能落进当前轮的下一迭代，也可能变成新的一轮**——取决于这一轮还有没有后续迭代。
  `sidecar_turns` 显示的是实际落点，不用自己推断。
  `sidecar_spawn` 的启动握手与第一句话投递会随父调用取消而收掉尚未交付的子进程；
  已经成功返回的子会话继续独立运行。`max_turns` 只能为正整数。
  `sidecar_wait` 取消时立即释放等待资源；`until` 只接受 `idle`、`text`、`turn`，
  非法条件或非正数 `timeout_ms` 会直接说明参数问题。
  父会话切换时已经开始退出的子进程仍由插件追踪，插件卸载会等它们真正退出后再完成。

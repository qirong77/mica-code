# 中转站号池搭建踩坑教程

> 适用于 Mica Mobile Relay：一台公网中转机承载多台本机，每台本机拿到独立访问口令，手机通过对应链接访问对应机器。
>
> 本文只记录搭建和排障经验，不包含真实域名、IP、SSH 地址或口令。

## 1. 先搞清楚“号池”是什么

这里的号池不是一堆可以随便轮换的共享账号，而是中转机上的机器登记表：

```text
手机 -- HTTPS/SSE --> 中转机 -- 出站轮询 --> 本机桥 -- 127.0.0.1 --> Mica runtime
                         |
                         +-- agents.json
                             +-- 机器 A -> 口令 A
                             +-- 机器 B -> 口令 B
                             +-- 机器 C -> 口令 C
```

每台机器有自己的：

- 访问口令和手机链接；
- 在线状态、事件流和结果缓存；
- 本机桥到中转机的加密通道。

因此，机器 A 的链接不会看到机器 B 的会话。重复注册同一台机器会复用原来的记录，不会每点一次就新增一个“号”。

实现上，中转机的清单默认位于 `/var/lib/mobile-relay/agents.json`，本机设置位于 `$MICA_HOME/plugin-settings/mobile-relay.json`。

## 2. 推荐搭建顺序

### 2.1 首次部署：只做一次

准备一台公网 Linux 中转机，建议至少具备：

- Node.js 18 或更高版本；
- nginx；
- certbot；
- 可用的 SSH 登录；
- 80/443 端口能从公网访问。

本机先构建页面产物：

```bash
cd apps/desktop
npm install
npx electron-vite build
cd ../..
```

然后从仓库根目录执行首次部署：

```bash
node plugins/mobile-relay/setup.mjs --host root@<公网IP>
```

已有域名时显式指定：

```bash
node plugins/mobile-relay/setup.mjs \
  --host root@<公网IP> \
  --domain mica.example.com
```

SSH 不是 22 端口时要同时传 `--ssh-port`：

```bash
node plugins/mobile-relay/setup.mjs \
  --host root@<公网IP> \
  --ssh-port 2222
```

没有域名时，脚本可以按公网 IP 使用 `sslip.io` 并申请 Let's Encrypt 证书。不要把 `--no-cert` 当成正式方案，它只适合内网调试。

### 2.2 第二台及之后的本机：只注册，不重部署

中转机已经运行后，新机器不要重新上传页面、重配 nginx、重签证书。推荐在插件设置里：

1. 填中转地址，例如 `https://<你的中转机>`；
2. 点击“注册到中转机”；
3. 使用返回的本机链接。

如果必须命令行代办，可以运行：

```bash
node plugins/mobile-relay/setup.mjs \
  --host root@<同一台中转机> \
  --ssh-port 2222
```

脚本检测到 relay 已经运行后，会进入 join 模式：只更新 `agents.json`，不传页面、不重启服务、不动 nginx。这样不会把已经在线的手机连接打断。

### 2.3 Mica 升级后：只同步页面

页面旧了，不要用完整重部署。使用：

```text
mobile_relay action=sync_page
```

或者从插件面板点击“更新中转机页面”。它只比较页面版本，不一致才上传，并在中转机上原子替换 `public/`。

注意：同步页面不会更新 `relay.mjs`、本机桥脚本、systemd 或 nginx 配置。

## 3. 最容易踩的坑

### 坑 1：把“新增机器”做成了“重新部署中转机”

**症状：** 新机器接入时手机短暂断开、页面被重新上传、证书流程再次执行。

**原因：** 把首次部署命令当成每台机器的入池命令使用，或手动加了 `--redeploy`。

**正确做法：**

- 首次部署才用完整部署；
- 后续机器只走“注册到中转机”；
- 只有 relay 服务本身需要升级时，才考虑 `--redeploy`。

### 坑 2：口令不是自己编的，也不要手抄来回传

**症状：** 手机能打开登录页，但 API 返回 401；桥日志出现“口令不匹配”。

**原因：** 口令同时参与路由和 AES-GCM 通道密钥派生。随便编一个值、复制错一位、把另一台机器的口令填过来，都会指向错误的机器或直接鉴权失败。

**正确做法：** 通过插件“注册到中转机”拿口令，让插件自动写入设置。手机链接使用：

```text
https://<域名>/?t=<对应机器的口令>
```

不要把真实口令写进 Git、截图、工单或公共日志。口令泄露时，应在中转机清理/重建对应机器登记，并重新注册。

### 坑 3：只同步页面，却期待新 relay 功能生效

**症状：** 页面看起来是新版，但附件、事件批次去重、wake 通知等功能仍异常。

**原因：** 页面、桥、中转机服务和 nginx 是不同的发布物。`sync_page` 只更新 renderer 静态文件，不会更新服务端协议。

**正确做法：** 协议或服务有变化时，至少一起升级：

- 本机桥；
- 中转机 `relay.mjs`；
- nginx 上传限制；
- 页面产物。

否则就会出现“界面版本新、传输链路旧”的半升级状态。

### 坑 4：用自签证书验证完，直接拿给手机用

**症状：** `curl` 可能能通，但手机浏览器白屏、拒绝建立安全连接，或桥严格校验证书失败。

**原因：** 手机不信任自签证书；桥默认也严格校验证书链。

**正确做法：** 正式环境使用真实域名或 `sslip.io` + Let's Encrypt。Cloudflare 代理场景把 DNS 设为 **DNS only（灰云）**，让 certbot 能直接验证源站。

`--no-cert` 只用于内网链路调试，不要作为生产配置。

### 坑 5：域名解析和 80 端口没准备好，certbot 必然失败

**症状：** certbot 超时、验证失败，或证书签发成功但手机访问的域名不是这台机器。

**先检查：**

```bash
# 在本机检查解析结果
nslookup <域名>

# 在外部网络检查 HTTP 入口
curl -I http://<域名>
```

确认 A/AAAA 记录指向中转机，安全组和防火墙放行 80/443。域名刚改过时，先等待 DNS 生效再重试。

### 坑 6：nginx 默认配置吞掉流式输出

中转链路依赖长轮询、SSE 和即时推送。nginx 至少要保留这些关键配置：

```nginx
proxy_http_version 1.1;
proxy_set_header Connection "";
proxy_buffering off;
proxy_cache off;
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
gzip off;
```

否则常见表现是：消息不是不来，而是攒成一坨很久才到；终端回显延迟明显；长连接被 nginx 提前断开。

附件和页面发布还需要匹配的 `client_max_body_size`。当前模板按 24 MB 配置，存量服务器如果只改了页面而没更新 nginx，附件仍可能返回 413。

### 坑 7：小内存 VPS 被 apt 或 journald 拖成“假死”

464 MB 左右的小 VPS 最危险的不是 relay 自己崩溃，而是整机 OOM：SSH 可能能收到 SYN，但不出登录 banner，HTTPS 握手也超时。

建议部署前做三件事：

1. 配置至少 512 MB swap，并写入 `/etc/fstab`；
2. 给 journald 设置磁盘上限，例如 `SystemMaxUse=80M`；
3. 给 apt 的定时升级服务设置内存上限和较高 `OOMScoreAdjust`，避免一次升级拖垮 relay/SSH。

排查时优先看：

```bash
dmesg | grep -i oom-kill
journalctl -u mobile-relay -n 100 --no-pager
systemctl status mobile-relay --no-pager
```

不要只盯着 `relay.mjs` 的日志；如果是全局 OOM，服务日志往往看不出根因。

### 坑 8：把“中转机在线”误判成“本机已接入”

不带口令访问 `/api/health` 只能证明中转机活着；带对应口令才是在检查某台机器：

```bash
curl -sS "https://<域名>/api/health?t=<对应机器的口令>"
```

重点看：

- `agentOnline`：本机桥是否在线；
- `phoneOnline`：手机页面是否正在访问；
- `label`：是否命中了正确的机器；
- `pageVersion`：中转机页面是否落后。

多机器场景下，显式带错 `t` 不应回退到浏览器记住的另一台机器。否则会出现“看起来能打开，但其实打开的是另一台本机”的误判。

### 坑 9：最后一个桌面会话关掉后，手机自然也断了

桥由桌面端插件宿主监管，不是独立的系统常驻服务。关闭最后一个 Mica 会话页签后，桥会停止；重新打开会话后通常 1–3 秒恢复，手机页面会自动重试。

如果需要真正脱离桌面会话长期运行，当前实现没有提供这一形态，不要把它误当成服务器端常驻 agent。

### 坑 10：把 `app.asar` 里的页面当成部署源

打包版 Electron 的页面在 `app.asar` / `app.asar.unpacked` 内，不能把“能运行”误认为“适合拿来部署”。部署脚本优先找仓库里的：

```text
apps/desktop/out/renderer
```

找不到就先构建，或用 `--renderer <dir>` 明确指定一个包含 `index.html` 的产物目录。页面资源和服务代码的来源要可追溯，避免手工从安装包抠出一份不可复现的页面。

## 4. 一套最短排查顺序

遇到“手机打不开 / 没会话 / 机器离线”时，按下面顺序，不要一上来重部署：

### 第一步：确认本机 runtime

```bash
curl -sS -o /dev/null -w '%{http_code}\n' \
  http://127.0.0.1:8787/api/health
```

应返回 `200`。本机桌面端没跑时，中转机就算在线也没有会话可看。

### 第二步：确认中转机服务

```bash
systemctl is-active mobile-relay
journalctl -u mobile-relay -n 100 --no-pager
```

服务没有 active，先修 Node、权限、端口或 OOM，不要反复注册机器。

### 第三步：确认 nginx/TLS

```bash
nginx -t
curl -I https://<域名>
```

重点排查证书、域名解析、80/443 防火墙和反向代理超时。

### 第四步：带正确口令检查具体机器

```bash
curl -sS "https://<域名>/api/health?t=<对应机器的口令>"
```

看 `label` 和 `agentOnline` 是否属于预期机器。

### 第五步：再查本机桥

使用插件提供的诊断入口：

```text
mobile_relay action=doctor
```

重点确认：中转地址、口令、桥进程、TLS 校验、本机 runtime。

### 第六步：最后才判断版本问题

- 页面旧：执行 `mobile_relay action=sync_page`；
- relay/桥协议变更：完整升级服务和桥；
- 附件返回 413：检查 nginx 的 `client_max_body_size`；
- 事件延迟：先查 nginx `proxy_buffering` 和长连接配置。

## 5. 手机认证转成本地副本认证

手机端登录成功，只说明手机拿到了中转机访问权限，不代表本机已经拥有同一份认证状态。需要让本机独立使用时，应把认证结果落成本机副本，而不是长期依赖手机在线转发。

建议流程：

1. 在手机端完成登录或授权，确认账号可正常使用；
2. 通过项目提供的导出/同步入口，把认证信息写入本机对应的配置目录；
3. 在本机重新启动相关 provider 或会话，确认请求不再依赖手机；
4. 用一条最小请求验证本地副本有效，再关闭手机页面测试独立运行。

注意：

- 中转机口令、手机访问链接和 provider 登录凭据是三种不同的认证信息，不要混用；
- 不要直接把 cookie、refresh token 或完整认证文件粘贴到聊天、Git 或日志里；
- 本地副本过期后应重新走授权流程，不要手工修改过期时间或复制另一台机器的凭据；
- 多台本机要分别生成自己的认证副本，避免多个实例同时刷新同一个 token，导致互相登出；
- 验证时先关掉手机端连接。如果本机仍能完成请求，才算真正完成了“手机认证 → 本地副本认证”。

## 6. 上线前检查清单

- [ ] 中转机 Node >= 18、nginx、certbot 都可用。
- [ ] DNS 已指向中转机，公网 80/443 已放行。
- [ ] 正式环境使用可信 HTTPS，不使用 `--no-cert`。
- [ ] 首次部署已成功，`mobile-relay` 为 active。
- [ ] 本机 `127.0.0.1:8787/api/health` 返回 200。
- [ ] 每台机器都通过注册流程获取自己的口令。
- [ ] 每台机器用自己的 `?t=` 链接验证，`label` 和 `agentOnline` 正确。
- [ ] 新增机器没有误用 `--redeploy`。
- [ ] Mica 升级后区分“同步页面”和“升级 relay 服务”。
- [ ] nginx 关闭代理缓冲，并设置正确的长连接超时和上传上限。
- [ ] 小内存 VPS 已配置 swap、journald 上限和 OOM 保护。
- [ ] 没有把口令提交到仓库、日志或截图。

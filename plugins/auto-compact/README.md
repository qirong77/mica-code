# Auto Compact

一次模型请求跑完就检查上下文占用，超过阈值时在「这次请求结束、下一次请求发出」的间隙把历史压小，
不等整个任务结束。

## 为什么在插件里

压缩策略是**产品决策**，不是协议的一部分：阈值多少、压几次、要不要花一次模型请求做摘要，
不同部署会给出不同答案。放在插件里之后，内核只保留「怎么压」的原语（`agent.compact()`），
「什么时候压」完全由插件决定。会话级覆盖也不再是宿主里的一列字段：它按清单声明生成，任何
插件把设置项标成 `perSession` 都能用同一套界面与协议。

## 三条路径

| 路径 | 触发                                    | 做什么                                         |
| ---- | --------------------------------------- | ---------------------------------------------- |
| 快速 | 上下文 ≥ 快速压缩阈值，次数没用完       | 本地把工具结果、工具参数正文、媒体块换成占位符 |
| 模型 | 本地清理后仍 ≥ 模型压缩阈值，次数没用完 | 调模型生成 checkpoint 摘要                     |
| 空闲 | 会话空闲 ≥ 空闲阈值，用户又在输入框敲字 | 在轮次之外先做一次快速压缩并落盘               |

模型阈值（默认 200k）低于快速阈值（默认 300k）：本地能清掉的优先本地清，清不干净才花钱。
同一次触发里的「快速 → 模型」升级算一次。最小间隔只约束**同一轮运行中**的重复压缩：
模型还在为这一轮反复请求、上下文又长回阈值时才等一会儿；上一轮压过不会拖住新一轮——
用户发来下一句、上下文已经超阈值时，插件必须立刻动手。

模型那一路的摘要请求走清单声明的 `llm`（「压缩摘要模型」面板）：**默认复用当前会话模型**，
也可以单独填接口地址 / Key / 协议 / 模型（例如换一个更便宜的小模型）；填了自己的接口而请求
失败时会自动降级回会话模型。分段、预算与重试仍由内核的 `CompactionService` 负责，插件只换
「由谁来写这段摘要」。

「空闲」这条不走阈值：它判断的是**人回来了**，不是上下文变大了。桌面端在用户敲字时发
`mica/input/activity`，宿主把它翻成运行期事件 `input:activity`；插件据此决定要不要趁这个间隙
把**已经落盘的**历史压小（`ctx.agent.compactIdleHistory()`，走同一个 `CompactionService`，
不调用模型）。用户的下一轮请求因此直接按压小的历史发出，而不是等请求上路了才压。

它同样消耗「快速压缩次数」，但**不看**「同一轮内的压缩间隔」、「不看上下文阈值」：那个间隔
是为同一段上下文被反复按阈值压准备的，而这里判断的是「人回来了」——刚压过一次就离开再回来，
这期间历史又长大了，压一次才有意义；套上间隔会让最常见的场景（工作密集、一会儿压一会儿走）
静默失效。没有新内容时宿主直接回「没得压」，本来也不会白写一次盘。

宿主回 `skipped` 时不消耗次数、也不报错，但把原因分开记（`busy`：会话正忙 / 另一个进程持着
turn lease；`empty`：没有可清理的内容）——这两件事在日志里必须能分清，否则「没生效」只能靠猜。
压成之后在对话里留一行 notice，写成压缩前后的对比而不是一个孤零零的节省量
（`空闲 22 分钟后重新输入，已快速压缩历史：792K → 46K（省 94%）`，k/M 换算走 `mica-common` 的 `formatTokenCount`），
并把计数与这条 notice 与压缩结果**同一次写进会话文件**（`afterApply` 在落盘之前调用），
同时发 `mica/sessionHistory/replaced` 让桌面端立刻重载记录。

只有能独占写会话文件的常驻宿主提供这条通路：`mica exec` 不落盘，TUI 由 `/compact` 负责，
两边都不发这条事件。

「焦点」这条比它更早一步：用户**把焦点放回输入框**（还没敲字）、且这一轮没在跑时，桌面端发
`mica/input/focus`，宿主翻成运行期事件 `input:focus`。人已经坐在输入框前，下一步就是按发送，
这是最后一个能白捡的间隙——等第一个按键再压，压缩与这次请求已经撞在一起了。它不看空闲多久
（刚聊完也可能马上接着说），看的是「上一次轮次之外压缩之后有没有跑过新一轮」：`turn:before`
把 `turnCount` 加一，压缩时把这个值记进 `compactedTurnCount`，两者相等就说明那段历史已经压过，
点进点出输入框不会让宿主反复全量扫一遍大会话。notice 写的是
`回到输入框，已快速压缩历史：792K → 46K（省 94%）`。

两条「抢跑」（焦点与空闲回来）都再加一道前提：**上下文已经到快速压缩阈值**
（`reachesQuickThreshold`：`ctx.agent.lastUsage().inputTokens` 对比 `effectiveThresholds().quick`）。
低于阈值时，这次压缩在请求里本来也不会发生——那就不是「提前」，只是把几十 MB 的历史白扫一遍、
再往对话里写一条 notice。真实反馈是：一个 100K 上下的会话来回切几次焦点，对话里排出一列
「已快速压缩」，而用户全程没说话。

**对话里只留一行状态**：自动压缩的 notice 全部带 `command: 'auto-compact'` 与 `replace: true`
（见 `plugins/README.md` 的「notice 槽」），同一个 command 只保留最新一条——几小时里各跑一次的
空闲 / 焦点压缩不会在对话里堆成一列。轮次边界的**本地清理不写 notice**：它一轮里可能发生几十次，
不改用户看到的对话（工具结果本来显示的就是一行摘要），提示只留给真正改写历史的模型摘要。

压缩是同步的：它跑着的时候宿主读不到 stdin 上的下一条 `turn/start`，用户这几秒发的消息只会
静静排在管道里，界面上一点反馈都没有。所以宿主动手之前先发一条
`mica/host/maintenance`（`active: true`），压缩收尾再发 `active: false`；桌面端据此把这
段时间的发送放进本地队列——界面上一共一条排队中的消息（提示写的是「等自动压缩结束」，可以
撤回、可以双击改字），压缩一结束就自动补发。别的排队条目（中止后留给用户撤回的）不在这条
通路里，不会顺手被发出去。

## 计数在哪

存在**会话快照的插件状态**里，不在宿主的全局表里。一条会话压过几次是它自己的事实，
resume / fork / rewind 都跟着走；换台设备打开同一会话也不会从零开始。

## 配置

配置页 Plugins → Auto Compact。默认值写在 `plugin.json`，用户改过的值存
`$MICA_HOME/plugin-settings/auto-compact.json`，改完立刻生效（读设置带 mtime 缓存）。

每一项都标了 `perSession`，因此还能**按会话覆盖**：桌面端「会话设置 → 插件」里改的项只作用于
当前会话，只存改过的键，其余继续跟随默认值；点「跟随默认」即退回继承。

| 项                 | 默认    | 说明                                                     |
| ------------------ | ------- | -------------------------------------------------------- |
| 启用               | 开      | 关掉之后只在手动 `/compact` 时压缩                       |
| 快速压缩阈值       | 300k    | 超过就先做本地清理                                       |
| 快速压缩次数       | 999     | `0` 表示不做这一类                                       |
| 模型压缩阈值       | 200k    | 本地清理后仍超过才花一次模型请求                         |
| 模型压缩次数       | 999     | `0` 表示不做这一类                                       |
| 最小间隔           | 30 分钟 | 只管同一轮里的重复压缩；`0` 表示不限制                   |
| 空闲后输入触发压缩 | 15 分钟 | 不看同一轮间隔；仍要求上下文到快速压缩阈值，`0` 表示关掉 |

「压缩摘要模型」是清单 `llm` 声明生成的一组字段（`useMainProvider` / `baseUrl` / `apiKey` /
`protocol` / `model`），见 `plugins/README.md` 的「模型接口」一节；它同样按会话可覆盖。

## 边界

- `mica exec` 这类一次性运行不压缩：没有第二轮，改历史只会改变这一次的开销与结果。
- 压缩失败（没有可清理内容、次数用尽）不中断 turn、不消耗次数，写插件日志与健康状态。
- 请求前压缩只改发给模型的历史，不改 `conversationMessages`；空闲压缩会同时落盘（工具结果
  在界面上本来就是一行摘要，占位符不改变用户看到的内容），因此它在对话里留的那行 notice
  会跟着会话保存，resume 之后还在。

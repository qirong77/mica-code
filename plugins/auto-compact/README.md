# Auto Compact

一次模型请求跑完就检查上下文占用，超过阈值时在「这次请求结束、下一次请求发出」的间隙把历史压小，
不等整个任务结束。

## 为什么在插件里

压缩策略是**产品决策**，不是协议的一部分：阈值多少、压几次、要不要花一次模型请求做摘要，
不同部署会给出不同答案。放在插件里之后，内核只保留「怎么压」的原语（`agent.compact()`），
「什么时候压」完全由插件决定。会话级覆盖也不再是宿主里的一列字段：它按清单声明生成，任何
插件把设置项标成 `perSession` 都能用同一套界面与协议。

## 三条路径

| 路径 | 触发                                    | 做什么                                         |
| ---- | --------------------------------------- | ---------------------------------------------- |
| 快速 | 上下文 ≥ 快速压缩阈值，次数没用完       | 本地把工具结果、工具参数正文、媒体块换成占位符 |
| 模型 | 本地清理后仍 ≥ 模型压缩阈值，次数没用完 | 调模型生成 checkpoint 摘要                     |
| 空闲 | 会话空闲 ≥ 空闲阈值，用户又在输入框敲字 | 在轮次之外先做一次快速压缩并落盘               |

模型阈值（默认 200k）低于快速阈值（默认 300k）：本地能清掉的优先本地清，清不干净才花钱。
同一次触发里的「快速 → 模型」升级算一次，节流只看两次触发之间。

「空闲」这条不走阈值：它判断的是**人回来了**，不是上下文变大了。桌面端在用户敲字时发
`mica/input/activity`，宿主把它翻成运行期事件 `input:activity`；插件据此决定要不要趁这个间隙
把**已经落盘的**历史压小（`ctx.agent.compactIdleHistory()`，走同一个 `CompactionService`，
不调用模型）。用户的下一轮请求因此直接按压小的历史发出，而不是等请求上路了才压。

它同样消耗「快速压缩次数」，但**不看**「两次压缩的最小间隔」、「不看上下文阈值」：那个间隔
是为同一段上下文被反复按阈值压准备的，而这里判断的是「人回来了」——刚压过一次就离开再回来，
这期间历史又长大了，压一次才有意义；套上间隔会让最常见的场景（工作密集、一会儿压一会儿走）
静默失效。没有新内容时宿主直接回「没得压」，本来也不会白写一次盘。

宿主回 `skipped` 时不消耗次数、也不报错，但把原因分开记（`busy`：会话正忙 / 另一个进程持着
turn lease；`empty`：没有可清理的内容）——这两件事在日志里必须能分清，否则「没生效」只能靠猜。
压成之后在对话里留一行 notice（`空闲 22 分钟后重新输入，已快速压缩历史（约省下 45120 tokens）`），
并把计数与这条 notice 与压缩结果**同一次写进会话文件**（`afterApply` 在落盘之前调用），
同时发 `mica/sessionHistory/replaced` 让桌面端立刻重载记录。

只有能独占写会话文件的常驻宿主提供这条通路：`mica exec` 不落盘，TUI 由 `/compact` 负责，
两边都不发这条事件。

## 计数在哪

存在**会话快照的插件状态**里，不在宿主的全局表里。一条会话压过几次是它自己的事实，
resume / fork / rewind 都跟着走；换台设备打开同一会话也不会从零开始。

## 配置

配置页 Plugins → Auto Compact。默认值写在 `plugin.json`，用户改过的值存
`$MICA_HOME/plugin-settings/auto-compact.json`，改完立刻生效（读设置带 mtime 缓存）。

每一项都标了 `perSession`，因此还能**按会话覆盖**：桌面端「会话设置 → 插件」里改的项只作用于
当前会话，只存改过的键，其余继续跟随默认值；点「跟随默认」即退回继承。

| 项                 | 默认    | 说明                                 |
| ------------------ | ------- | ------------------------------------ |
| 启用               | 开      | 关掉之后只在手动 `/compact` 时压缩   |
| 快速压缩阈值       | 300k    | 超过就先做本地清理                   |
| 快速压缩次数       | 999     | `0` 表示不做这一类                   |
| 模型压缩阈值       | 200k    | 本地清理后仍超过才花一次模型请求     |
| 模型压缩次数       | 999     | `0` 表示不做这一类                   |
| 最小间隔           | 30 分钟 | 只管按阈值的触发；`0` 表示不限制     |
| 空闲后输入触发压缩 | 15 分钟 | 不看阈值与间隔；`0` 表示关掉这个触发 |

## 边界

- `mica exec` 这类一次性运行不压缩：没有第二轮，改历史只会改变这一次的开销与结果。
- 压缩失败（没有可清理内容、次数用尽）不中断 turn、不消耗次数，写插件日志与健康状态。
- 请求前压缩只改发给模型的历史，不改 `conversationMessages`；空闲压缩会同时落盘（工具结果
  在界面上本来就是一行摘要，占位符不改变用户看到的内容），因此它在对话里留的那行 notice
  会跟着会话保存，resume 之后还在。

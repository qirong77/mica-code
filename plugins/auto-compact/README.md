# Auto Compact

一次模型请求跑完就检查上下文占用，超过阈值时在「这次请求结束、下一次请求发出」的间隙把历史压小，
不等整个任务结束。

## 为什么在插件里

压缩策略是**产品决策**，不是协议的一部分：阈值多少、压几次、要不要花一次模型请求做摘要，
不同部署会给出不同答案。放在插件里之后，内核只保留「怎么压」的原语（`agent.compact()`），
「什么时候压」完全由插件决定。会话级覆盖也不再是宿主里的一列字段：它按清单声明生成，任何
插件把设置项标成 `perSession` 都能用同一套界面与协议。

## 两条路径

| 路径 | 触发                                    | 做什么                                         |
| ---- | --------------------------------------- | ---------------------------------------------- |
| 快速 | 上下文 ≥ 快速压缩阈值，次数没用完       | 本地把工具结果、工具参数正文、媒体块换成占位符 |
| 模型 | 本地清理后仍 ≥ 模型压缩阈值，次数没用完 | 调模型生成 checkpoint 摘要                     |

模型阈值（默认 200k）低于快速阈值（默认 300k）：本地能清掉的优先本地清，清不干净才花钱。
同一次触发里的「快速 → 模型」升级算一次。最小间隔只约束**同一轮运行中**的重复压缩：
模型还在为这一轮反复请求、上下文又长回阈值时才等一会儿；上一轮压过不会拖住新一轮——
用户发来下一句、上下文已经超阈值时，插件必须立刻动手。

模型那一路的摘要请求走清单声明的 `llm`（「压缩摘要模型」面板）：**默认复用当前会话模型**，
也可以单独填接口地址 / Key / 协议 / 模型（例如换一个更便宜的小模型）；填了自己的接口而请求
失败时会自动降级回会话模型。分段、预算与重试仍由内核的 `CompactionService` 负责，插件只换
「由谁来写这段摘要」。

## 轮次之内动手，轮次之外只问一句

轮次之外（会话空闲、焦点回到输入框）**不压**。桌面端仍会发 `mica/input/activity` 与
`mica/input/focus`，宿主把它们翻成 `input:activity` / `input:focus` 运行期事件，但自动压缩
不订阅它们：一条会话该不该压，只看「这次请求即将发送的历史有多大」。

在用户按下发送之前抢先压一遍存下来的历史，试过，代价大于收益：

- 上下文远未到阈值时它白扫几十 MB 历史——压不出东西、不写盘也不计次，但真实反馈是用户
  来回切几次焦点，对话里就排出一列「已快速压缩」，而全程没说话；
- 阈值之上时它会把工具结果换成占位符并立刻落盘，等于替用户决定了「这段历史从这一刻起
  不再完整」，而用户可能只是想再翻一眼。

轮次之外唯一主动做的事是**问一句**：会话放久了（距离上一次请求超过「空闲多久后提醒」，默认
一小时）或者上下文快顶到窗口（默认 ≥ 窗口的 80%），就在输入框上方挂一张卡片——
「已经 1 小时没有请求，缓存大概率已失效」「上下文已经 480k，快到窗口上限了」。

这张卡片是**非阻塞**的（`ctx.ask.post()`，宿主标成 passive）：

- 不点就什么都不发生，卡片挂到超时自己消失，用户可以照常打字、发送；
- 用户一发下一条消息，卡片立刻撤掉——那时它已经没有意义；
- 走的是同一块提问位置，别的插件正在问（或工具正等用户选）时让开，攒到下一个空闲窗口；
- 一次空闲窗口只问一次：答完「先不压」也不会反复弹，直到用户又发了一轮新请求；
- 一轮正在跑时不问：那时轮内压缩本来就在按阈值动手。

点「现在压缩」做的是**本地清理**（`agent.compactIdleHistory()`：把旧工具结果换成占位符），
不调用模型、不改对话文本。它仍然不是自动的：改历史这件事由用户点一下。

手动触发照旧，两条路与自动压缩共用同一份 `CompactionService`：

| 入口                         | 做什么                          |
| ---------------------------- | ------------------------------- |
| 命令面板「快速压缩（本地）」 | 本地清理，不调用模型、不丢轮次  |
| `/compact`（桌面同理）       | 本地清理                        |
| `/compact llm`               | 模型摘要 checkpoint，会重写历史 |

自动压缩的全部 notice 都带 `command: 'auto-compact'` 与 `replace: true`（见
`plugins/README.md` 的「notice 槽」），同一个 command 只保留最新一条。轮次边界的**本地清理
不写 notice**：它一轮里可能发生几十次，不改用户看到的对话（工具结果本来显示的就是一行摘要），
提示只留给真正改写历史的模型摘要。

压缩是同步的：它跑着的时候宿主读不到 stdin 上的下一条 `turn/start`，用户这几秒发的消息只会
静静排在管道里，界面上一点反馈都没有。所以宿主动手之前先发一条
`mica/host/maintenance`（`active: true`），压缩收尾再发 `active: false`；桌面端据此把这
段时间的发送放进本地队列——界面上一共一条排队中的消息（提示写的是「等自动压缩结束」，可以
撤回、可以双击改字），压缩一结束就自动补发。别的排队条目（中止后留给用户撤回的）不在这条
通路里，不会顺手被发出去。

## 计数在哪

存在**会话快照的插件状态**里，不在宿主的全局表里。一条会话压过几次是它自己的事实，
resume / fork / rewind 都跟着走；换台设备打开同一会话也不会从零开始。

## 配置

配置页 Plugins → Auto Compact。默认值写在 `plugin.json`，用户改过的值存
`$MICA_HOME/plugin-settings/auto-compact.json`，改完立刻生效（读设置带 mtime 缓存）。

每一项都标了 `perSession`，因此还能**按会话覆盖**：桌面端「会话设置 → 插件」里改的项只作用于
当前会话，只存改过的键，其余继续跟随默认值；点「跟随默认」即退回继承。

| 项           | 默认    | 说明                                   |
| ------------ | ------- | -------------------------------------- |
| 启用         | 开      | 关掉之后只在手动 `/compact` 时压缩     |
| 快速压缩阈值 | 300k    | 超过就先做本地清理                     |
| 快速压缩次数 | 999     | `0` 表示不做这一类                     |
| 模型压缩阈值 | 200k    | 本地清理后仍超过才花一次模型请求       |
| 模型压缩次数 | 999     | `0` 表示不做这一类                     |
| 最小间隔     | 30 分钟 | 只管同一轮里的重复压缩；`0` 表示不限制 |
| 空闲与过大的压缩提醒 | 开 | 关掉之后不再问「要不要压缩」，轮内自动压缩照旧 |
| 空闲多久后提醒 | 60 分钟 | 距上一次请求超过这么久，缓存大概率已失效 |
| 提醒的上下文下限 | 100k | 小于这个量不提醒：省下的还不够一次请求的零头 |

「压缩摘要模型」是清单 `llm` 声明生成的一组字段（`useMainProvider` / `baseUrl` / `apiKey` /
`protocol` / `model`），见 `plugins/README.md` 的「模型接口」一节；它同样按会话可覆盖。

## 边界

- `mica exec` 这类一次性运行不压缩：没有第二轮，改历史只会改变这一次的开销与结果。
- TUI 与 `mica exec` 没有可点的地方（宿主不提供 `ctx.ask`），那边只有轮内的自动压缩。
- 压缩失败（没有可清理内容、次数用尽）不中断 turn、不消耗次数，写插件日志与健康状态。
- 请求前压缩只改发给模型的历史，不改 `conversationMessages`；手动触发的压缩会同时落盘
  （工具结果在界面上本来就是一行摘要，占位符不改变用户看到的内容）。

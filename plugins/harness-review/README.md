# Harness Review

运行机制自动记录 agent 轨迹，聚合有证据的问题候选，供用户定期复盘。无需在 system prompt 中要求模型在任务结束后反思，也不增加后台模型请求。

## 使用

在插件设置里启用 Harness Review 后，新启动的 TUI、app-server 与 `mica exec` 会自动采集。

交互式终端：

```text
/harness-review list
/harness-review report
/harness-review prune 14       # 删除 14 天前的运行记录（当前工作区）
/harness-review rebuild        # 按当前规则从轨迹重算历史问题条目
/harness-review assess <条目id> accepted 用户认可这个改进方向
/harness-review assess <条目id> validated 在相关任务和回归样本上验证，附结果和文件路径
/harness-review assess <条目id> dismissed 这是正常轮询，无需修改
```

桌面端可以直接对 agent 说“查看当前工作区的 harness 复盘并导出报告”，由 `harness_review` 工具读取或导出。桌面对话输入框不分派 TUI 斜杠命令。

### Web 运行控制台

在 **Plugins → Harness Review → 打开运行控制台** 进入，或直接打开当前 Mica 运行时地址下的 **`/plugins/harness-review/console`**。例如默认端口为 `http://127.0.0.1:8787/plugins/harness-review/console`；若主端口发生回退，以运行时的实际地址为准。页面和 `GET /plugins/harness-review/api/snapshot` 都复用主运行时端口，不另起 HTTP 服务、不启动会话或模型请求。只支持随包页面模块，停用插件后页面及数据接口一起拒绝新请求。

控制台使用项目共享的 **Arco Design React** 控件、主题和表格，包含：

- **总览**：主运行、委派和 helper 分开计数，模型/工具请求、运行终态、评估进展与工具健康。
- **问题候选**：按状态和进展筛选、搜索当前有界投影，查看建议、验证方式和证据元数据。
- **运行记录**：来源、模型、终态、请求、工具与耗时；不返回输入、prompt、工具正文或可读取任意文件的轨迹接口。工作区只显示不可逆的稳定标识，不返回 cwd 原路径；非固定插件 taskId 只显示稳定摘要。
- **插件与埋点**：随包清单、用户插件的已观察记录、最近宿主装配快照、健康上报、操作终态及曝光/点击。装配状态带宿主与更新时间，不冒充所有活进程的实时状态；零样本只表示未观察到。
- **系统日志与覆盖**：机器级日志旁证、RSS 峰值、扫描/截断/未知覆盖和警告，不把整机日志误归因于某个项目。

页面默认自动刷新，仅在可见且聚焦时每 30 秒查询，不重叠。冷服务优先读取 `console-snapshot-v3.json` 的安全持久投影，立即展示原统计时间、缓存到期时间、是否过期及覆盖范围，同时后台刷新有界内存快照；首次从未生成缓存、缓存损坏或版本不符时才等待正常只读扫描，不新增加载态。持久投影由既有**全机采集/状态发布**流程生成，不是 GET 写入；它只含已观察/最近装配的插件目录，当前清单由后台刷新补齐。刷新失败保留旧值，只返回固定安全提示，不透出原始异常。服务端共享 30 秒快照及在途查询；过期内存快照同样立即返回并刷新，失败后限频重试，避免多窗口反复全盘扫描。列表、文本和最终 JSON 都有上限，counts 与日志终态总计保留缩减前数字，不能将当前筛选结果解释为完整历史。删除派生缓存不会删除运行或评估，旧缓存版本直接失效，不需要 Evolution 迁移。

这是**只读控制台**：不触发 flush、僵尸运行回收、重建、报告导出、清理、派生缓存发布或评估写入，不改变既有采集设置；没有清理、自动修复或自动验收按钮。死宿主的可信轨迹可以在内存投影中补回确证事实，不改写运行。健康只展示固定安全分类（运行/后台/钩子/依赖/模型/存储等）、级别、时间和版本是否已知，不返回 health.message/hint/原始 issueKey，不靠自由文本秘密检测器兑现这个边界。原有工具/命令仍负责显式操作。接口继承完整访问口令和 Host/Origin 守卫，分享会话 cookie 无权访问，不开放跨源读取。该路径面向主运行时直连；Mobile Relay 的转发目录尚未包含新的只读接口，不能据此宣称中转手机入口可用。

状态有 `open`（待复盘）、`accepted`（认可方向）、`dismissed`（忽略）、`validated`（人工记录验证通过）、`regressed`（人工记录回归）。`assess` 必须提供依据，并且只能操作当前工作区可见的条目。这些状态是人工评估记录，插件本身不运行评测。

每次评估追加一条不可变历史，并保存当时范围内每条运行的出现次数（插件常驻失败保存次数下界与最后时间）。`validated` / `dismissed` 后出现超出该基线的新证据，条目保留人工状态，另标 `reviewNeeded` 待复核，不自动断言回归。旧评估迁移后没有基线，明确显示「基线缺失」并提醒重新评估；没有新失败不等于验收通过，仍需相关调用样本和独立验证。

评估时间边界在扫描开始前固定，扫描期间新启动的运行不会被误当成已看过的旧证据。历史报告最多返回最近 1000 条有效评估并提示截断，但选择当前状态时仍检查所有记录，不能让随机文件名挤掉最新结论。

配置页的插件详情里能看到机器级「运行状态」（统计范围为「所有工作区」），分开列出最近24小时未评估的重复候选与单次信号、历史待评估、时间覆盖不足、已接受待验证、已验证待观察、已忽略和待复核。候选数不等于已确认缺陷数；「已接受」只代表认可方向，不代表已经修复，「已验证待观察」也不表示后续永不复发。统计更新时间、近期窗口与数据覆盖单独展示，运行数只计纳入范围的主运行，不冒充全机完整历史。工具 `list` 同样返回 `progress` 与时间/覆盖信息，并优先显示待复核和近期重复候选，避免历史高频问题挤满前20项。

工具与命令的 `list` / `report` / `prune` / `rebuild` / `assess` 仍按会话工作区执行，不会把某个工作区的计数覆盖到全机状态。手动重算、清理与评估后立即刷新状态；局部重算更新「上次重算」，不代表全机历史已按新规则重建。常驻宿主启动及轮次结束时检查状态缓存，最多每30分钟重算一次；没有新宿主或轮次时不后台唤醒，页面的更新时间即真实统计截止。旧展示缓存按视图版本失效重算，无需迁移轨迹或评估历史。

仅最近24小时内重复出现的未评估候选、已有评估需要复核或人工标记为 `regressed` 时，侧栏 Plugins 才显示提示点；累计重复但近期未重复的历史候选仍保留，不持续触发提醒。时间覆盖不足明确列为未知，不当成近期无失败，更不自动标为已解决。缺少评估记录不表示从未有人读过复盘；改过代码或沉默一段时间都不会自动写 `assess`，登记验证仍须附实际方法与结果，之后有新证据则提示复核。「打开复盘」新开一个会话，把按进展分组的复盘提示词放进输入框（不自动发送、不自动登记 `assess`）。优先使用发起动作时页面提供的工作区，其次使用真实会话工作区；都没有时明确要求从工作区会话打开，不用插件动作进程的目录冒充。一次性动作宿主只注册这个入口，不启动历史重建或采集。

## 记录与分析

- 运行开始、终态（completed / error / aborted / paused；paused 是迭代边界暂停，不是失败，另有 interrupted 表示未正常结束）、模型请求数、工具调用和结果、provider 重试、历史改写、模型 token 用量。已有带完整 `run:finish(paused)` 轨迹的摘要在 review / rebuild 中照常读取，不当作损坏记录。
- 上下文压缩单独记一类事件（策略 local / llm / idle、原因、前后条数与字符、是否真的改了历史），按策略计数并保留最后一次。压缩不生成问题条目——它是正常机制；记下来是为了解释「某轮越跑越差」时能看出历史被改过几次。**只覆盖轮次内发生的压缩**（插件在请求边界动手）：事件挂在一次运行上，手动 `/compact`、终端里的 loop 轮前压缩与宿主的空闲压缩都在轮次之外，不进这条流。
- 委派运行单独成一条运行记录，带 `delegation: { type, parentSessionId }`，报告里按子代理类型聚合运行数、成功 / 失败 / 中止与平均请求数、平均输出 token，用来回答「哪种类型的子代理回报最差」。
- helper 运行（宿主内部工作：压缩摘要 `compaction`、旁问线程 `thread`、桌面 BTW `btw`、插件自己问模型 `plugin-llm`、兜底 `subagent`）单独成一条运行记录，带 `helper: { kind, pluginId?, purpose? }`，按来源聚合运行数、成功 / 失败 / 中止、请求数、平均请求耗时与平均输出 token。它们同样花钱、同样会失败，但不是用户的一轮：运行数、失败率与「用户重试同一任务」的推导都不把它们算进去（压缩摘要每轮喂的是同一段 transcript，按用户输入判重只会把正常机制读成「回答被拒绝」）。
- 用户纠正（`input:corrected`）：改写已发消息重跑、撤回排队消息、原样重发。收到时即异步持久化元数据，不保存正文；跨宿主重启保留。仅下一次同会话**主运行**原子认领，helper / 委派既不消费纠正，也不污染用户重试输入槽位。运行摘要持久化后确认消费，无法确认的认领保留并报告，不猜测重分配。纠正证明用户动作发生过，不单凭它判断回答质量；`rebuild` 保留摘要里已记录的纠正及对应条目。
- 每次 `run:start` 在插件装配完成后通过当前宿主的 `ctx.pluginStatus()` 取一次内存快照，记下当时的 `host`、已加载数量、加载失败与被跳过的插件 id，并算一个稳定短 hash。后续高频事件不读取共享 `plugin-status.json`，其他宿主的写入不会污染本轮归属。回调缺失或失败就省略快照；历史摘要结构不变，重建保留原始归属，不凭当前状态伪造历史纠正。hash 变化说明投影字段变了，不表示同数量的已加载插件替换一定能被识别。
- 插件自身的失败走 schemaVersion 2 的 `plugin:observe`，按 `pluginId + pluginVersion + pid + generation + taskId` 追加进 `plugin-events.jsonl`：常驻任务（`ctx.background.register`）与钩子处理函数抛错（任务名记作 `hook:<钩子>`）。保留真实生产者版本/进程世代，不拿当前清单回填历史。两者都不在任何一轮里，健康状态也只留最后一句话，看不出它已经坏了三百次。每次通知先更新累计失败、`tick` 与最新错误，再对详细事件按 5 分钟窗口合并：首条立即写；窗口到期、显式 flush、正常 dispose 与内存键淘汰都会补写尚未落盘的最新检查点，重复 flush 不重复写。即使短时间连续失败 40 次、窗口未满就退出，也保留 40 次累计数。每个身份投影取「记录行数」与「累计数最大值」中较大者，可信不同世代再汇总到稳定的插件/任务 finding；人工评估键不随进程世代改变。明确是**下界而非精确总数**：身份未知、强杀未 flush、文件轮转仍可能缺历史。合并行的时间只代表最后一次失败，不能拿它给全部累计失败定日期。失败次数到第三次才生成条目。未版本化的旧失败流不再支持，交给 Evolution 补 schemaVersion 2 与显式 unknown 身份；迁移前不解释旧形态、不改原字节，只提示覆盖未知。
- 最终组装的 system prompt 记录 SHA-256 和字符数，用于识别变化，正文不落盘。
- 工具失败、无进展的重复调用、provider 重试、运行失败与「失败后重试同一任务」形成候选，按模式聚合，附运行 ID、事件序号和轨迹文件。
- 非零退出码按**命令语义**判定：`rg` / `grep` 无匹配、`test` / `[` / `which` / `type` 的条件或查找未命中、`diff` 有差异、`git diff --quiet` / `--exit-code` 有改动，以及 `git config --get` / `--get-all` 查询未设置值，退出码 1 属正常结果，只计入 `expectedExits`。Git 按真实子命令和参数判定，其他命令、参数值或文件名中的 `--quiet` / `--get` 不享受此规则；查询出现错误诊断仍计错误。`ls` / `stat` / `find` 退出码 1、`rg` 退出码 2、失败测试及 Git 查询退出码 2 / 3 仍是错误。
- `;` / 普通换行后的状态由最后一条命令决定，管道按最后一个命令判定（不推断 `pipefail`）。`&&` 可能提前短路，保留所有可能决定非零状态的命令；这些命令的退出语义一致时采用共同结论。若同时可能是正常查询退出和真实失败，例如 `rg absent src && node --check file.js` 退出 1 且输出为空，则记 `unknown-exit` 待核实，不算成功、预期退出或已确认工具故障。有明确测试失败或错误诊断时仍保留真实失败；普通 stdout 不能证明退出归属。
- 重复调用只在**没有推进**时才算：脱敏后的完整结果指纹与上一次相同，且两次之间没有别的写操作。指纹在截断正文之前计算，重建时不会因为三次结果的前 4,000 字相同就误判重复；轮询类工具（`wait_for`、`background_tasks_read`、`agent` 的 `await` / `join` / `read` / `list`）完全不参与；改完代码重启 dev server、重跑一次验证都会因为中间有写操作而不计入。
- 「上次运行未成功后重试同一任务」用 `run:start` 的输入推导：同一会话上一次以 aborted / error / interrupted 结束，这次输入与上次高度相似（字符 bigram Jaccard ≥ 0.82，两侧都不短于 40 字符）。它是重试候选，不证明回答被拒绝；运行期的前一输入槽位仍只在当前宿主内维护。
- 每项提供可能涉及的模块、建议及验证方式；错误分类先看工具的显式失败字段或失败首句，不把旧条目、参数列表、示例 patch 里的关键词当成本次原因。通用 JSON 结果识别顶层 `outcome: error|failed|failure|timeout`、`error: string|{message,code}`、`exitCode`、`timedOut`，继续识别现有 `isError` / `success` / `ok` / `status` 信封；不递归扫描 stdout / content / 任意嵌套数据。无判别字段的旧 `exit_code` / `timed_out` shell JSON 仅按 shell 元数据解释，避免把读到的源码当失败。既有 `[任务] exit=… · …s`、`[步骤/总数] … → 失败（exit=…）` 操作块状态头也可分类，不依赖 SSH / Computer Use 等插件名；建议新生产者使用结构化 outcome，避免靠任意自然语言猜结果。
- 空 hunk、patch 头缺失、上下文不匹配 / 匹配不唯一、记忆容量超限、连接提前关闭、普通连接失败、路径不存在、超时、非零退出码各有对应类别。模型 transport 的 retry 另按请求上下文归为 `provider-overload` / `provider-connection` / `provider-timeout` / `provider-rate-limit` / `provider-error`；运行终态中的同类故障沿用 provider 类别，其他未知终态保留 `runtime-error`，不再一律标成 `tool-error`。旧的 metadata-only retry 也按事件类型纠正故障域，但无法从缺失原文推断具体供应商错误。provider 类别说明模型请求路径失败，不单凭它断定是供应商、本地网关还是网络，更不归咎于工具或直接建议修改本机。helper 的模块仍表示调用来源，不是根因定论。
- 工具超时包括浏览器明确报告「页面截图超过 …ms 未返回」「页面脚本执行超过 …ms」；模型请求无输出的「No stream data from provider for …s (waiting for model output).」属于 `provider-timeout`。源码、成功结果的 stdout 或普通文字引用这些句子不会触发超时。只有 shell 命令超时才建议改用后台任务。工具失败不等于任务失败，运行 `completed` 不等于用户目标已验证。
- 采集范围是通过 `AgentRuntime.run` 执行的运行，宿主内部工作也在其中（runId 为负、带 `helper` 来源），所以它们有同样的请求级事件与用量。最终 prompt 指纹可识别包括记忆在内的整体变化，但不能单凭指纹归因到某条记忆。
- 运行 ID 标识一次 agent 执行尝试；turn 级重试可能产生多条运行记录。

不自动修改指令、工具、loop 或记忆，不生成或执行修改 patch。第一版交付观察、聚合和人工 review 流程。

Markdown 报告的 `## Runs` 与 `harness_review list` 最近运行列表不列 helper；委派仍单独标注，helper 由 `helpers` 汇总。`## Tool health` 按失败率列每个工具，使用与实时采集 / 重建共用的分类逻辑，不直接把旧轨迹类别当现行规则。仅完整、可分类且工具调用 / 结果配对的已结束轨迹参与健康统计；损坏文件的正常前缀也不计入，丢事件、未结束、配对不全或退出归属不明时整条运行排除。`toolHealthCoverage` 显示纳入 / 排除运行数和无法分类或配对的数量，`unknownResults` 包括 `unknown-exit`：未覆盖是未知，不能当作零失败。完整轨迹中归属不明的退出会移除对应旧工具误报，同一运行里其他可确认的错误仍保留；摘要工具错误 / 预期退出计数只含已确认部分。不完整记录保留采集计数及警告，不假装已经重算。helper 汇在 `## Helpers`，插件自身失败在 `## Plugin health`；后者是机器级事实，不受 cwd 过滤，次数是下界。它们派生的条目都可 `assess`。

## 存储与设置

默认位置：`$MICA_HOME/plugin-data/harness-review/`。

- `runs/<uuid>/`：每次运行独立的 `events.jsonl` 与 `summary.json`。
- `decisions/<条目键>/<uuid>.json`：每次人工评估一份版本化记录，保留状态、备注、时间和证据基线；插件失败条目键哈希成 `h-<32 位>` 避免非法文件名。旧单文件形态不再支持，由 Evolution 的 `harness-review-assessments` 迁移并归档，未知 / 损坏文件不改。
- `corrections/<uuid>.json`：尚未写入运行摘要的用户纠正元数据；`corrections/claims/` 保存不可变认领，防止并发重复消费，不生成虚假的运行。
- `plugin-events.jsonl`：插件自身（常驻任务与钩子）的失败记录（超过 4 MB 滚成 `plugin-events.1.jsonl`，旧的覆盖）；轮转 + append 与读取两份文件的快照共用跨进程锁，避免并发覆盖或跨 rename 重复计数。
- 报告由 `report` 按需导出，命令和工具返回实际文件路径。
- `state.json` / `data.json`：规则重建账本与机器级配置页状态；原子替换，跨宿主只在发布时短暂持 `status.lock` 并重读最新状态，避免旧内存状态覆盖别的宿主刚写入的重建时间与版本。重建、轨迹重放、扫描日志均在此锁外；自动刷新由独立 `refresh.lock` 去重，其他宿主在做或发布锁繁忙就跳过，不将正常争用报成插件故障。
- `console-snapshot-v3.json`：可删除、可重建的安全控制台派生缓存，版本与分类规则不符即丢弃；0600 原子发布，不保存轨迹正文或错误原文。GET 仅读且按文件身份核验，损坏/超限/符号链接不修复、不覆盖。

问题条目与错误分类计数是派生数据，轨迹才是事实来源。`rebuild` 重算 `findings`、`toolErrors` 与 `expectedExits`，不改请求数、token、耗时、终态和评估历史。规则版本变化后常驻宿主自动重算；一次性宿主跳过。当前分类规则版本为 11，仅使派生缓存失效，无需 Evolution 数据迁移；控制台功能本身不提升分类规则版本。重建复用参数指纹，完整正文按现行规则分类，明确完整的失败首句也可重新分类；正文不足时保留已保存结论（包括 `unknown-exit`；retry 的旧工具类别仅纠正故障域），不凭附注猜测。完整配对轨迹即使含归属不明的退出也能重建已确认部分，该运行仍排除出健康率。仍在运行、轨迹损坏、工具配对不全、丢事件或 id 非法的记录跳过并计数，不用部分结果覆盖旧证据。

每次运行最多跟踪 1000 个不同工具调用键、记录 100 个 finding 候选。超过上限时摘要会保存未跟踪调用与未记录 finding 信号的数量，`list` / `report` 显示受影响运行、漏记数量和明确的分析不完整警告；旧摘要缺少计数且轨迹不可完整重放时标为未知，不把没有 finding 解读为没有问题。完整轨迹可由 `review` / `rebuild` 按当前规则重算这两个计数。

摘要写入与重建共用每运行的进程锁；重建持锁重读后只替换派生字段，保留并发补写的纠正和消费回执。参数截断导致命令无法恢复时，保留采集时明确记录的预期退出结论，不因结果正文完整就把它改判成失败。

每条摘要记录 `mode`（`session` / `one-shot`）与 `host`（`desktop` / `cli`），并记下采集进程的 `hostPid`。显式复盘/重建先在摘要锁内重读并回收死宿主（早期无 pid 时沿用超过 6 小时的写入新鲜度边界），避免覆盖迟到的 finish。摘要落后时，只有稳定、连续、从本次 run:start 开始且没有丢事件的本地轨迹才可补回确证的请求/工具/重试次数、finding 与明确末尾 finish 的终态/原时间/原耗时；不推造错误正文或验收。没有末尾 finish 只恢复已证实的前缀事实，终态仍是 `interrupted` / 未知；损坏、缺行、半行、有损、冲突终态不做恢复，缺终态轨迹不进工具健康率。回收不制造 finishedAt。Web 只对明确已退出 pid 或已回收的历史记录做同一内存投影，不修改摘要；当前/存活/未知宿主的 running 不被猜成结束。缓存只保存投影，恢复规则变化使派生索引失效，不改采集/评估格式。

记录使用异步串行批量写入；摘要在运行开始、每 25 个事件、运行终态与显式 flush 时更新，不为每个事件重写整份摘要。待写与正在写入的轨迹正文合计最多 4 MiB，背压或事件上限造成的丢弃计入 `droppedEvents`，计数、问题分类和运行终态仍继续更新；超过事件上限的正文不再准备脱敏副本与内容哈希。设置和会话信息在运行开始时读取一次。正常关闭时 flush；未结束的运行会保留未完成状态，不当作成功；进程被强制杀死时可能保留 `running`，复盘时应视为未完结记录。

工具默认 `list` 与命令 `list` 的完整 JSON（含缩进、转义）硬上限为 **24,000 字符**，不仅按条目数截断。保留 coverage、progress、总体指标、优先级最高的问题与工具健康摘要；最多 20 条精简运行、20 项问题、15 行工具健康，每项仅一条短证据，预算不足时继续缩减。warning、评估历史、委派树、helper 等以计数 / 短摘要展示，不把长文本或 prompt 指纹散列整块带进上下文。`outputBudget` 给出省略数量；同一统计快照会自动导出 Markdown，`reportPath` 是完整 warnings、证据、评估历史与来源明细的真实文件路径。`report` 仍可单独导出完整复盘范围。请求数按 provider 实际进入一轮请求计数，transport 重试单独统计。

插件设置支持关闭自动记录、关闭任务与工具内容采集（只留摘要与指标）、调整单条内容字符数和单次运行事件上限。超限丢弃数量保留在摘要中，运行终态仍会更新。设置变更从下一次运行开始生效。

任务与工具内容默认脱敏后截断记录，敏感键、常见凭据格式和媒体 payload 会过滤；这不是任意自由文本的完整秘密检测器。模型配置只存 provider/model/protocol/effort/role 等白名单字段，不复制接口凭据。可以关闭内容采集，仅保留元数据；文件保存在本机，由用户按需清理。

数据在 `$MICA_HOME` 下，**不随重启丢失**，会持续累积（实测一次长任务约 0.8MB，十几条就是十几 MB）。插件不按日程自动删除：用 `/harness-review prune <天数>` 手动清理当前工作区早于该天数的运行记录（默认 30 天，仍在运行的记录永不删除，人工评估结论保留）。

复盘按当前工作目录过滤，并有扫描与证据数量上限：最多扫描 10,000 个运行目录，在扫描范围内**先按工作区筛选，再按真实 `startedAt` 降序选最近 2000 次**（同时间按 id 稳定排序），不拿目录 mtime 充当运行时间。超出目录扫描范围仍明确是不完整历史。历史轨迹元数据仅校验自己的 `runs/<id>/events.jsonl` 后缀；所有 trace 读取、重建与返回的证据路径始终重定位到**当前 root** 下对应的运行，即使搬家前的旧副本仍存在也不读取它，本地轨迹缺失即报证据不可用。

`derived-index.ts` 是每 recorder 可丢弃的有界内存缓存，不写用户存储、不需要迁移：摘要索引最多 10,000 项 / 4 MiB，只存选取所需头字段；轨迹推导最多 2000 项 / 16 MiB，缓存 finding、工具计数、事件时间等投影，不缓存事件正文。签名包含 dev/ino/size/mtime/ctime，配合分类规则版本使追加、同大小改写、替换、删除与重建失效；有变化的文件读取前后校验签名再入缓存。最近24小时指标每次用当前窗口重新计算，缓存命中不冻结时间。运行中的轨迹不复用派生结果，实例/root 切换冷启动。

## 日志旁证（只读、有界）

`log-evidence.ts` 从 `resolveLogDir()`（测试可用 `MICA_LOG_DIR` 隔离）读取本机 JSONL 日志，`ReviewReport.logEvidence`、`list` 的短摘要和 Markdown 的 **Log evidence** 使用同一份投影。只打开只读文件、不创建日志、不追符号链接；以最多 16 并发检查**全部候选文件元数据**后按 mtime 选最新 64 个，不再先按名称截断 512 个。每文件最多尾部 128 KiB、单次合计 4 MiB，每文件最多 2048 条投影；签名缓存最多 64 项 / 4 MiB，只存白名单标量，不缓存日志正文。所有已纳入记录先累计全机 `totals` 与每插件 `pluginTotals`，再把明细按错误/超时、未知优先截成每类 100 组；总计不从保留的明细反算。每插件总计也独立限 100 身份并明确覆盖限制，错误/未知优先，机器总计仍保留全部已读事实。

- `scope=plugin-operation`、`event=operation.start|finish` 读取顶层 `operationId/plugin/pluginVersion/operation/surface/outcome/code/ms/pid/generation`，按插件、版本、进程世代、操作、界面和终态聚合；相同身份/operationId/阶段去重。`busy/waiting/conflict/cancelled/declined/partial/skipped/unknown` 不混为 error；只有 start 没有 finish 是未知，不凭它断言失败。成功只证明处理器完成，不是用户验收。
- 消费 `plugin-heartbeat/background.heartbeat` schema 1 的后台例行合并窗口（success/skipped/waiting 原样保留）：保留 count、窗口实际首末时间、累计/最长耗时与 `[10,100,1000,10000]` ms 的 5 桶分布，按唯一 heartbeatId 去重，计入操作次数。合并 count 不包含即时状态转换/失败记录，不把单条心跳当一次 tick，也不按最后时间给整段计数造日期。漏掉尾部、轮转和写入损失仍使它只是下界。
- 消费 `writer-health/writer.checkpoint` schema 1：按 pid/generation 取累计丢弃、溢出、序列化、写失败、丢失下界和检查点失败的最大值，并保留日志级别/关闭策略。缺检查点是未知；写入失败可能已有部分写入，不把它直接加进已证实丢失下界。
- `event=plugin:experience` 只读取 `data.schemaVersion=1` 的 `event/surface/action/outcome/count`，归属来自外层 `pluginId`（优先）或 `plugin`，时间来自 `at`；现存日志里的 `time/plugin` 只读规范化，不回写旧文件，不复制 sessionKey/revision 等无关标识。
- 系统 `warn/error` 保留固定 pluginId/pluginVersion/pid/generation 再按 scope/event/level 分组，历史缺字段明确 unknown，不合并不同插件的同名错误，不用当前清单回填。`mem` 采样按 pid 汇总 RSS / heap 峰值（MB）。Electron `render-process-gone/child-process-gone` 的 reason=crashed/oom 是明确崩溃事实；正常 reason=killed / exit 15 / SIGTERM 不计 crash，不扫描 stderr 猜测根因。
- 不复制正文、文件路径、URL、命令或错误原文；操作/动作名和类别严格限制为固定标识字符，结果/错误对象不展开。这些是机器级旁证，**不冒充当前 cwd 或某条 agent run 的归因**，不自动生成新的 finding 或写人工结论。

`logEvidence.coverage` 明示候选、实际检查元数据、扫描、未纳入、不可读、读取字节、尾部截断、坏行、忽略行、丢弃首尾半行、行数/分组上限、截断前组数、合并心跳数量、各已读域的时间范围与 writer 检查点是否观察到。域窗口只证明已读覆盖，不证明没读到的域没有事件。限额、轮转和保留期都会漏历史，计数和峰值只覆盖已读尾部，不能把未看到解释成没有发生。`list` 每类先取最多 5 行，继续服从既有 24,000 字符硬预算，同时保留总计与覆盖，完整有界投影见同快照 report。

# Harness Review

运行机制自动记录 agent 轨迹，聚合有证据的问题候选，供用户定期复盘。无需在 system prompt 中要求模型在任务结束后反思，也不增加后台模型请求。

## 使用

在插件设置里启用 Harness Review 后，新启动的 TUI、app-server 与 `mica exec` 会自动采集。

交互式终端：

```text
/harness-review list
/harness-review report
/harness-review prune 14       # 删除 14 天前的运行记录（当前工作区）
/harness-review rebuild        # 按当前规则从轨迹重算历史问题条目
/harness-review assess <条目id> accepted 用户认可这个改进方向
/harness-review assess <条目id> validated 在相关任务和回归样本上验证，附结果和文件路径
/harness-review assess <条目id> dismissed 这是正常轮询，无需修改
```

桌面端可以直接对 agent 说“查看当前工作区的 harness 复盘并导出报告”，由 `harness_review` 工具读取或导出。桌面对话输入框不分派 TUI 斜杠命令。第一版没有专用 review 页面。

状态有 `open`（待复盘）、`accepted`（认可方向）、`dismissed`（忽略）、`validated`（人工记录验证通过）、`regressed`（人工记录回归）。`assess` 必须提供依据，并且只能操作当前工作区可见的条目。这些状态是人工评估记录，插件本身不运行评测。

配置页的插件详情里能看到「运行状态」（已记录运行数、待复盘问题数、最近运行、上次重算），出现**跨多轮重复且还没有人处理过**的问题时，侧栏 Plugins 上会点一枚提示点；点开的「打开复盘」动作会新开一个会话、把复盘提示词放进输入框（不自动发送），由 agent 去读报告并挑出值得处理的条目。单次失败不上报，避免提示点点不动。

## 记录与分析

- 运行开始、终态（completed / error / aborted）、模型请求数、工具调用和结果、provider 重试、历史改写、模型 token 用量。
- 最终组装的 system prompt 记录 SHA-256 和字符数，用于识别变化，正文不落盘。
- 工具失败、无进展的重复调用、provider 重试、运行失败与「失败后重试同一任务」形成候选，按模式聚合，附运行 ID、事件序号和轨迹文件。
- 非零退出码按**命令语义**判定：`rg` / `grep` 无匹配、`ls` / `test` / `which` 找不到、`diff` 有差异、`git diff --quiet` 有改动都是命令自身的正常结果，不算工具错误，只计入 `expectedExits`；`rg` 的退出码 2（正则错误）仍是真实错误。判定看决定 `$?` 的那个程序：链式命令取最后一段、管道取最后一个命令，所以 `bun test … | tail -25` 按 `tail` 判。
- 重复调用只在**没有推进**时才算：结果与上一次逐字节相同，且两次之间没有别的写操作。轮询类工具（`wait_for`、`background_tasks_read`、`agent` 的 `await` / `join` / `read` / `list`）完全不参与；改完代码重启 dev server、重跑一次验证都会因为中间有写操作而不计入。
- 「上次运行未成功后重试同一任务」用 `run:start` 记下的输入指纹推导：同一会话上一次以 aborted / error / interrupted 结束，而这次输入与上次高度相似（字符 bigram Jaccard ≥ 0.82，两侧都不短于 40 字符）。这是目前唯一能反映「回答被拒绝」的信号。
- 每项提供可能涉及的模块、建议及验证方式；建议按失败原因给出，不同原因（空 hunk、patch 头缺失、patch 上下文不匹配、路径不存在、超时、非零退出码等）给的是不同的可执行指引，而不是同一段通用话术。工具失败不等于任务失败，运行 `completed` 不等于用户目标已验证。
- 采集范围是通过 `AgentRuntime.run` 执行的运行。直接创建的 helper/subagent 模型客户端内部请求目前没有完整轨迹；主流程委派工具的调用与返回仍会记录。最终 prompt 指纹可识别包括记忆在内的整体变化，但不能单凭指纹归因到某条记忆。
- 运行 ID 标识一次 agent 执行尝试；turn 级重试可能产生多条运行记录。

不自动修改指令、工具、loop 或记忆，不生成或执行修改 patch。第一版交付观察、聚合和人工 review 流程。

## 存储与设置

默认位置：`$MICA_HOME/plugin-data/harness-review/`。

- `runs/<uuid>/`：每次运行独立的 `events.jsonl` 与 `summary.json`。
- `decisions/`：每个问题条目独立的人工判断记录。
- 报告由 `report` 按需导出，命令和工具返回实际文件路径。

问题条目是从轨迹推导出来的派生数据，轨迹才是事实来源。改进了错误分类或聚合规则后，用 `rebuild` 让历史运行按新规则重算：替换 `findings` 与派生计数 `expectedExits`，运行次数、token、耗时与 outcome 保持原值。分类规则版本（`CLASSIFIER_VERSION`）变化后，常驻宿主会在启动时自动重算一次，`mica exec` 这类一次性宿主跳过、交给下一次常驻宿主。重建复用保存的参数指纹；正文完整时重新分类错误，关闭正文采集或正文截断时复用已保存的错误分类，保留相同的问题身份与人工评估。仍在运行、轨迹损坏、超过采集上限或 id 不合法的记录会跳过并在返回值里计数；不完整轨迹不会覆盖原有问题证据。

每条摘要记录 `mode`（`session` / `one-shot`）与 `host`（`desktop` / `cli`），并记下采集进程的 `hostPid`。复盘与重建前会先回收僵尸运行：`hostPid` 对应的进程已不存在（早期记录没有 pid 时改看摘要文件是否超过 6 小时没被写过）且没有 finish 事件，就判为 `interrupted`，回收条数写进 warnings——宿主被强杀时 dispose 不会执行，不回收会永远挂在 `running` 上。

记录使用异步串行批量写入；摘要在运行开始、每 25 个事件、运行终态与显式 flush 时更新，不为每个事件重写整份摘要。待写与正在写入的轨迹正文合计最多 4 MiB，背压或事件上限造成的丢弃计入 `droppedEvents`，计数、问题分类和运行终态仍继续更新；超过事件上限的正文不再准备脱敏副本与内容哈希。设置和会话信息在运行开始时读取一次。正常关闭时 flush；未结束的运行会保留未完成状态，不当作成功；进程被强制杀死时可能保留 `running`，复盘时应视为未完结记录。

`list` 最多展示最近 20 次运行和 20 项聚合问题，每项 5 条证据，避免复盘内容挤占模型上下文；`report` 导出完整复盘范围。请求数按 provider 实际进入一轮请求计数，transport 重试单独统计。

插件设置支持关闭自动记录、关闭任务与工具内容采集（只留摘要与指标）、调整单条内容字符数和单次运行事件上限。超限丢弃数量保留在摘要中，运行终态仍会更新。设置变更从下一次运行开始生效。

任务与工具内容默认脱敏后截断记录，敏感键、常见凭据格式和媒体 payload 会过滤；这不是任意自由文本的完整秘密检测器。模型配置只存 provider/model/protocol/effort/role 等白名单字段，不复制接口凭据。可以关闭内容采集，仅保留元数据；文件保存在本机，由用户按需清理。

数据在 `$MICA_HOME` 下，**不随重启丢失**，会持续累积（实测一次长任务约 0.8MB，十几条就是十几 MB）。插件不按日程自动删除：用 `/harness-review prune <天数>` 手动清理当前工作区早于该天数的运行记录（默认 30 天，仍在运行的记录永不删除，人工评估结论保留）。

复盘按当前工作目录过滤，并有扫描与证据数量上限：合并最近 2000 次运行的问题条目（先按工作区筛选再截断，别的项目不会挤掉当前项目的记录）。轨迹归属只比路径后缀，所以整个数据目录搬过家（换 `MICA_HOME`、从备份恢复）时，历史不会因为绝对路径对不上而全部作废。

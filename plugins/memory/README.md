# Memory

跨会话记忆。存在的唯一目的是：**下次开会话时，不必再问一遍已经确认过的事实**。

它不是「把对话记下来」，也不是「给模型一个笔记本」。记错了、记多了，比不记更糟——
每一条记忆都会出现在之后某些会话的系统提示词里，成为模型判断的前提。

## 为什么这么设计

旧版按**主题**分三块（`user` / `memory` / `project`），并且三块**无条件全部注入**。
真实使用里它有两个后果：

- 「针对需求 A 花两天挖出来的字段路径」写进 `memory`，之后每一个无关会话都要读一遍；
- 三块各 1375 / 2200 / 2200 字符的预算同时当写入上限，写满之后写入永远失败，
  模型只能 `patch` 覆盖它读不懂的旧条目——记忆越改越歪。

新设计的起点不是「记什么」，而是 **这条事实在哪些会话里还成立**。记忆按作用域分层，
注入只给当前会话适用的那些。

## 三层作用域

| 层        | 文件                 | 放什么                                                           | 注入条件                                       |
| --------- | -------------------- | ---------------------------------------------------------------- | ---------------------------------------------- |
| `profile` | `PROFILE.md`         | 用户本人的稳定属性：称呼、语言、跨任何项目都成立的偏好与红线     | 总是                                           |
| `domain`  | `domains/<名字>.md`  | 跨仓库、但只在一个主题内成立的事实（一组同域仓库共享的坑与规则） | 会话的 cwd / 仓库根落在该领域声明的 `match` 里 |
| `project` | `projects/<仓库>.md` | 一个仓库的目录结构、运行命令、架构决策及其理由、非显然的坑       | 会话在一个 git 仓库里，且按仓库身份匹配        |

**没有第四层「任务」**。本次需求的中间发现、待办、进度不写进记忆——那是会话自己的事，
用 `session_notes` 或对话本身承载。会话结束后它就该消失。

### 项目身份 = 仓库，不是 cwd

按 cwd 归档会在真实用法里裂成好几份：同一个仓库从根目录开、从 `apps/desktop` 开、
在临时 worktree 里开，各写一份互不可见的记忆，而它们讲的是同一套约定。

`repo.ts` 只用文件系统算出身份（**不 spawn git**：本机 git 配置挂了 trace2 钩子，
一条命令 150–600ms，而这段代码在会话第一次渲染提示词时就会跑）：

1. 从 cwd 往上找 `.git`；
2. `.git` 是文件时读 `gitdir:`，再读 `<gitdir>/commondir`（worktree 共享这一份）；
3. 身份优先用 `config` 里的 `origin` 地址，归一化后跨 clone 共享；没有远端才用 common dir 路径。

所以 `apps/desktop`、`website` 与仓库根是同一份项目记忆，worktree 也是，另一个 clone 也是。

### 目标仓库 = 实际在改的仓库，不是开窗的位置

会话从哪开会话不等于任务属于哪：在 `mis` 里开、实际改 `sass`；在 `mica-code` 里开、
去修 `spring-cli`；从 melos 的 workdir 里开、工作区根本不是 git 仓库。只按 cwd 归项目记忆，
这些会话写下的东西会落进一个谁也不读的文件，真正需要它的仓库那份永远是空的。

`activity.ts` 从工具调用里认**实际被碰到的路径**（`write_file` / `apply_patch` 的文件行、
`run_shell` 里的 `cd`、读工具的 `path` / `file_path`），按信号强弱加权：

| 信号                                    | 权重 | 说明                               |
| --------------------------------------- | ---- | ---------------------------------- |
| 写文件（`write_file` / `apply_patch`）  | 3    | 改到这里就是真的在这里做事         |
| `run_shell` 里的 `cd <目录>`            | 2    | 显式切过去的意向                   |
| 读 / 搜索（`read_file`、`grep_search`） | 1    | 看一眼不算，累计两次或一次写才进来 |

然后：

- 权重 ≥ 2 的非 cwd 仓库，最多 2 个，**注入**它的项目记忆（标题带「本次任务目标」）；
- 权重最高的那个成为 `memory` 工具省略 `repo` 时的**默认写入目标**；
- 整理器按同一个候选列表决定「这条事实属于哪个仓库」。

模型也可以显式指定：`memory({ repo: '~/Desktop/VsGo-Projects/sass', ... })`，
路径可以是还没创建的文件。观察是进程内的、按会话 id 分桶，重启后重来。

它带来的一个代价要清楚：目标仓库是在第一轮工具调用之后才认出来的，那一次注入会让
记忆段落变一次（prompt cache 前缀在这处失效一次）。这比「整场会话写错仓库」便宜得多。

### 领域由用户划定

领域不是模型能凭空造的概念。模型造一个「领域」等于换个名字继续写全局记忆，
那正是要解决的问题。领域只能由用户创建：

```
/memory domain new 租车 ~/Desktop/VsGo-Projects/sass ~/Desktop/VsGo-Projects/mis ~/Desktop/VsGo-Projects/zuche-*
```

文件头部声明它覆盖哪些目录（前缀语义，`*` 按路径分段通配）：

```markdown
---
description: 租车业务相关仓库
match:
  - ~/Desktop/VsGo-Projects/sass
  - ~/Desktop/VsGo-Projects/mis
  - ~/Desktop/VsGo-Projects/zuche-*
---

跨仓库共享的事实写在这里。
```

`/memory domain list` 看已有领域，`●` 标出当前会话命中的那些。

## 存储与注入解耦

- 文件里放多少条不受注入预算限制（只有 20 000 字符的失控保护）。**写不进去**不再等于
  「预算满了」，所以不需要靠改写旧条目来腾空间。
- 注入按层按预算挑选：`! ` 前缀的条目（pin）优先，其余按文件顺序；被挤掉的条目仍在盘上，
  段落头写「另有 N 条更早的未展示」。
- 三者都可直接编辑：一条记忆就是一个自然段，空行分隔。没有数据库、没有向量索引、
  没有需要同步的元数据。

## 什么时候注入

会话内**冻结**：第一次渲染时读盘，之后不变，直到 `/memory refresh` 或会话结束。
记忆每轮都变的话，它前面所有内容的 prompt cache 前缀都会失效。
唯一例外是作用域名变了（`/cd` 换仓库、新建领域），那时换掉对应层。

没有适用的条目时，整段不出现——新会话、一次性任务不该为记忆付 token。

## 写入门槛

`memory` 工具的描述里写着三道测试，任一不过就不要写：

1. **三个月后，在一个完全无关的需求里，它还有用吗？**
2. **脱离本次对话，能独立读懂吗？**（不许有「这个字段」「上面那个 bug」）
3. **它是事实，还是行动规则？**

第 3 条最容易被忽略：`必须复用 X 组件`、`改完要跑 Y`、`不要用 Z` 是**行动规则**，
属于角色文件（`$MICA_HOME/role/*.md`）、`AGENTS.md` 或项目约定，不是记忆。
规则写错会永久污染每一次对话，事实写错只影响相关的那一层。

多数会话结束时没有任何该写的东西。留空是正确结果。

## 自动整理

`turn:after` 后可选跑一次（默认开启，最少 8 条消息，按间隔节流），用一套更保守的
判据把对话收敛成操作：

- 判据是三套测试 + 「不要保存」清单（中间状态、临时路径、代码里一眼可见的事实、凭据）；
- **默认最窄**：能进 `project` 就不进 `domain`，能进 `domain` 就不进 `profile`；
- **写对仓库**：操作可带 `repo`（仓库名），省略时落到本次任务的目标仓库；
  会话开在 A、实际改 B 时整理器会把事实归到 B；
- **不允许写 `profile`**：用户画像只能由用户在对话里明确要求时写入；整理器判断属于画像的
  内容写进 `notes`，交给用户决定；
- 领域必须已存在且覆盖当前目录，否则拒绝——不新建领域。

整理方式二选一：宿主子代理（复用当前模型）或独立接口（`llm` 声明的地址 / Key / 协议 / 模型，
可复用当前会话模型）。失败只记健康状态与日志，不中断 turn。

## 文件布局

```
$MICA_HOME/memory/
  PROFILE.md                  # 用户档案
  projects/<仓库名>-<hash8>.md  # 项目记忆，身份来自 remote 或 common dir
  domains/<名字>.md            # 领域记忆（头部有 match）
  state.json                  # 上次整理时间 / 模式 / 结果，节流基线
  curator.lock                # 跨进程整理锁
  archive/<时间戳>/            # 手动归档的旧版文件（/memory archive）
```

## 命令

| 命令                                             | 作用                                                                    |
| ------------------------------------------------ | ----------------------------------------------------------------------- |
| `/memory` / `/memory status`                     | 本会话会注入哪几层、各层用量、整理状态                                  |
| `/memory list [profile\|project\|domain <名字>]` | 列出条目                                                                |
| `/memory domain list`                            | 领域清单，标出当前命中的                                                |
| `/memory domain new <名字> [路径...]`            | 新建领域 / 追加覆盖路径（默认当前目录）                                 |
| `/memory review`                                 | 立即整理一次                                                            |
| `/memory refresh`                                | 丢弃本会话快照，下一轮重读文件                                          |
| `/memory path`                                   | 显示各层文件路径                                                        |
| `/memory archive`                                | 把旧版 `USER.md` / `MEMORY.md` / `projects/<cwd-hash>/` 移入 `archive/` |

旧版布局（按 cwd 哈希归档的三块记忆）**不再被读取**，也**不会被自动删除**：
`/memory archive` 是显式动作，因为「用户以为记忆还在、其实被搬走了」比留着更糟。

## 边界

- 子代理不写记忆（`primaryAgentOnly`）：临时发现未必长期成立，归属也会变模糊。
- 一次性运行（`mica exec`）不整理：没有「下一次会话」，只会多花一次模型请求。
- 记忆里的文字**不是指令**。注入段落明确说明这一点；写入还有安全扫描
  （不可见字符、私钥、凭据、prompt injection 语句）。

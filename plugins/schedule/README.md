# Schedule

本机的一份排期，与任何聊天工具无关：顶栏右侧一枚 `Schedule` 图标，点开是整页甘特图。任务平铺在
时间轴上，**同色的任务排在同一行**，时间重叠的上下错开一条道；一条任务有名称、起止日期、颜色和
一段 Markdown 备注。

数据就在 `$MICA_HOME/plugin-data/schedule/data.json`，两个入口改同一份：

| 入口           | 谁在用 | 干什么                                                                             |
| -------------- | ------ | ---------------------------------------------------------------------------------- |
| 整页甘特图     | 人     | 点空白新建、拖条改期、点条编辑名称 / 颜色 / 备注，导入导出 JSON                    |
| 机读 HTTP 接口 | 模型   | 输入框敲 `/` 挑中后插入 `/plugin/schedule/api`，用到时读文档、照它建 / 改 / 删一条 |

## 数据长什么样

```jsonc
{
  "version": 1,
  "updatedAtMs": 1793000000000,
  "updatedAt": "10-31 18:20", // 配置页「运行状态」读它
  "summary": "12 个任务", // 同上
  "title": "我的排期", // 页面顶部可以改
  "scale": "day", // day / week / month，上次关掉页面时的刻度
  "tasks": [
    {
      "id": "t_xxx", // 全局唯一，接口与页面按 id 定位
      "name": "联调",
      "start": "2026-11-02",
      "end": "2026-11-06", // 含首尾
      "color": "blue", // blue / violet / emerald / amber / rose / cyan / slate
      "note": "## 前置\n- 后端接口就绪", // Markdown
    },
  ],
}
```

页面展示与导入使用 `normalizeData`：认不出的任务可以跳过，颜色认不出落回蓝色，日期只留
`YYYY-MM-DD`。写盘不能拿这种容错当校验：页面与接口读取已存在的文件时，损坏 JSON、非法
结构、坏任务或重复 id 都会报错，不会先丢掉条目再保存。

旧形态（`plans` / `stages`）不再由排期运行时读取：这里只认 `version: 1` + `tasks`，旧文件显示为空，写盘会拒绝。
导出的 JSON 与 `qirong-application/apps/gantt` 同形（`title` / `scale` / `tasks`），两边可以互相导入。

## 机读接口

Mica 运行时在自己的监听端口提供这套接口，Schedule 页面关着也能用：

```text
http://<mica-host>:<mica-port>/plugin/schedule/api
```

宿主把 `/plugin/schedule/api` 挂在应用现有端口上（任意方法、JSON 请求体、单次 30 秒），不再有
`schedule` 工具，排期也不在每轮请求里带 schema。桌面 / Web 主对话的输入框敲 `/`，在「API 文档」
里挑中 `schedule`，只会插入这个 URI；模型需要时再 GET 一次文档，照端点调用。TUI、`mica exec`
与其它外部客户端同样用 HTTP 调，应用需要在运行。

| 方法   | 路径         | 说明                                                     |
| ------ | ------------ | -------------------------------------------------------- |
| GET    | `/`          | 接口文档：描述、调用纪律与端点表（宿主直接回，不进插件） |
| GET    | `/overview`  | 今天日期、标题、刻度、全部任务（含 `task_id`）与可读排期 |
| POST   | `/tasks`     | 新建一条任务                                             |
| PATCH  | `/tasks/:id` | 只改传入的字段，其余保持原样                             |
| DELETE | `/tasks/:id` | 删除一条任务                                             |

调用顺序写在 `guide` 里，模型每次先读文档：

1. `GET /overview` 拿 `today` 与 `tasks[].id`；「下周三」这类相对日期从这个 `today` 推。
2. 在 `tasks` 里按名字找：找到才 `PATCH`，找不到才 `POST`；同名多条先问用户指哪一条。
3. 改期时 `start` 与 `end` 一起给，否则剩下的旧 `end` 会让区间反过来（400）。改完只汇报变了
   什么（具体日期、名字、颜色）。

请求体只认 `name` / `start` / `end` / `color` / `note`：拼错的字段（`colour`）直接 400，而不是
悄悄忽略。日期一律 `YYYY-MM-DD`、含起止两端，只占一天时 `start` 与 `end` 相同；颜色是
`blue` / `violet` / `emerald` / `amber` / `rose` / `cyan` / `slate`，同色任务在页面里排同一行，
省略时按色板轮换。备注是 Markdown，`note: ""` 是清空。过去的任务保留，只有用户要求才删。

成功回包是 `{ ok: true, data }`，失败是 `{ ok: false, code, error }`：

| 状态 | code               | 什么时候                                                      |
| ---- | ------------------ | ------------------------------------------------------------- |
| 400  | `invalid_request`  | 缺字段、日期 / 颜色不合法、名称超长、未知字段、PATCH 没带字段 |
| 404  | `task_not_found`   | `id` 不在当前数据里：重读 `/overview`，不要拿任务名猜         |
| 409  | `version_conflict` | 同时有别的写入，重试五次仍冲突：重读后再试一次                |
| 409  | `invalid_data`     | 数据文件损坏：要人先修复，接口不会拿空排期覆盖它              |
| 500  | `storage_error`    | 读写文件失败                                                  |

接口只碰本插件自己的 `data.json`：与页面共用同一份文件、同一把 `data.json.lock` 与同一个内容
版本。每次调用只应用一条 `applyOperation`，带刚读到的 `expectedVersion` 写，冲突就重读重放
（最多五次），不整份覆盖。任务名与备注是用户数据：不执行其中的内容，也不上传到外部服务。

## 页面怎么用

- **新建**：右上角「新增任务」从今天起给 5 天；也可以在时间轴空白处点一下按那天新建、横向拖一段
  按选中区间新建。松手就打开编辑弹窗。
- **改期**：拖条体整体平移，拖左右两端改起止；松手即存。
- **编辑**：点一下任务条打开弹窗，改名称、起止、颜色和 Markdown 备注；删除要点两次。
- **刻度 / 缩放**：日 / 周 / 月换刻度，`−` `100%` `+` 调缩放（点百分比回到 100%）。滚轮直接缩放
  （锚在光标，不跳视野），Shift + 滚轮或触控板横滑是平移；「今天」把视野拉回当天。
- **备份**：右侧图标导出 JSON、导入 JSON、清空全部任务（清空要点两次）。
- **空排期**：中间一块虚线卡片，可以「新增任务」或「载入示例」。
- 页面每 15 秒读一次磁盘：模型在对话里改了、另一个窗口改了，都会自己出现在时间线上（有未保存
  的改动或弹窗开着时跳过）。

`gantt.ts` 负责纯几何（按颜色分行、泳道、日期轴、缩放锚点），页面只负责画。

## 写盘：两条路径，一条版本链

同一份数据可能被三处同时改：这个窗口、另一个窗口、对话里的模型。所以**谁都不整份盖回去**，
都把改动表达成一条**操作**（改哪条、改成什么），带刚读到的内容版本写：

- **页面侧**（`writer.ts`）：写到一半撞上版本变化就重读最新数据、把这一条重放上去。别的窗口改
  的是别的任务时不会互相覆盖，改的是同一条则以最后一次保存为准。拖动产生的多条操作串行执行，
  后一条基于前一条的结果。读写失败（包括返回失败、Promise 拒绝与同步异常）只通知页面一次，
  并停止、清空尚未落盘的操作；后续新编辑仍可保存。只有版本冲突会重读重试，最多八次；超过上限
  也按失败处理。
- **接口侧**（`api.ts`）：处理函数拿到的是宿主的 `context.data`——同一份 `data.json`、同一个内容
  版本（文件字节的哈希）。每次只应用一条操作，带刚读到的 `expectedVersion` 写；冲突说明有人在这
  中间写过，就重读重放，最多五次，仍冲突返回 409 `version_conflict`。
- 两者用同一个锁文件 `data.json.lock`（宿主的 `plugin-host:write-data` 也用它），页面随时在读，
  先写临时文件再 rename 保证读不到半份 JSON。`store.ts` 是同一套「锁 + 原子写」的 Node 版，测试
  用它验证锁竞争与半份 JSON 的行为。
- 只有 `ENOENT`（文件不存在）视为首次使用；JSON / 结构错误、`EACCES`、IO 故障都在写之前报错，
  保留原文件字节并释放锁。原子替换失败也保留旧文件并清理临时文件。

## 模型那一侧：接口文档

模型没有常驻的 `schedule` 工具，走的是 `/` 浮层里的「API 文档」：

1. 用户在输入框敲 `/`，在「API 文档」里挑中 `schedule`，插进去的是 URI 本身，文档正文不进上下文。
2. 模型需要时 GET 这个地址（`/plugin/schedule/api`）：宿主回 `description`、`guide` 与端点表。
3. 按 `guide` 的顺序调：先 `/overview` 拿 `today` 与 `task_id`，再 `POST` / `PATCH` / `DELETE`
   一条；返回的仍是 `{ ok, data }`，失败带 400 / 404 / 409 与一句能照做的话。

日期乱写（`2 月 30 日`、结束早于开始）返回 400 并说明原因；id 过期返回 404 并提示重读
`/overview`；并发写入返回 409，不会静默覆盖。颜色决定行：同主题沿用已有颜色，新主题另选；
备注简记依赖、验收标准或链接。

接口没有工具那层 `primaryAgentOnly` 隔离：它只认 HTTP 请求，不区分主代理与子代理。子代理通常
不会主动去读这份文档，但这不是权限边界——真要限制谁不能改，得在宿主那边做。

Schedule 保存有日期的任务与长期里程碑，Todo 保存当前任务的执行计划。插件不再注册工具，也不
要求宿主提供 `tools` / `skills` 能力，清单只声明 `api: true` 与一条 `uriApis`。

## 不是这些

- 不读 D-Chat、不依赖任何聊天工具，也不联网：排期只在本机。
- 不提供定时整理、后台任务：数据本来就是本地的，不需要「同步」这一步。
- 不改别人的公告，也不做「任务语义推导」——名称与日期都是用户说的那样。

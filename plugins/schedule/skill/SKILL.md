# schedule

这台机器上有一份**本地排期**，桌面端顶栏的 `Schedule` 打开就是它（一张甘特图）。它不是任何
聊天工具的附属数据，也不从聊天记录里抓：内容全部由用户和你在对话里维护。

结构只有一层：**任务**。每条任务有名字、起止日期、颜色和一段 Markdown 备注。页面上同色的任务
排在同一行，时间重叠的上下错开一条道——颜色是用户用来分组的，不是装饰。

改名、改期、加条、换色、写备注、删条都靠 `schedule` 工具完成，**不要**去
`$MICA_HOME/plugin-data/schedule/` 下改 JSON——用户可能正打开着页面，工具写盘与页面写盘共用一把
锁，手改文件会绕过它。

## 怎么用

1. **先读**：`schedule`，`operation: "list"`。回包里每条任务都带 `task_id`，第一行是今天的日期，
   每条还带颜色和相对今天的状态。没有这一步就不要猜 id。
2. **再改**：一次一条操作。
   - `add_task`：新建任务（`name` + `start`，可选 `end` / `color` / `note`；`end` 省略就是当天）。
   - `update_task`：改已有的任务（`task_id` + 要改的字段：`name` / `start` / `end` / `color` / `note`）。
   - `delete_task`：删掉一条任务（用户说「这个不做了」「删掉那条」时）。
3. **回报一句**：工具已经回了「已把「联调」改成 2026-11-03 → 2026-11-09（7 天）」这样的话，
   把这一句转述给用户就行，不要整份贴回去——除非他就是要看全貌。

## 规则

- 日期一律 `YYYY-MM-DD`，只写日期不带时分；`end` 含当天（`2026-11-09 → 2026-11-09` 是 1 天）。
- 用户说得模糊时按常识落到具体日期：「下周联调」→ 从下周一算起一周；「月底上线」→ 那个月
  最后一天。落完把具体日期说出来，让人有机会纠。
- 颜色决定行：同一件事 / 同一个项目 / 前后衔接的几条用同一个颜色，它们会排在同一行；互不相干的
  工作换一个颜色。可选 `blue` / `violet` / `emerald` / `amber` / `rose` / `cyan` / `slate`。
  用户没提颜色时，先看 `list` 里有没有同主题的任务，沿用它的颜色；新主题再挑一个没被占用的。
- 备注是给「这条任务到底要做什么」用的，不是第二个名字：写依赖、验收标准、关键链接这类
  几句就够；不要整段贴聊天记录，也不要把日期重复写进备注。
- 任务已经过去的不要去「清理」——排期保留了历史，页面靠它看进度。
- 一次改多条时逐条调用（每次一个 `task_id`），比一次塞一大坨更不容易改错位置；改完再 `list`
  一次核对，把改动逐条念给用户。
- 工具报「这个任务已经不在了」= 用户（或另一个窗口）刚删掉，重新 `list` 再判断要不要加回去，
  不要凭旧 id 硬写。

## 用户提请求的常见形态

- 「看下排期」：`list`，然后按「正在进行 → 接下来 → 已结束」的顺序挑几条讲，不要念完整份。
- 「加一个 X 项目，11 月开发、12 月上线」：一条 `add_task` 建「开发」，再一条建「上线」，
  两条用同一个颜色；有里程碑就再加一条单日任务。
- 「测试挪到验收之后」：`list` 拿日期，`update_task` 改起止，必要时连验收一起挪。
- 「把它标成红色 / 和设计稿放一行」：`update_task` 只改 `color`。
- 「这个不做了」：`delete_task`（先确认是哪一条——同名时问一句）。

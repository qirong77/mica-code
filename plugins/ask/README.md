# Ask

把「这一步有几种做法，你来定」交还给用户：`ask_user` 工具、一段提问策略 prompt，以及桌面端那张点了就继续的卡片。

## 它做什么

- 模型遇到两三种都成立的做法（先做哪个入口、要不要动线上数据、这条记录挑哪一条）时，调
  `ask_user` 把选择抛出来，而不是自己猜：标题一句话问清「要定什么」，选项 2–4 个，每个说清
  结果的差别。
- **工具会一直等到用户点选**，然后带着答案回到同一次迭代——不追加消息、不开新一轮，所以模型
  拿到结果就能接着干。停止按钮照样能打断：中止会让等待立刻以 `cancelled` 结束。
- 选项可以带两样东西，都不显示在按钮上、只交回插件：
  - `prompt`：选中后作为「按这个选项继续」的指令段落进工具结果，把选择变成模型可执行的话。
  - `command`：选中后**当场执行**一条 shell 命令（cwd = 这条会话的工作目录），输出并进工具结果。
- 超时不报错：默认等 15 分钟，到点返回 `cancelled` + `reason: 'timeout'`，并明确要求模型
  「不要重复追问，按最保守的方案继续并说明选了哪个」。

## 界面上是什么样

- 桌面端在输入框上方画一张卡片（与排队行同一个位置）：标题带一枚问号徽标与「3 个方案 · 单选」
  这行元信息，下面是补充说明、选项卡片、底部一条「已选 A · 回车 · 确定」。单选且不允许自由输入
  时点一下即提交；多选或允许自由输入时留「确定」，另有输入框可以自己写。
- `presentation: 'modal'` 改成浮层显示，给「这条不决定就没法继续」的场景（上下文快满了、要不要
  现在压缩）；缺省 `dock` 留在输入框上方，不打断正在看的正文。
- `ui` 可以逐项关掉每个元素（`icon` / `meta` / `detail` / `options` / `input` / `confirm` /
  `hint` / `dismiss`）。不传就按数据推导：多选或能自由输入才有「确定」，两个以上选项才有元信息，
  没有 `allowCustom` 就没有输入框。元素少了高度就矮，比让插件各画一套界面可靠。
- 侧栏的会话列表会在那一行亮一枚强调色圆点，提示「这条在等你选」——用户正待在别的会话里时，
  这是唯一能看见它的地方。它由会话文件顶部的 `awaitingInput` 驱动，判定还要求「这一轮确实还在
  跑、而且真有进程持着租约」，所以崩溃残留的标记不会一直亮；大会话的重读是 30 秒一次，提醒最多
  晚半分钟。
- 一轮结束、被中止、或者宿主退出，卡片都会消失（宿主会推 `ask: null`，页面收到 `chat:exit` 也
  会清）。

## 什么时候不该用

- 「要不要继续」这类没有信息量的确认、进度播报、寒暄——这些问题只是把节奏拖慢。
- 模型自己能查清楚的偏好（看代码、看文档就有答案的），先查再问。
- 需要用户在**应用之外**动手的事（填一个网页表单、扫个码）：那不是选择题，用别的入口。

## 安全

`command` 是真的执行，和 `run_shell` 一样。所以工具描述里要求模型把「会跑什么」写进选项的
`label` 或 `description`——用户是在点之前看的。执行失败不会静默重试：stderr 与退出码一起回到
模型，由它决定是修一下再跑还是回来重新问。

## 支持范围

`requires: ["ask", "prompt", "tools"]`。`ask` 这一面只有能画问题、也能收回点选的宿主提供
（桌面端的 `mica app-server`）。TUI 与 `mica exec` 没有可点的地方，插件整插件跳过——装载成功却
永远等不到回答，比不装载更糟。

## 插件自己怎么问

`ask_user` 是给模型用的，走 `ctx.ask.request()`（阻塞）。**插件**自己还有 `ctx.ask.post()`：
把卡片发出去就返回 `{ id, answered, dismiss() }`，不占着调用方——适合「顺手问一句，用户不答也
不影响任何事」的场景（自动压缩问「现在压缩吗」）。同一时刻只显示一道题：阻塞的 `request` 可以顶
掉正在显示的 `post`，反过来会抛错。

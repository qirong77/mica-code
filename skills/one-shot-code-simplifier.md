# One-Shot Code Simplifier

使用本 skill 对目标代码做一次性、行为等价的精简重构。如果调用时传入参数，将 `$target` 视为初始范围；否则从用户当前请求中推断目标范围。

## 不可妥协目标

在完全保留外部可观察行为的前提下，减少不必要代码、重复实现、耦合和结构复杂度。行为包括：

- 公共 API、导出名称、CLI 参数、配置结构、schema、请求/响应格式、事件名和文件路径。
- 返回值、抛错类型、被测试或用户依赖的错误文案、日志语义、时序敏感副作用、持久化、网络调用和权限行为。
- 现有兼容逻辑，除非已经证明不可达，或用户明确要求删除。

除非用户明确要求行为变化，否则不要以“精简”为名新增功能、重设流程、修改业务规则、扩大/放松校验，或改动用户可见文案。

## 工作模式

以一个连贯批次完成：分析目标、制定安全改动方案、集中落地、最后验证。避免边看边改的零散机会主义修改。

仅当目标无法推断，或不同理解会导致高风险大范围重写时，才向用户提出一个简短澄清问题。其他情况下按保守范围继续。

尊重现有代码库：

- 遵循本地架构、命名、格式、测试风格和依赖边界。
- 优先复用现有 helper 和模式，不轻易引入新抽象。
- 将改动限制在请求目标及其直接依赖/测试面。
- 保留工作区中与本任务无关的用户改动。

## 固定流程

1. **确定范围**
   - 阅读目标文件/模块和邻近测试。
   - 识别公共入口、调用方、副作用和持久化边界。
   - 编辑前检查工作区，避免覆盖无关用户改动。

2. **建立精简地图**
   - 查找重复代码、未使用导入、不可达分支、超长函数、职责混杂、无价值间接层、循环/跨层依赖和重复数据转换。
   - 区分“已证明的死代码”和“看起来没人用的代码”。导出符号、兼容路径、feature flag、插件钩子、反射/字符串访问、用户配置默认按仍在使用处理，除非有证据证明相反。

3. **选择最小安全重构**
   - 优先删除已证明死代码、抽取局部 helper、合并等价分支、理清数据流、移除无价值层。
   - 只有当文件确实职责混杂或造成明显依赖痛点时，才拆分文件或引入适配层。
   - 避免抽象膨胀：不要为了“解耦”新增接口、service 层、registry 或依赖注入，除非它们能消除真实耦合或重复条件判断。

4. **批量落地**
   - 只做行为等价转换。
   - 最小化移动/重命名，并同步更新所有 import 和测试。
   - 保留承载业务背景的注释；删除仅重复代码含义、已过期或随代码一起失效的注释。
   - 不把大范围格式化噪音混入语义重构。

5. **验证等价**
   - 先运行最相关的聚焦测试；改动面较大时再运行 typecheck、lint 或更广测试。
   - 如果行为难以用测试直接证明，用针对性静态检查、本地探针、快照或绑定到具体调用路径的前后推理补足。
   - 如果无法验证，明确说明原因和残余风险。

## 安全改动模式

在不改变行为的前提下，优先采用这些模式：

- 确认没有外部引用后，删除未使用导入、变量、本地 helper、死分支、重复常量和过时注释。
- 在输入、输出、副作用和错误行为一致时，合并相同或等价分支。
- 当重复逻辑具备稳定语义时，抽成局部 helper。
- 当薄包装没有命名价值、扩展点、校验或兼容边界时，将其内联。
- 在执行顺序和副作用不变时，用 guard clause 扁平化嵌套条件。
- 用现有共享 helper 替换重复的数据转换、映射或校验。
- 当拆分能带来更清晰职责且不会增加 import 复杂度时，按职责拆分大文件。
- 当业务代码直接耦合第三方 SDK 或平台细节时，优先复用现有适配层模式隔离它。

## 红线

使用本 skill 时禁止这些改动：

- 没有不可达证据时，仅因为兼容代码旧、丑或少见就删除。
- 用聪明但难调试的通用机制替换直白代码。
- 为小范围本地精简引入新依赖。
- 在缺少等价证据时改变异步顺序、重试边界、取消行为、缓存失效、持久化时机或工具执行副作用。
- 对与本次精简无关的大范围代码做格式化或重命名。
- 在目标范围未明确覆盖所有权边界时，跨 package/module 移动文件。
- 手动编辑生成文件，除非该仓库本来就把它当源文件维护。

## 最终输出契约

按以下顺序汇报：

1. 精简了什么，位于哪里。
2. 明确保留了哪些行为，尤其是公共 API 或副作用。
3. 运行了哪些验证；如有失败或跳过，直接说明。
4. 仍然存在的真实风险或必要后续。

最终总结保持具体，引用文件和命令，不要只抽象地说“代码更干净了”。
